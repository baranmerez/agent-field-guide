Two questions that look like one

When the “Claude Code or Codex, which is better?” debate starts in a team, the two sides are usually arguing about different things. One talks about the model (“Claude plans better”), the other about the tool (“Codex has the stricter sandbox”). Both can be right, because there is no single thing on the table: the model and the harness are separate layers.

Remember the equation from the beginner level: Agent = Model + Harness. Claude Code is Anthropic’s harness; Claude models run inside it. Codex, as of November 2026, is the name of OpenAI’s agent product: a CLI, an IDE extension, a desktop app and a cloud environment. Models from the GPT family run inside it. The distinction used to be blurry, because for a while OpenAI shipped coding-specific models with a “-codex” suffix. Since GPT-5.4 there has been no separate coding model; coding ability was folded into the general model. So saying “the Codex model” today is technically wrong. Codex is a harness; the model is a GPT release such as gpt-6.1-sol or gpt-6-astra.

Why do we have to separate them?

Because when you want to fix a behavior, you need to know which layer to touch. If you are wondering why the agent changed a file without asking, the answer is not in the model but in the harness’s permission mode. If you are wondering why the agent called an API the wrong way, the answer is probably in the model’s training and in the context. As you saw in level 6, the same model produces noticeably different results in different harnesses: LangChain reports that, without changing the model at all and only changing the prompt, the tools and the middleware, it raised its Terminal-Bench 2.0 score from 52.8% to 66.5% (the company’s own measurement). According to an independent compilation, the same Opus 4.6 model spreads across a range of roughly 24 points on this benchmark depending on the harness; that figure comes from a secondary source and is not exact, but the direction is consistent.

You already know thisThe same PostgreSQL database can perform very differently through EF Core and through hand-written SQL. And the same EF Core behaves differently on different database engines. When you see an “application performance” number, you know it measures the engine and the access layer together. Agents are no different: a score measures the model and the harness together.

The layers are not fully independent either

One detail complicates things a little. Both labs train their models together with their own harnesses. OpenAI’s Codex guide says plainly that the model was trained on the apply_patch diff format and a dedicated terminal tool, and tuned to follow AGENTS.md instructions closely. Anthropic likewise writes that tool schemas such as bash and text_editor are “baked into training”, and that the model has been optimized on thousands of successful trajectories with those exact signatures. The result: a model is usually most comfortable in its own “home” harness. But this is not a law; teams such as LangChain argue that the training harness does not have to be the best harness for a given task.

In practice this means that when you use Claude Code with Claude models and Codex with GPT models, the two layers are tuned to each other. That is why, while comparing them in this level, we will always keep two questions apart: what can the model do? and what does the harness allow it to do, and what does it show it?

The cache difference can outweigh the price difference

In level 2 you saw how prompt caching works. Here the difference between the two sides starts to matter. At Anthropic, a cache read is normally 0.1 times the input price; but on Opus 5.5 and Sonnet 5.5 it is 0.05 times, and on Fable 5.1 0.025 times. The cache lives for 5 minutes by default and the timer resets on every hit; a 1-hour cache is also available if you want it. At OpenAI caching is automatic and on by default; a read is 0.05 times on GPT-6.1 Sol and 0.1 times on Astra. Because the overwhelming majority of input tokens in a long agent session are read from the cache, a model with a high-looking list price can turn out cheaper than expected in practice, or the other way round. Raising philosophy: constitution and Model Spec

Both labs describe how their models should behave in a public document, but their styles differ.

Anthropic: constitution

In January 2026 (21–22 January) a new Claude constitution was published and released to the public under CC0. The approach is to explain the why instead of listing rules one by one: values, judgment and an order of priorities. The order is roughly safety, ethics, guidelines and helpfulness. The goal is for the model to develop judgment that behaves sensibly even in situations it has never seen.

OpenAI: Model Spec

Commentators find the Model Spec more rule-based and structured. At the center of the document is an explicit “chain of command”: OpenAI, then the developer, then the user. We could not verify the exact current version number of the document; its principled structure, however, has been widely reported.

In chat mode this difference is felt as a difference in style, but for agents what matters is the common ground: both documents define an authority hierarchy. An operator or developer instruction, a user message and tool output do not carry the same weight. Tool output in particular, meaning a web page that was read, an issue body or a file, is data; it is not a party that gives instructions. This is the model-side half of the defense against prompt injection. The other half lives in the harness and is the subject of level 10. The model-side half is probabilistic: training lowers the chance that the model mistakes data for instructions, but does not bring it to zero.

Go deeper: is effort a model setting or a harness setting?Both. Effort (the thinking budget) is a parameter sent to the model in the API; but the harness decides what value it is sent with. In Claude Code you can raise it for a session with /effort high or /effort xhigh; that is also what is recommended for hard bugs and schema changes. The default effort depends on the model (see the table above). Higher effort is not always better: OpenAI also writes that high effort can increase the tendency to “overthink” and run unnecessary searches. In the next topic you will see why effort is a separate axis in benchmark comparisons.

What does a score measure?

When a new model comes out, the first thing you see is a benchmark table: “model X scores 80% on this test”. Learning to read that number is the cheapest way to protect yourself from marketing when choosing a tool. The rule is simple: a score is a single point in the product task set × version × model × harness × effort × infrastructure. If any of these axes differs, putting two scores side by side is like comparing two response times measured with different queries on two different databases.

Why was SWE-bench Verified dropped?

SWE-bench Verified was a subset of real issues from open-source Python projects plus their tests, verified by humans as “solvable”. Throughout 2024–2025 it was the main showcase for coding agents. On 23 February 2026 OpenAI announced that it would no longer report this benchmark. The reasoning has two parts:

  • Broken tests: An audit of the hardest 138 problems found that in at least 59.4% of them the tests also rejected correct solutions. In other words, the ceiling of the score was the quality of the tests, not the model’s ability.
  • Contamination: Models such as GPT-5.2, Opus 4.5 and Gemini 3 Flash could reproduce some fixes from memory. The benchmark itself had leaked into the training data.

In its place OpenAI recommended SWE-bench Pro, a harder set designed against Verified’s weaknesses. But you need to be careful here too: in Scale’s standardized common setup (SEAL), as of October 2026 the top results are around 60% (e.g. Muse Spark 1.1 at 61.5%, GPT-5.4 xHigh at 59.1%). The 89.9% that Anthropic reports for Opus 5.5, on the other hand, is a vendor figure measured in a different setup and not independently verified. Both carry the same benchmark name but cannot be compared.

Terminal-Bench and the weight of the harness

Terminal-Bench tests the agent with terminal tasks in a container: build, configure, debug, process data. For coding agents it is a more “agentic” measure than SWE-bench. As of November 2026 the official site shows version 4.0 as current. The figures circulating for this version come from aggregator sites and have not been verified, so in the lab below we use the better-documented results of version 2.0. These results show the core lesson very clearly: at the top of Snorkel’s 2.0 table are GPT-5.5 entries run with custom harnesses (84.7%) and Opus 4.7 with a custom harness (80.2%). When the same models are measured with vals.ai’s fixed harness (Terminus 2), GPT-5.5 scores 73.2% and Opus 4.8 70.0%. The 10-point gap in between is largely the harness’s doing.

Then there is infrastructure noise. Anthropic’s February 2026 post on “infrastructure noise in agentic coding evals” shows that infrastructure differences alone (timeouts, resource limits, network) can move scores. So a two-point difference may simply be the result the same model got on a different day.

Five questions to ask when reading a table row

  2. Which harness? The vendor’s own agent, the benchmark’s reference harness, or a custom harness tuned for the competition? Harnesses tuned for benchmarks differ from product harnesses in things like timeouts and non-interactivity; a product harness is optimized for safety, permissions and cost.

Two different security philosophies

The most visible architectural difference between the two harnesses is how the decision to let the agent “do something” is made. Roughly speaking, Codex is designed sandbox-first and Claude Code permission-first. Each later added the other’s mechanism, so today they share largely the same building blocks; but the defaults and the way of thinking differ.

Codex: walls first, questions second

In Codex every command runs inside an operating-system sandbox, and that is an inseparable part of the model. sandbox_mode takes three values:

  • read-only: can read, cannot write.
  • workspace-write: can write to the working directory; network is off by default (enabled with [sandbox_workspace_write] network_access = true). .git, .agents, .codex and .aws are read-only even when they are inside the writable root.
  • danger-full-access: no walls.

What happens to a command that hits the wall is decided by approval_policy: on-request lets the model ask for escalation and you approve it; never never asks, and the error goes back to the model. There is also a detailed (granular) table option. The old untrusted value has been retired; if it lingers in an old config file it can prevent Codex from starting. Codex’s “Auto” preset means workspace-write + on-request in folders under version control and read-only elsewhere. codex exec (non-interactive mode) is read-only by default. On the platform side, Codex uses Seatbelt on macOS, bubblewrap and seccomp on Linux, and the preferred “MXC” sandbox on Windows.

approval_policy = "on-request"
sandbox_mode    = "workspace-write"

[sandbox_workspace_write]
network_access = false

[features.network_proxy]
enabled = true
domains = { "registry.npmjs.org" = "allow", "db.example.test" = "deny" }

Claude Code: rules first, sandbox optional

In Claude Code every tool call goes through a permission mode and permission rules. The modes: default (“Manual” in the UI: asks about most things), acceptEdits (accepts file edits without asking), plan (read-only, no edits until the plan is approved), auto (a classifier model decides), dontAsk and bypassPermissions (never asks). As of November 2026 the default starting mode in the interactive terminal and in VS Code is auto (since v2.1.283); in claude -p and the SDK it is Manual (since v2.1.302). The 2025-era knowledge that “the default asks about everything” is out of date.

The operating-system sandbox in Claude Code is optional and off by default. When enabled, it uses Seatbelt on macOS and bubblewrap with socat on Linux and WSL2. There are two important limits: there is no native sandbox for Windows (you need WSL2), and the sandbox only wraps shell commands (Bash, PowerShell, Monitor); Read, Edit, WebFetch, MCP tools and hooks are outside the sandbox, under the control of the permission system. The network is restricted through a proxy with a domain allowlist (sandbox.network.allowedDomains, which starts empty). Anthropic reports that the sandbox cut permission prompts by 84%, because there is no need to ask about commands that stay inside the walls.

{
  "permissions": {
    "defaultMode": "acceptEdits",
    "allow": ["Bash(npm run test *)"],
    "deny":  ["Read(./.env)", "Bash(curl *)"]
  },
  "sandbox": {
    "enabled": true,
    "network": { "allowedDomains": ["registry.npmjs.org"] }
  }
}

On both sides some paths are protected. In Claude Code, writes to paths such as .git, .claude, .vscode, .idea, .husky, .devcontainer, shell startup files, .npmrc and .mcp.json are never auto-approved in any mode except bypassPermissions. The logic is the same: these files can run code on the next command or in the next session.

There are three things I want you to notice in the lab. First, the workspace-write sandbox runs rm -rf build/ without asking: the sandbox does not block destructive operations inside the working directory, it only blocks getting out of it. Model-based approvers: auto mode and auto_review

Both sides added an “approver model” to spare the human from being asked at every step. The reason is real data: according to Anthropic’s March 2026 post, users approve 93% of permission prompts. A prompt that gets “yes” that often becomes, after a while, a habit rather than a safeguard. Claude Code’s auto mode uses a two-stage transcript classifier and a server-side injection probe. The classifier only sees user messages and tool calls; the assistant’s own prose and tool results are stripped out so that injected text cannot “argue” with the classifier. The reported figures: a false-positive rate of 0.4% on 10,000 real actions; a miss rate of 17% on 52 real “overeager” actions; a miss rate of 5.7% on synthetic data-exfiltration attempts. After 3 consecutive or 20 total denials it hands back to the human. In Codex, approvals_reviewer = "auto_review" does a similar job: a reviewer agent looks at requests that already need approval and denies them when it is unsure (fail closed).

Caution: YOLO flagsIn Claude Code --dangerously-skip-permissions and in Codex --dangerously-bypass-approvals-and-sandbox (short name --yolo) remove all protection. Codex’s old --full-auto flag is no longer supported. In the Nx “s1ngularity” attack of August 2025, malicious npm packages invoked the agent CLIs installed on the machine with exactly these flags and sent them hunting for secrets. Only use these flags in a disposable container; consider disabling them by policy on team machines (in Claude Code, disableBypassPermissionsMode).

Key takeaways

  • In Codex the sandbox (sandbox_mode) is always there; approval_policy says what happens when you hit the wall.
  • In Claude Code the permission mode and rules are the foundation; the OS sandbox is optional, starts off, is not native on Windows and only wraps shell commands.
  • A sandbox does not block a destructive operation inside the working directory; it blocks getting outside the boundary.
  • Auto mode and auto_review are probabilistic layers; they go next to deterministic rules, not in place of them.

Different names, converging architecture

The good news: the extension mechanisms of the two harnesses are converging fast. Instruction files, the hook contract and the skill format now have largely the same shape. That means the investment your team makes in these tools (rules, automations, procedures) is not locked into one tool. But the differences in the details are worth knowing, because they may be the answer to “why wasn’t this rule loaded?”.

Instruction files: CLAUDE.md and AGENTS.md

Claude Code

A managed (organization) file, the user file ~/.claude/CLAUDE.md, the project file ./CLAUDE.md or ./.claude/CLAUDE.md, and the personal ./CLAUDE.local.md that stays out of git. At startup the ancestors from the root down to the working directory are loaded; those in subdirectories are loaded when a file in that directory is touched. Files are merged, they do not override each other; the closer one is read later. You can import with @path (up to 4 hops). .claude/rules/*.md files with a paths: header are loaded only when a matching file is touched. Target: under 200 lines per file.

Codex

Globally ~/.codex/AGENTS.override.md, otherwise ~/.codex/AGENTS.md (the first non-empty file). In the project, one file per directory from the root down to the working directory: AGENTS.override.md first, otherwise AGENTS.md, otherwise the fallback names you define with project_doc_fallback_filenames. All of them are merged; reading stops when the total reaches the project_doc_max_bytes limit (32 KiB by default). It is said to have no import mechanism, but only a third-party source says so.

If your team uses both tools, the most robust setup is this: keep the shared project rules in AGENTS.md, and put only an @AGENTS.md line and a few Claude-specific notes in CLAUDE.md. How Claude Code handles an AGENTS.md file directly has changed from version to version, so do not guess what gets loaded; check it in Claude Code with /context. On the Codex side, too, checking which files were read at the start of a session is a good habit.

Hooks: the same contract

In level 8 we will go deep into Claude Code hooks; here the comparison is what matters. As of November 2026 Claude Code offers 33 hook events and five handler types (command, http, mcp_tool, prompt, agent). Codex has 14 events: SessionStart, SessionEnd, PreToolUse, PermissionRequest, PostToolUse, PreModelRequest, PostModelRequest, PreCompact, PostCompact, UserPromptSubmit, SubagentStart, SubagentStop, Stop and Interrupt. What really matters is the shape of the contract, and that is almost identical:

  • The hook receives the event information as JSON on stdin.
  • Exit 2 blocks the action; text written to stderr goes back to the model as the reason.
  • For PreToolUse, hookSpecificOutput.permissionDecision: "deny" in the JSON output blocks.
  • For Stop and UserPromptSubmit, a top-level {"decision": "block", "reason": "…"} is used.

The difference is in the trust model: Codex runs hooks with hash-based trust, meaning that if the content of a hook you approved changes, it needs to be trusted again. In Claude Code a project’s hooks become active once workspace trust has been granted. Both approaches exist for the same reason: a configuration file in the repository is a file that can run code on your machine. In level 10 we will look at real CVEs for this.

Skills: SKILL.md is now a common standard

A skill is a folder with a SKILL.md file inside that has a front-matter header. At first only its name and description enter the context; the body is loaded only when needed, and extra files only when referenced. Thanks to this “progressive disclosure”, defining dozens of skills does not fill up the context. Anthropic handed the SKILL.md format over to the Agentic AI Foundation on 22 October 2026; the format no longer belongs to a single company. Together with AGENTS.md and MCP, it forms the common language of the two worlds.

You already know thisThis convergence resembles the Language Server Protocol in the editor world. Once, every editor needed a separate plugin for every language; with LSP, language support became an asset independent of the editor. AGENTS.md, SKILL.md, MCP and the shared hook contract likewise turn your team’s knowledge and automation into an asset independent of the harness.
In practiceWrite hook scripts without depending on harness-specific fields: read tool_name and tool_input from stdin and give the decision with exit 2. That way the same block-db-writes script works in both tools. The only tool-specific part is the configuration file you wire the script into.

Key takeaways

  • Claude Code merges instruction files, allows imports and loads rules by path; Codex takes one file per directory and cuts off at 32 KiB.
  • Keep shared rules in AGENTS.md and import them from CLAUDE.md; verify what was loaded with /context.
  • The hook contract is the same on both sides: stdin JSON, exit 2 to block, permissionDecision, decision: "block".
  • SKILL.md, AGENTS.md and MCP are harness-independent assets; invest in them.

A no-hype decision guide

We will not declare a winner in this topic, for two reasons. First, both sides ship a release every few weeks; today’s advantage may be reversed three months from now. Second, the answer to “which is better?” depends on your work: which operating system, which security requirement, which kind of work, which budget. What we will do in this topic is lay out, situation by situation, the real differences that affect the decision.

A protocol for running your own comparison

If you need to make a real decision, a small experiment you can run over a weekend is enough. What matters is that the experiment follows the eval discipline you will see in level 9.

  1. Pick tasks: 20–30 jobs your team actually did in the last three months. Mix easy, medium and hard. The success of each must be checkable automatically: certain tests must pass, certain files must not change.
  2. Level the environment: The same commit, the same instruction file (shared AGENTS.md, imported by CLAUDE.md), the same permission level. If the sandbox is on in one and off in the other, what you are comparing is the security setting.
  3. Repeat: Run each task at least three times in each tool. A single run is chance.
  4. Record four things: did the tests pass, how many turns did it take, what did it cost, would a human accept the diff.
  5. Read the transcripts: Check whether the failures were “fair”. Was the task ambiguous, did the harness block it, or did the model get it wrong?
In practice: using both togetherMany teams use the two tools together, and that is a legitimate choice. For example, having one tool write the code in a session and the other do an independent review can catch different mistakes than having the same model review its own work. All you need for this is to keep instruction files, skills and hook scripts portable; you saw how in the previous topic.
Myth“One is secure, the other isn’t.” The security of both tools depends largely on your settings. If you run Codex with --yolo, there is no sandbox; if you set up Claude Code with the sandbox, deny rules and PreToolUse hooks, you get a fairly narrow box. The defaults differ; the ceilings are similar.

Key takeaways

  • There is no winner; there are differences that stand out depending on your work, operating system, security requirements and budget.
  • For a team working natively on Windows the sandbox difference is concrete: Codex has a native Windows sandbox, Claude Code needs WSL2.
  • To decide, measure repeatedly on your own tasks in a level environment; read the transcripts.
  • If you keep your investment in instructions, skills and hooks portable, switching tools gets cheap.
