The model doesn’t remember you

LLM APIs are stateless. With every request, the entire conversation is sent to the model again: the system prompt, tool definitions, all previous messages, tool results, images and your latest message. The model carries nothing over from the previous call, and the server keeps no session for you.

You already know thisThis is a stateless HTTP service. Picture a client that keeps no session on the server and carries the whole state with every request: a shopping client that resends every item in the cart with each request, or a token that carries all its claims on every call. The server stays simple; the price is paid by a payload that grows with every request.

What is inside a request?

The entire text the model sees at that moment is called the context. A coding agent’s request typically contains:

System prompt

The harness’s own instructions: role, rules, how to use tools. Often thousands of tokens.

Tool definitions

Each tool’s name, description and JSON schema. With many MCP tools connected, this can reach tens of thousands of tokens.

Project context

Rule files such as CLAUDE.md and AGENTS.md; loaded again in every session.

Messages

User messages, the model’s answers, tool calls and tool results. The fastest-growing part: a single test output or file read can be thousands of tokens.

Thinking blocks

On Opus, Sonnet and Haiku 5.5, thinking blocks from earlier turns are kept in later turns and billed as input. On older models the API stripped them out.

The output the model produces becomes part of the input on the next turn. That is why an agent session is a transcript that grows at every step. A 30-turn session rereads turn 1 thirty times.

“Memory” is always the harness’s job

There is no magical persistence on the model side. Every feature offered as “memory” is the harness putting some text back into the next request:

  • The rules file (CLAUDE.md, AGENTS.md) is read from disk at the start of every session and added to the context.
  • “Resuming” a session means loading the old transcript from disk and sending it again.
  • In long conversations, summarizing the old parts and sending the summary (compaction) is also a text operation; topic 4.
  • Saying “write your notes to a file” moves information outside the context and has it read back when needed.
Myth“Claude Code knows my project; I explained the architecture to it yesterday.” What you explained in yesterday’s session lived in yesterday’s transcript. Today’s session doesn’t see it unless you or the harness load that information again. If you want knowledge to carry over to the next session, write it to a file and make sure the harness loads that file.
In practiceStart a new session for each new task. Continuing with unrelated work in an old session means resending the whole transcript of the previous work with every request: it costs money and scatters attention (topic 3). Give the new session the information it needs as a short note.

Key takeaways

  • The API is stateless: every request carries the system prompt, the tools and the whole history again.
  • Output is the next turn’s input; the transcript grows at every step.
  • Memory is the harness putting text back; there is no persistence in the model.

How big is the window?

The context window is the maximum number of tokens the model can process in a single request. The input and the output to be generated count towards this limit together. As of November 2026, the picture for the major providers’ current models looks like this:

A rough measure from Anthropic’s documentation: with the current Claude tokenizer, 1M tokens ≈ 555K English words. Because text in non-English languages such as Turkish takes more tokens, fewer of its words fit in the same window (level 0).

What happens when you exceed the limit?

  • If the input alone exceeds the limit: the request is rejected with HTTP 400 “prompt is too long”.
  • If input + max_tokens exceeds the limit: on 4.5 and later models the request is accepted; the model stops when the window is full and stop_reason is model_context_window_exceeded. Your code has to handle the possibility that the answer was cut off.

Some models can see for themselves how much of the window is left: models such as Sonnet 5, Sonnet 4.6 and Haiku 4.5 get the total budget injected, plus a “this many tokens left” note after every tool call. Newer Opus and Sonnet 5.5 have optional task budgets instead.

Where do the tokens go in an agent?

The idea “1M tokens, I’ll just put the whole repo in” is wrong on two counts. First, the window fills with a fixed load before you type a single line: the system prompt, tool definitions, the rules file. Second, the agent’s own work (reading files, running tests, inspecting logs) is the biggest consumer of the window. The output of a single failed test run can be longer than your entire conversation.

Key takeaways

  • In November 2026, the major providers’ current models have a window of ~1M tokens and an output limit of 128K.
  • Input and max_tokens count together; exceeding the limit means a 400 error or an answer cut off halfway.
  • The fixed load (system, tools, rules) and tool outputs eat most of the window; measure and prune.

More context is not better

Remember the attention intuition from level 0: every token looks at every previous token, and that “looking” is shared out through a softmax. Every token added to the context takes a share of a limited attention budget. Irrelevant tokens dilute the signal of the relevant ones. There are two strong measurements of this intuition.

Lost in the middle

In the study by Liu and colleagues (TACL 2024), models were given 20 documents with the answer to the question placed in one of them. Accuracy came out U-shaped: highest when the answer was in the first or last document, lowest when it was in the middle. The effect showed up in base models too, so it is not just a side effect of chat training. Raising the number of documents from 20 to 50 brought almost no benefit. This phenomenon is called lost in the middle.

Context rot

Chroma’s July 2025 study tested 18 models, including Claude Opus 4, Sonnet 4, GPT-4.1, Gemini 2.5 and Qwen3. The findings:

  • Performance drops as the input gets longer, even when the task is simple, and the drop is not smooth.
  • The drop accelerates as the semantic similarity between the sought information (the needle) and the question decreases.
  • Even a single distractor hurts; four hurt more. Some distractors are far more harmful than others.
  • A surprise: randomly shuffled haystacks gave better results than logically coherent ones across all 18 models.
  • On LongMemEval (306 prompts), focused input (~300 tokens) beat the full input (~113K tokens) on every model. With thinking on, the gap narrowed but did not disappear.
  • Even on a trivial task such as copying repeated words, accuracy fell with length; some models started producing random words after a few hundred words.

Anthropic’s own documentation adopts the term as well: more context is not automatically better; as the token count grows, accuracy and recall fall. This is called context rot.

Myth“Context is 1M now, so there’s no need for RAG or selective file reading; I’ll put everything in.” The window got bigger, but the attention budget is shared out by the same logic. Measurements show that a few thousand relevant tokens give better results than the same information buried among hundreds of thousands of irrelevant tokens. And every token costs money too.

The engineering consequences

  1. Less, but relevant. Instead of having it read fifty files and saying “now fix it”, have it read the three relevant ones. Giving the agent a file path and a line range beats telling it to “search everywhere”.
  2. Critical instructions at the start or the end. A constraint buried in the middle of a long context is the easiest thing to lose. Persistent rules go in the rules file (at the start), the essence of the task in the last message.
  3. Prune noisy tool output. Instead of putting a 4,000-line test log into the context in full, filter for the failing tests. Log lines that look similar but are irrelevant fit the definition of a “distractor” exactly.
  4. New job, new session. The leftovers of the previous task are distractors for the next one.
  5. Hand exploration to a sub-agent. Running a broad search in a separate context and bringing only its summary back to the main session keeps the main context clean (topic 4).

Key takeaways

  • Accuracy falls as the context gets longer; information in the middle gets lost more easily than at the ends.
  • Distractors and low semantic similarity speed up the drop.
  • A focused context is almost always better than the full one: more accurate, faster, cheaper.

When the window fills: compact, prune, distribute

Sooner or later a long agent session reaches the limit of the window, or at least the zone where context rot becomes noticeable. The harness has to do something. Anthropic’s context engineering post and documentation describe a few techniques:

Compaction

A model summarizes the history; the summary replaces the original messages and the session continues from the summary.

Clearing tool results

Old tool results (files read, test outputs) are removed from the context. Anthropic describes this as “the safest, lightest-touch form of compaction”: if needed, the tool is simply called again.

Structured notes

The agent writes progress, decisions and open items to a file outside the window and reads it back when needed.

Sub-agents

Exploration happens in a separate context, spending tens of thousands of tokens; only a 1,000–2,000-token summary comes back to the main session.

Just-in-time retrieval

The context holds file paths and identifiers instead of content; content is loaded when needed. Claude Code loads the rules file up front and searches the rest with glob and grep.

Compaction in Claude Code

Claude Code’s compaction summarizes the history: it tries to keep architectural decisions, open bugs and implementation details, and it drops repeated tool output. The session then continues with the summary and the 5 most recently accessed files. /compact triggers this manually; it also runs automatically as the window nears full. There are similar tools on the API side: server-side compaction in beta for Claude 4.6 and later, and context editing, which clears old tool results or thinking blocks.

Summarization is lossy

A model writes the summary, and it decides what matters. An exact error message, the precise line number in a file, a small but critical constraint you mentioned at the start of the conversation: any of these can get lost in the summary. Most of what an agent “forgets” at the end of a long session comes from here. The problem is that the loss is silent: the agent won’t tell you “I forgot that rule”; it acts as if it never heard it.

What survives compaction?

In practicePut everything that must not be lost outside the conversation. Persistent rules go in the rules file (CLAUDE.md, AGENTS.md): the harness reloads them from disk. For exact error texts, decisions and to-dos, ask the agent to keep a notes file. When compacting manually, say what it must keep (in Claude Code you can add instructions to the /compact command). And if possible, move to a new session when the work is done, so compaction is never needed at all.
CautionCompaction has a hidden cost: because the message history changes completely, the message part of the prompt cache is invalidated and the next request rewrites it. You will see this, with its price, in the simulation in the next topic.

Key takeaways

  • Techniques against a filling window: compaction, clearing tool results, notes, sub-agents, just-in-time retrieval.
  • Compaction is lossy and silent; exact values and early constraints are the first to go.
  • Write persistent knowledge to a file, not into the conversation; the harness loads it back every time.

Never compute the same prefix twice

The price of a stateless API is that the whole history is reprocessed on every request. Prompt caching largely erases that price. The mechanism is familiar from level 0: the provider stores the processed KV cache of a prompt prefix. If a later request starts with a byte-for-byte identical prefix, the prefill of that part is skipped. The result is both cheaper and faster (TTFT drops).

The key word is prefix. The cache uses the part that matches from the start of the request. If a single character changes near the start of the prefix, everything after it is invalidated. Hence the golden rule: static content first, variable content last.

How does it work at Anthropic? (November 2026)

  • Prefix order: tools → system → messages. A change in the tools invalidates everything; a change in the system invalidates the system and the messages.
  • Two ways to use it: automatic caching (a single top-level cache_control in the request; the breakpoint moves forward as the conversation grows) or up to 4 explicit breakpoints.
  • Lookback: if no match is found, the system goes back up to 20 blocks looking for an earlier cache write.
  • Minimum prefix: 512 tokens on 5.x models (1,024–4,096 on older models). Below that, nothing is cached, silently.
  • TTL: 5 minutes by default, refreshed for free on every hit; 1 hour if you want.
  • Warm-up: a cache entry exists only after the first response has started. Cold parallel requests sent at the same moment all miss.
  • Isolation: the cache is separate per organization or workspace.
  • Window: cached tokens take up space in the context window too. Caching lowers the price; it doesn’t enlarge the window.

The picture at OpenAI and Google

Same mechanism, different details. At OpenAI, caching is automatic and on by default; the whole processed prefix has to match. On GPT-5.6 and later the minimum prefix is 1,024 tokens, and explicit breakpoints with a 30-minute (default) or 12-hour TTL are supported; writes cost 1.25× (30 min) or 2.5× (12 h), reads 0.1× (0.05× on GPT-6.1 Sol and Terra). Because caches live on individual machines, prompt_cache_key, which influences routing, and the first tokens of the prefix affect the hit rate. At Google, implicit caching is on by default for 2.5 and later models; on Gemini 4 Argon and 3.x the minimum prefix is 4,096 tokens.

In practiceIf you are writing your own agent: keep the tool list fixed for the whole session, don’t put a clock or a request ID into the system prompt (put it in the last message if you need it), don’t change effort or the thinking setting mid-session, and warm the cache with a single request before a parallel fan-out. And always watch cache_read_input_tokens and cache_creation_input_tokens: if the prefix is under 512 tokens or something changes on every request, the cache is silently not working.

Key takeaways

  • Prompt caching stores the KV cache of a byte-for-byte identical prefix: a change in the prefix invalidates everything after it.
  • The order is tools → system → messages; static first, variable last.
  • On 5.5 models a read costs 0.05× the base price; a write 1.25× (5 min) or 2× (1 h). The TTL is refreshed on a hit.
  • Timestamps, tool changes, effort changes, long breaks and compaction break the cache.

Working out the bill and the wait

You now have all the pieces: the token (the unit), statelessness (every turn resends everything), the prefill/decode asymmetry (output is expensive and slow), caching (a repeated prefix is cheap). Put them together and you can build a realistic model of cost and latency.

A cost model for a session

Let P be a fixed prefix (system + tools), a the new input added each turn, and o the output each turn. The request on turn t is roughly P + (t−1)·(a+o) + a tokens. Without caching, the total input sent over N turns grows with the square of N: the transcript is read once more every turn. With caching, the earlier prefix is paid at the read price (a small fraction of the base price) and only the newly added part at the write price. In long sessions the difference is measured in multiples.

A latency model

Total time ≈ TTFT + output tokens / decode speed. TTFT grows with the length of the uncached input; caching shortens it. The decode part is proportional to the output length, and caching doesn’t affect it. Thinking tokens add to the output side even when invisible. In Claude, leaving the thinking display omitted makes the first text token arrive sooner, because the thinking isn’t streamed. Absolute decode speeds vary a lot by model, tier and load; measure them in your own environment. Anthropic also offers a higher-priced “fast mode” for Opus.

Makes it cheaper

A fixed prefix and a high cache hit rate, focused context, a short output format, the smallest model that does the job, the right effort, Batch for non-interactive work.

Makes it pricier

Cache breakers, noisy tool output, unrelated work in one session, needlessly high effort, long explanations, prompts that spill into higher window tiers.

Measure

usage in every response: input, cache read, cache write, output. Log them and track the cost per turn; most surprises are a cache breaker.

Level 2: key takeaways

  • The API is stateless; every request carries the whole transcript again, and without caching the cost grows with the square of the number of turns.
  • Even with a ~1M window, context rot is real: focused context is more accurate, faster and cheaper.
  • Compaction is lossy; persistent knowledge must live in a file.
  • Prompt caching is prefix matching: static first, variable last; learn to recognize the breakers.
  • Output costs ~5 times as much as input; decode time grows with output length, TTFT with uncached input.
