Explore, plan, implement, verify

The teams that get the most out of Claude Code share a common rhythm, and it has not changed since 2025: first have it read, then have it plan, then have it implement, and last have it verify. What has changed is that the tools supporting this rhythm have matured, and the official guide has boiled it down to a sharper statement.

The current “best practices” page ties the work to three sentences: tell Claude what it cannot see, give it a check it can run, and enforce the rules that must have no exceptions. The first is the job of context (this lesson and CLAUDE.md), the second is the job of verification (tests, the compiler, /verify), the third is the job of the harness (permission rules and hooks). Every lesson in this level unpacks those three sentences.

Why plan first?

In level 5 you saw the agent loop: every turn is a model call that rereads the whole history. An agent spinning for twenty turns on a misunderstood task burns context, money and your time, and ends up producing a diff you will have to revert. Spending five minutes reading the plan is the cheapest debugging method there is. Plan mode exists exactly for this: the agent can read files and run read-only commands, but it cannot edit anything until the plan is approved. If auto mode is available, commands approved by the classifier also run in plan mode.

You cycle through the modes with Shift+Tab. As of November 2026 the cycle is: auto → default → acceptEdits → plan → (bypassPermissions) → auto. The mode in parentheses only joins the cycle if it has been enabled; dontAsk is not in the cycle at all and can only be turned on with a command-line flag.

The Shift+Tab cycle

Press the button to move to the next mode. For each mode, see what happens to four representative actions. The “bypass enabled” box adds bypass mode to the cycle, as long as it has not been disabled in settings.

A good task description

In level 3 we talked about writing a prompt like a work order. In Claude Code the practical version is: state the symptom, where to look, and what counts as “done”. The official guide’s example replaces “fix the login bug” with “login fails after session timeout; check the token refresh in src/auth/; write a failing test that reproduces the issue first, then fix it”. Apply the same pattern to your own work:

order total is wrong, fix it
In example.orders, discounted orders get the
discount applied twice (e.g. order_id 1042).
Look at the calculation in src/Orders/OrderTotal.cs.
First write a failing test that reproduces this,
then fix it. dotnet test must pass; no migration.

Anatomy of a session

A realistic session for the task above, in the fictional example_app repository. Step through it; at each step, watch which mode you are in, what the agent is doing and where you step in.

Steering: when do you intervene?

  • Esc stops the agent mid-action. The guide’s advice: “watch the first minute, and press Esc the moment it starts to drift”.
  • Esc Esc or /rewind opens the rewind menu (the last lesson of this level).
  • After two failed fixes, do not write a third: clear with /clear and start again with a better prompt. A context full of failed attempts keeps the model in the same rut.
  • /btw lets you ask a side question without polluting the history.
  • /rename names the session, and claude --resume <name> brings you back to it.
  • /verify builds and runs the application; /goal has a separate model check a condition every turn; /code-review gets the change reviewed.
  • /effort high or xhigh raises the thinking budget for subtle bugs and schema changes.
You already know thisIt is like working with a talented new junior. First you ask them to read the code, then to explain what they intend to do; you do not let them touch anything until you have approved the plan. When the work is done, you run the tests together. The difference: this junior is extremely fast, never gets tired, and may forget the beginning of the conversation.

Key takeaways

  • Tell it what it cannot see, give it a check it can run, enforce no-exception rules in the harness.
  • Plan mode reads but does not edit; reading the plan is the cheapest debugging there is.
  • The Shift+Tab cycle: auto → default → acceptEdits → plan → (bypass) → auto. dontAsk only via a flag.
  • After two failed fixes, /clear and a better prompt.

Instructions read in every session

CLAUDE.md is a Markdown file that Claude Code loads into context at the start of every session. In level 3 we said that for lasting impact you should invest in the layers that are added automatically to every request; this is that layer. But let us make one thing clear up front: CLAUDE.md is guidance, not enforcement. Claude reads it and mostly follows it; but, in the words of the official docs, it is allowed to decide that a line does not apply in a given situation. That is why the most important sentence in the guide is this one: If you keep adding emphasis to a CLAUDE.md line and Claude still misses it, that line belongs in a hook. Adding “IMPORTANT” probably will not fix it.

Hierarchy

ScopeLocationFor whom
Managed (organization)/etc/claude-code/CLAUDE.md, on Windows C:\Program Files\ClaudeCode\CLAUDE.mdAll users; deployed by IT
User~/.claude/CLAUDE.mdAll your projects
Project./CLAUDE.md or ./.claude/CLAUDE.mdThe team; committed to the repo
Local./CLAUDE.local.mdYou, this project; stays out of git
Rules.claude/rules/*.md (with a paths: header)Only when matching files are touched

At startup, the files in the ancestor directories from the root down to the working directory are loaded; files in subdirectories are loaded when a file in that directory is touched. The files are concatenated, they do not override each other: the closer one is read later. This resembles the CSS cascade but is not quite the same; if two rules conflict, both stay in context and the model has to decide which one applies. Resolve the conflict yourself.

With the @path/file.md syntax you can import other files. The path is relative to the importing file; at most 4 hops of depth are allowed; importing a file from outside the project requires a one-time approval. Let us correct an important misconception: imports do not reduce context cost; the imported file is loaded in full as well. The real savings tools are rules with a paths: header under .claude/rules/, and skills. The official target is under 200 lines per file. For auto memory (MEMORY.md), the first 200 lines or 25 KB are loaded. In monorepos you can leave out the files of unrelated subprojects with claudeMdExcludes.

---
paths:
  - "**/*.sql"
---
- Always schema-qualify names: example.orders, example.customers.
- DML scripts start with BEGIN and end with ROLLBACK; a human puts in the COMMIT.

What goes in, what stays out?

Write

  • Exact verification commands: how to run a single test file, typecheck, lint.
  • Misleading code: “src/legacy/ is still live, but do not copy its patterns into new code”.
  • Decisions that are not in the repo, and their reasons.
  • Anything you have corrected twice.

Don’t write

  • Things that can be inferred from the code (“we use Angular in this project”).
  • Personal preferences: those go in CLAUDE.local.md.
  • Long procedures: those go in a skill.
  • No-exception prohibitions: those go in a deny rule or a hook.
  • Secrets, tokens, passwords. Never.

The sample file in the official docs is a good summary of these principles. Here is a version adapted for a .NET project:

# Commands
- Build: dotnet build -warnaserror
- Single test class: dotnet test --filter FullyQualifiedName~OrderTotalTests
- Format check: dotnet format --verify-no-changes

# Conventions
- Use src/Common/Result.cs for error returns; do not throw raw exceptions
- src/Legacy/ is still live, but do not copy its patterns into new code

# Gotchas
- Integration tests need DATABASE_URL; see .env.example
- example.orders.amount is numeric(12,2); use decimal on the C# side

Key takeaways

  • CLAUDE.md is guidance, not enforcement. If a rule is still missed after you add emphasis, it belongs in a hook.
  • Files are concatenated, not overridden; resolve conflicts yourself.
  • @import does not reduce cost; savings come from .claude/rules (paths) and skills.
  • Write commands, misleading code, decisions not in the repo and anything corrected twice; everything else goes elsewhere.

Permission rules: who gets what, in which order

In level 7 you saw the permission modes. Modes are the coarse setting; fine-tuning is done with permission rules. A rule has the form Tool or Tool(specifier): Bash(npm run *), Read(./.env), WebFetch(domain:example.com), mcp__server__tool, Skill(skill:release). Rules go into three lists: deny, ask, allow.

Evaluation order: deny, ask, allow

The most important sentence of this lesson: deny is evaluated first, then ask, then allow; the first match wins, and specificity does not matter. In the words of the docs, an allow rule cannot carve an exception out of a deny rule. For someone used to firewall rules this may feel backwards at first; there, usually the most specific rule or the first rule in order wins. Here, the list type wins.

How do Bash rules match?

  • The pattern is a glob applied to the whole command. Bash(npm run *) matches npm run build, not npm install.
  • The space before * matters: Bash(git diff *) only matches git diff …; Bash(git diff*) also matches git diff-index.
  • Compound commands are split: && || ; | |& & and newline are separators. For allow, every subcommand must be permitted; for deny and ask, a match on any subcommand is enough. The contents of $(…), subshells and loops also count as subcommands.
  • Wrappers are stripped: timeout time nice nohup stdbuf command builtin noglob. timeout 30 npm run build is evaluated like npm run build.
  • Leading environment variable assignments (FOO=bar command): allow rules do not match past them, deny rules do. So nobody can trick an allow with an environment variable, but nobody can escape a deny that way either.

Permission rule matcher

Edit the rules, type a command or path, or pick one of the ready-made examples. The matcher splits the command into subcommands, strips wrappers and, for each piece, shows which rule matches in deny → ask → allow order. It is a teaching matcher built from the rules in the docs; it does not mimic every detail of the real implementation.

Caution: Bash deny is not a security boundaryThe docs say this explicitly. A Bash(curl *) deny rule does not stop /usr/bin/curl … or sh -c 'curl …'; nor does it stop curl written into a script file and executed. Deny rules are a good seatbelt against accidental mistakes. A real boundary is a mechanism that works regardless of how the command is written: the sandbox’s network allowlist, operating system permissions, the narrow scope of the agent’s credentials. Pair deny rules with these; do not substitute them.

Read and Edit paths

File rules use gitignore syntax and there are four path forms: //absolute/path, ~/home/directory, /relative-to-settings-file-source and ./relative. Careful: a path starting with a single slash is not absolute; it is relative to the project where the settings file lives; an absolute path needs a double slash. Windows paths are normalized: C:\Users\alice becomes /c/Users/alice on the rule side; to block .env files on every drive you write //**/.env. A Read deny rule also blocks Edit and Write for the same path. A misconception: a file called .claudeignore has no effect whatsoever.

Settings layers

Rules live in settings.json files, and the precedence order is: managed settings > --settings on the command line > .claude/settings.local.json > .claude/settings.json > ~/.claude/settings.json. Arrays such as permissions.allow are merged across layers, not overridden. Two details matter for security: allow rules in a project wait until workspace trust is granted, while deny and ask rules apply immediately; and a defaultMode: auto or bypassPermissions value in a project or local file is ignored (since v2.1.257). So a repo you clone cannot put itself into bypass mode on its own.

{
  "permissions": {
    "deny":  ["Bash(git push --force *)", "Read(./.env)", "Read(//**/.ssh/**)",
              "Edit(./src/Generated/**)"],
    "ask":   ["Bash(git clean *)"],
    "allow": ["Bash(dotnet build *)", "Bash(dotnet test *)", "Bash(git diff *)", "Bash(git status)"]
  }
}

There are new keys for organization-level hardening: permissions.blockReadsOutsideWorkingDirectories and permissions.blockWritesOutsideWorkingDirectories (v2.1.314), disableBypassPermissionsMode and disableAutoMode. When these are placed in managed settings, users cannot loosen them.

In practicePut only the safe allows everyone will want and the hard denies into the team settings (.claude/settings.json): build and test commands open, force push and secret files closed. Write personal conveniences into settings.local.json. If you approve a command every day, adding it to allow reduces approval fatigue; 93% of approval prompts get approved anyway.

Key takeaways

  • deny → ask → allow; the first match wins; allow cannot carve an exception out of deny.
  • In a compound command, every piece must be permitted for allow; one piece is enough for deny and ask. Wrappers are stripped.
  • The space before * matters; a single-slash path is relative to the project, a double-slash path to the root.
  • Bash deny is not a security boundary; pair it with the sandbox and narrow credentials.
  • Arrays merge across layers; project allows wait until trust is granted.

Six tools, one question: who decides?

There are six ways to extend Claude Code, and the most common mistake teams make is handing the job to the wrong tool: writing a no-exception rule into CLAUDE.md, putting a one-line fact into a skill, setting up an MCP server for a system that already has a good CLI. The key to picking the right tool is a single question: should Claude decide this behavior, or the harness?

Claude decides (probabilistic)

CLAUDE.md, .claude/rules, skills, subagent definitions, instructions in the prompt. The model reads them and usually follows them; depending on context it may also choose not to.

The harness enforces (deterministic)

Hooks, deny rules, a strict sandbox, managed settings, --max-turns and --max-budget-usd, CI checks, branch protection. They work regardless of what the model thinks.

The tools one by one

Subagent.claude/agents/*.md: separate context, its own prompt, tools, modelWhen delegated toIsolating noisy work, restricting tools, parallelism; only a summary comes back
MCP serverExternal tools and dataTool names are deferred by default (tool search)Systems without a good CLI; if gh or aws exists, prefer them

Plugin.claude-plugin/plugin.json: a bundle of the aboveDescriptions of enabled plugins in every sessionDistributing a setup to the team or a marketplace; runs with your permissions

The old custom commands (.claude/commands/*.md) have merged into skills; if you want to write a new “slash command”, write a skill. A skill’s frontmatter has fields such as name, description, when_to_use, allowed-tools, disable-model-invocation, model, effort, context: fork and paths. A powerful feature is dynamic context: a line such as !`git diff HEAD` in the skill body is executed before the model sees the skill, and its output is substituted in. Keep SKILL.md under 500 lines; move detail into extra files.

---
name: release-notes
description: Drafts release notes for example_app. Use when the user asks for release notes,
  a changelog, or "what changed in this release".
allowed-tools: Bash(git log *), Bash(git diff *), Read
disable-model-invocation: false
---
Changes since the last tag:
!`git log --oneline $(git describe --tags --abbrev=0)..HEAD`

1. Group the changes as Feature / Fix / Maintenance.
2. Describe the user-visible impact in one sentence; do not copy commit wording.
3. See templates/release-notes.md for the format.

In a subagent’s frontmatter the required fields are name and description; there are also fields such as tools, disallowedTools, model (sonnet, opus, haiku, fable, inherit or a full ID), permissionMode, skills, hooks, isolation: worktree, background, maxTurns and mcpServers. Built in: Explore, Plan and general-purpose. Subagents can be nested up to 3 levels deep. “Agent teams”, where several agents talk to each other, are experimental and according to the docs spend roughly 7 times the tokens.

Myth“The more MCP servers I connect, the more capable the agent gets.” Every server means new tool names, new descriptions and a new attack surface. Because Claude Code defers tool definitions by default and loads only their names, the context cost is lower than it used to be, but tool selection gets harder and supply chain risk goes up (level 10). If there is a good CLI, the agent can already use it through Bash, and you can keep the CLI’s reach narrow with permission rules.

Key takeaways

  • First question: should Claude decide this behavior, or the harness? If it has no exceptions, the harness.
  • Short, always-relevant facts go in CLAUDE.md; path-specific facts in rules; procedures in a skill.
  • Noisy work, or work that needs isolation, goes to a subagent; only a summary comes back.
  • If there is a CLI, you may not need MCP. Plugins are for distribution and run with your permissions.

Certainty instead of probability

The most important idea of this level: an instruction in the prompt is probabilistic; a hook is deterministic. If you write “run the formatter before committing” in CLAUDE.md, the model will most likely comply. If you write a hook, it runs every single time. Every rule for which “most likely” is not good enough should move into a hook.

A hook is a handler attached to an event in Claude Code’s lifecycle. As of November 2026 there are 33 events; most training material from 2025 lists only 9 of them. Handler types: command (a shell command), http (a POST to an endpoint), mcp_tool, prompt (a single-turn model decision) and the experimental agent. The last two are model decisions, so they are not deterministic; for a “no-exception rule” use command or http.

The events you will use most

EventWhenCan it block?Typical use
PreToolUseBefore a tool callYesStopping a dangerous command, rewriting the input
PostToolUseAfter a tool finishes successfullyNo (gives feedback)Formatter, lint, logging
PermissionRequestWhen a permission prompt is about to be shownReturns a decision objectAutomating approval or rejecting it
UserPromptSubmitWhen the user sends a messageYesAdding context, stopping a forbidden request
StopWhen Claude is about to finish its answerYes (keeps it going)“Don’t finish until the tests pass”
SessionStartAt session startNoLoading dynamic context
PreCompactBefore compactionYesPreserving critical notes
SubagentStop, TaskCompletedWhen a sub-task finishesYesChecking the quality of the sub-task

Others include PostToolUseFailure, PostToolBatch, Notification, SubagentStart, TaskCreated, InstructionsLoaded, ConfigChange, CwdChanged, FileChanged, WorktreeCreate, WorktreeRemove, PostCompact, PreModelSwitch, Elicitation and SessionEnd. The full list, and which of them can block, is on the official hooks page.

The contract: stdin, exit code, JSON

  1. Input: The hook receives the event information as JSON on stdin. Common fields: session_id, prompt_id, transcript_path, cwd, permission_mode, hook_event_name; PreToolUse adds tool_name, tool_input and tool_use_id.
  2. Exit 0: success. JSON on stdout is applied. Plain-text stdout is added to context only for UserPromptSubmit, UserPromptExpansion, SessionStart and PostModelSwitch.
  3. Exit 2: block. stderr goes to Claude as the reason. Exit 2 overrides even an “allow” in the JSON.
  4. Other codes: non-blocking error. The docs are clear about it: exit 1 is not a block. If your script exits with 1 at an unexpected point because of set -e, the tool call still runs.

For PreToolUse, the JSON output carries permissionDecision (allow, deny, ask, defer), permissionDecisionReason, updatedInput and additionalContext under hookSpecificOutput. Stop and UserPromptSubmit use a top-level {"decision":"block","reason":"…"}; UserPromptSubmit cannot rewrite the user’s prompt. Matcher syntax: * or empty means all; a value containing only letters, digits and _-|, is an exact list of names (Edit|Write); anything else is a JavaScript regex (mcp__memory__.*). The new if field uses permission rule syntax: "if": "Bash(psql *)". One last ordering detail: deny/ask rules and PreToolUse hooks run before the auto mode classifier.

The Stop hook: proof before saying “done”

In level 5 you saw premature completion, the agent saying “done” before the work is finished. The Stop hook is the deterministic cure. It runs when Claude is about to finish its answer; if it returns exit 2, Claude does not stop, it keeps working with the reason from stderr. The official example for a TypeScript project is pnpm tsc --noEmit 1>&2 || exit 2. There is a safety valve against infinite loops: after 8 consecutive blocks without a tool call, the harness lets Claude stop (CLAUDE_CODE_STOP_HOOK_BLOCK_CAP).

{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{ "type": "command", "if": "Bash(psql *)",
                  "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-db-writes.sh" }]
    }],
    "Stop": [{
      "hooks": [{ "type": "command", "command": "dotnet build -warnaserror 1>&2 || exit 2" }]
    }]
  }
}

The Stop hook loop

Two scenarios: the normal flow where the error can be fixed, and the flow where the agent gives up without calling any tools. In the second, watch what happens when the counter reaches 8.

CautionPattern-matching hooks are excellent at catching accidental mistakes, but a command can be written in countless ways. Think of a hook as a seatbelt, not a firewall. Also, hooks run with your permissions: a hook script in a repo can do anything it likes on your machine. In level 10 we will see, through a real CVE, why hooks in the .claude/settings.json of a repo you clone depend on trust approval.

Key takeaways

  • A hook is deterministic; any rule for which “most likely” is not enough goes into a hook. prompt/agent-type hooks are model decisions.
  • Exit 0 is success, exit 2 is a block (stderr goes to Claude), exit 1 is not a block.
  • PreToolUse JSON: permissionDecision allow/deny/ask/defer, rewriting the input with updatedInput.
  • A Stop hook sends Claude back to work with exit 2; it stops after 8 consecutive blocks without a tool call.
  • Hooks and deny/ask rules run before the auto mode classifier.

Context commands

In level 2 you saw that context is a limited resource that gets compacted lossily; in level 9 we will manage it like a budget. Here, let us get to know the knobs Claude Code gives you.

  • /context (and /context all) shows, category by category, what the context is filled with: system prompt, tools, CLAUDE.md, MCP, conversation. The first stop for “why did it forget this rule?”.
  • /compact <focus> summarizes the conversation and continues in a new window; the focus text steers what the summary preserves.
  • /clear wipes the history completely. It is free and resets the cost counter. The command you will use most when switching tasks.
  • /usage replaced the old /cost: it shows the session cost, the cache hit line and how the cost breaks down across skills, subagents, plugins and MCP; with f you can have it apply the suggested fixes.
Myth“The context window is the real constraint; try to squeeze everything into 200K.” The official guide now puts this on its list of “things you can let go of”: with 1M-token windows and automatic compaction, window size is not the bottleneck for most work. But that does not mean context is free: the whole context is resent every turn, and quality drops in long contexts. In the next level we will measure that trade-off.

Checkpoints and rewind

Claude Code takes a checkpoint before every user message; the latest 100 are kept and retained for about 30 days (cleanupPeriodDays). With /rewind or Esc Esc you go back to a point and choose one of: restore code and conversation, conversation only, code only, or “summarize from here”. It is a very reassuring feature, but if you do not know its limits it gives you a dangerous sense of safety. Checkpoints do not track:

  • files changed only through Bash (sed -i, rm, whatever a script writes),
  • most edits made by subagents,
  • edits made outside Claude Code (your editor),
  • symlinked or hard-linked files.

In the docs’ own words: checkpoints are not a replacement for version control. Commit regularly; start any big piece of work from a clean working tree.

What does rewind bring back?

A four-message session. Each message changes files in a different way: the Edit tool, Bash and a subagent. Pick a rewind point and type; see which files come back and which stay changed.

Branching, resuming and parallel sessions

/branch or claude --continue --fork-session branches off the current conversation: ideal for trying two different approaches from the same history. Real parallelism, though, comes with git worktrees. Two agents changing the same files in the same repository creates a mess; a worktree gives each session its own working copy and its own branch.

bash
$ claude --worktree # open a session in a new worktree Worktree created: ../example_app-wt-7f3c (branch: claude/7f3c) $ claude -p --worktree "Write the missing tests for OrderTotal" # non-interactive Note: you clean up worktrees opened with -p --worktree yourself: $ git worktree remove ../example_app-wt-7f3c

If you give a subagent isolation: worktree, it also works in its own worktree. Other parallelism tools: background commands and background subagents, the Monitor tool that watches a long-running process, /loop which reruns a prompt at intervals, and scheduled tasks. An effective pattern is “writer and reviewer”: one session writes the code, a second session with a clean context reviews it. Because the reviewer does not carry the writer’s assumptions, it spots different mistakes.

In practiceA status line script receives the cost, context fill and prompt_cache fields; seeing “context 62%, session $1.40” in your own status line makes it intuitive to know when to /clear. With parallelism, the bottleneck is usually you: if you do not have time to review the five PRs that five agents opened, parallelism just produces a backlog.

Key takeaways

  • /context shows what is loaded, /usage shows what is spending money; /clear is free.
  • A checkpoint is taken before every message, but it does not track Bash changes, most subagent edits or outside edits. It does not replace Git.
  • Worktrees for parallel work; clean up the ones opened with -p --worktree by hand.
  • Separate writer and reviewer sessions; treat your review capacity as the limit on parallelism.
