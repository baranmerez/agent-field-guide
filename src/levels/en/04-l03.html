Your message is a small part of the request

When you type “fix the tests” into Claude Code, those three words are not what reaches the model. At that moment the harness assembles a large HTTP request: tool definitions, its own system instructions, your project rules, the whole conversation so far, the files it has read, command output. Your sentence is a few dozen tokens appended to the very end of that request.

Grasping this is the prerequisite for understanding the rest of prompt engineering. The model does not read “your message”; it looks at the entire token sequence it was given and produces the next token (Level 0). Whatever is in that sequence is the model’s whole world. It does not know anything that is not in the sequence, and something that is in the sequence but buried in the middle of a very long pile often does not get enough attention either.

The API is stateless (we saw this in Level 2): the server keeps no session for you, and the whole history is resent with every request. In the Anthropic Messages API a request is made of three big fields, and this is also their order from the cache’s point of view: first tools, then system, then messages. The order is not arbitrary. The most stable content goes first and the most volatile content goes last, so the cached prefix is not invalidated.

An agent request, layer by layer

  • Tool-use system instruction. When a request contains tools, the API adds its own instruction telling the model how to use them. According to Anthropic’s documentation, on Opus, Sonnet and Haiku 5.5 this takes about 286 tokens before your tool definitions (as of November 2026).
  • Tool definitions. Each tool’s name, description and JSON schema. The description is the only place where the model decides when to use the tool; in other words, it is a prompt too (Level 4).
  • System prompt. The identity and working rules written by the harness, plus environment information: operating system, working directory, git status, date.
  • Project instructions. CLAUDE.md, AGENTS.md and similar files. You or your team write them; the harness adds them to every request (covered in detail in Level 8).
  • Skill descriptions. Only the name and a short description. A skill’s body is loaded only when it becomes relevant.
  • System reminders. Small notes the harness inserts into the middle of the conversation: “this file changed on disk”, “here is the state of the to-do list”.
  • Conversation history. Your earlier messages, the model’s replies and, on current models, thinking blocks.
  • Tool results. Files read, command output, search results. In a long session this is usually by far the largest part of the request.
  • Your latest message. At the very end, the shortest piece.

Three consequences

First: your message is competing. By turn 40 the sentence you typed is less than a thousandth of the request. The model spreads its attention across the entire sequence. A short, vague message easily becomes “noise” next to thousands of lines of tool output. So your message can be short, but it must not be vague.

Second: if you want a lasting effect, invest in the layers that go out with every request. If there is a rule you keep retyping in every session (“don’t delete tests”, “don’t touch the migrations”), its place is not the chat but the project instruction file the harness adds to every request, or an even harder layer (“where rules belong” in Level 6). A rule stated in chat can drop out of the summary during compaction in a long session; a rule in the project file is re-added to every request.

Third: when debugging, look at what the model saw first. The answer to “why did the model do that?” is usually not in the model but in the content of the request. In Claude Code, the /context command shows a breakdown of the context by category. If a rule is not being followed, first check whether that rule is actually in the context.

You already know thisIn C you write a single .c file, but the compiler never sees it as such; it sees a huge translation unit in which the preprocessor has expanded every #include and every macro. An error message can even point at a line that is not in your file. The same holds for the model: your message is your source file, and what the model sees is the “translation unit” the harness has stitched together.

Roles are real, but their boundaries are soft

All of these layers are ultimately flattened into a single text separated by role markers (the chat template we saw in Level 1). Through training, the model has learned to weight the system instruction above the user message, and the user message above text inside tool output. But this is a learned tendency, not an operating-system permission model. A “forget all previous instructions” sentence inside a web page or an issue comment enters the same token stream.

The practical rule is spelled out in Anthropic’s tool documentation too: untrusted content (a web page, an email, a user upload) goes into a tool_result, not into the system prompt. That alone is not protection; the real defense against prompt injection lives in the harness (Level 10).

Go deeperAnthropic’s current prompting guide says newer models are “more responsive” to the system prompt. That sounds like good news, but there is a side effect: forceful wording written to push older, weaker models is now over-applied. A large part of the next topic is about the consequences of this shift.

Key takeaways

  • The model does not see your message; it sees the entire request the harness built: tools, system prompt, project instructions, history, tool results.
  • In a long session the largest part of the request is usually tool results; your latest message is the smallest.
  • Lasting rules belong in the layers added to every request, not in the chat.
  • First step for “why did it behave like that?”: what was actually in the context? (/context)

Tricks left over from weaker models

“You are the best programmer in the world.” “I’ll tip you $200.” “CRITICAL: NEVER forget this.” “Take a deep breath.” Every one of these was genuinely tried at some point, shared, and spread because “it works”. Today most of them either do nothing or backfire. Understanding why they spread is the best way not to fall for the next ones.

How folklore is born

The models of 2022–2023 were far weaker at following instructions than today’s. People saw a particular sentence improve things on a particular model and shared it. The problem: model output is probabilistic (Level 0). Run the same prompt twice and you get two different answers. You got a bad answer with prompt A, added a “tip” and retried, and a good answer came back. Does that show the tip worked, or that the dice simply rolled better the second time? With a single attempt you cannot tell.

Wharton’s Prompting Science Report series measured exactly this, by repeating the same questions many times under every condition. The finding of Report 3 (August 2025) is clear: offering the model a tip or threatening it has, overall, no meaningful effect on benchmark performance. Individual questions swing in both directions, but those swings are noise, not a lever. Report 4 (December 2025) applied the same method to expert personas: roles such as “You are a world-class physicist” did not generally improve accuracy on graduate-level questions; even an expert role matched to the domain made little difference, while low-knowledge roles such as “a small child” often made results worse.

You already know thisA flaky test went red; you added a sleep(500), reran it, and it went green. Is it “fixed”? Maybe the test was already passing one run in three. Prompt folklore is the sum of sleep calls validated by a single run. The cure is the same too: repeat, measure the rate.

Shouting now backfires

The most instructive item on the list is capital letters. In 2023, writing “CRITICAL: You MUST…” really was necessary to make a model use a tool or follow a rule, because the model skipped the rule all the time. Those prompts were written to compensate for that era’s undertriggering problem.

Anthropic’s current guide sums up the situation like this: newer models are much more responsive to the system prompt; prompts written to fix older models’ undertriggering can now cause overtriggering. The cure is to soften aggressive language: instead of “CRITICAL: You MUST use this tool when…”, write “Use this tool when…”. The guide specifically notes that phrasing like “if in doubt, use this tool” also leads to overtriggering.

OpenAI’s GPT-5.5 guide points the same way: avoid unnecessary ALWAYS, NEVER, must and only; save them for truly invariant rules; for situations that require judgment, write decision rules. The GPT-5 guide recounts the Cursor team’s experience: an instruction to “be THOROUGH when gathering information” made the model call search tools needlessly even on small tasks; softening the wording fixed it.

Myth“My prompt works well, so I’ll carry it over to the new model unchanged.” OpenAI’s GPT-5.5 migration guide recommends the opposite: start not from the old pile of prompt text but from the smallest prompt that preserves the product contract. Every line added to patch the old model’s flaws can create a new flaw in the new model.

How do you test your own folklore?

  1. Build a small set from real tasks. 10–20 jobs your team actually hands out: a bug fix, writing a test, a review request.
  2. Run each variant several times. A single output is an anecdote. Run the same prompt at least a few times and look at the success rate.
  3. Write the criterion in advance. Not “looks better”, but: did the tests pass, how many lines is the diff, did it report in the requested format.
  4. Change one thing at a time. If you change the persona, the tone and the context at once, you can’t know which one helped.

This is a small-scale eval. We will cover building evals and automating them in detail in Level 9.

Key takeaways

  • When measured, tips, threats and expert personas make no meaningful contribution to accuracy (Wharton PSR 3 and 4, 2025). A role adjusts tone and scope; it does not add knowledge.
  • Capital letters and “CRITICAL/MUST” overtrigger on newer models. Say it calmly; move a truly invariant rule into a deterministic layer.
  • Folklore is coincidence validated by a single attempt. Compare variants by repeating them, against a criterion written in advance.

A brilliant but brand-new employee

Anthropic’s guide describes the model like this: a very brilliant employee who has just started and knows nothing about your team’s habits. The test it proposes is simple too: if you showed your prompt to a colleague with little context, would they be confused? If they would, the model will be too.

This analogy ties almost every technique that works to a single principle: tell the model what it cannot see. The model cannot guess why the repo is the way it is, where a constraint comes from or how it will know the job is done. Force it to guess, and it guesses based on the “average” project in its training data.

1. Be explicit, name the action

The example in the guide is very instructive: ask “Can you suggest some changes to improve this function?” and you get suggestions. Say “Change this function to improve its performance” and you get edits. The model reads a polite question literally. If you want an agent to do work, spell out the verb: find, fix, change, add, report only.

2. Give the reason behind the rule

Anthropic’s best-known example: writing “NEVER use ellipses” is less effective than writing “Your response will be read aloud by a text-to-speech engine, so never use ellipses, because the engine does not know how to pronounce them.” Why? The reason lets the model generalize the rule. A model that knows the reason also catches the rule’s unstated relatives (other symbols that cannot be read aloud) and recognizes the exceptions where the rule should not apply.

The rule alone, or with its reason?

The same project rule meets four different situations. Toggle at the top between “rule only” and “rule + reason”, and compare what information the model has in each case. The behaviors are representative; the point is to show the mechanism.

3. Show examples, but varied ones

Few-shot examples are, in the guide’s words, one of the most reliable ways to steer format, tone and structure. The recommended number is three to five; the examples should be relevant to the task, different from each other, and separated with <example> / <examples> tags. Give a single example and the model also copies its incidental features: its length, its first word, its field order. Variety lets the model separate “what stays the same” from “what is coincidence”. On models with thinking enabled, examples shape not only the output but the model’s internal reasoning as well.

4. Give it structure: XML tags and order

In a long prompt, instructions, context, input and documents can blur together. The guide recommends wrapping different kinds of content in XML tags: <instructions>, <context>, <input>, a <document> with its source stated. There is no magic in the tag names; what helps is the separation itself. The second rule is about order: put long documents at the top of the prompt and the actual question at the end. Anthropic says this improves performance on all models.

5. Say what you want, not what you don’t want

Instead of “Don’t use Markdown”, write “Your response should be made of flowing prose paragraphs.” That is a positive instruction. A prohibition draws the model’s attention to the forbidden thing but does not say what to put in its place. The guide makes one more subtle observation: the format of your prompt itself influences the format of the output. A prompt full of bullet points invites a bulleted answer.

6. Write down what “done” looks like and how it will be checked

In the agent world, this is the single most effective line. The Claude Code documentation puts it this way: give the model something that returns pass or fail, and it can close the loop itself. Its examples are concrete too: instead of “fix the login bug”, write “users report that login fails after a session timeout; look at the token refresh under src/auth/, write a failing test that reproduces the problem, then fix it”. Without a success criterion the model invents its own, and that is usually “the code compiles and looks reasonable”.

OpenAI’s GPT-5.5 guide calls the same idea an “outcome-first prompt”: write the expected outcome, the success criteria, the allowed side effects, the evidence rules, the output format and explicit stopping conditions.

7. Clean up contradictions

OpenAI’s GPT-5 guide says the model is affected more by contradictory or vague instructions, and spends reasoning tokens trying to reconcile them. Its example is a scheduling system: the prompt says both “never book an appointment without patient consent” and “automatically book an appointment in emergencies”. The equivalent in your project: if CLAUDE.md contains “write tests for every change” right next to “be quick on small fixes”, the model does not know which wins when. Write the decision rule yourself.

    The rise and retirement of “think step by step”

    In 2022, putting “Let’s think step by step” in front of a model’s answer gave a clear improvement on arithmetic and logic questions. Today the same sentence is mostly unnecessary on current models, and some forms of it can even be rejected. What changed in between is not the sentence but the model itself.

    Why did it work?

    The 2022 paper by Kojima and colleagues named this technique zero-shot chain-of-thought: getting the model to write out intermediate steps without giving any examples, just by saying “let’s think step by step”. Its mechanism is hidden in the generation loop from Level 0. The model performs a fixed amount of computation per token. When it writes out intermediate steps it gains two things: more tokens, meaning more computation; and subsequent tokens are now produced while looking at those intermediate results. The written text acts like the model’s working memory.

    Then there is the sentence “take a deep breath and work on this problem step by step”. It is reported to have been found not by a human but by an optimization method that tries prompts automatically (Google DeepMind’s OPRO work, 2023), for a specific model and a specific maths dataset. We could not re-verify this detail against the primary source for this course; but the lesson does not change: a phrase an optimizer found on one model is not a portable “spell” for another model. The essence was the “step by step” part.

    Reasoning models brought thinking inside

    As you saw in Level 1, current models are trained with reinforcement learning to produce thinking tokens before answering. So what was requested from the outside with a prompt in 2022 is now a trained behavior of the model. Anthropic’s current guide says so explicitly: on Fable 5.x, Opus 5 / 5.5 and Sonnet 5.5 you should rely on the thinking feature rather than a hand-written chain of thought; a prompt asking the model to write its reasoning between <thinking> tags can be rejected. Manual CoT is only a fallback for when thinking is turned off.

    You now steer how much thinking happens with settings, not with sentences in the prompt. In Claude this is called effort (Level 1). In OpenAI, for GPT-5.5, it is reasoning_effort: none, low, medium (default), high, xhigh. OpenAI’s guide also notes that higher effort is not always better: it can lead to overthinking and to unnecessary searching.

    So what should you write today?

    This shift has a practical consequence: the long thinking recipes common in old prompt libraries, of the “first analyze the problem, then list the options, then evaluate each one, then decide” kind, are largely unnecessary on a model with thinking enabled; in that situation Anthropic’s guide treats manual CoT only as a fallback. There is also the risk of tying the reasoning the model learned in training to a fixed sequence you wrote. Removing these recipes and measuring the result on a small task set is one of the first clean-ups to do when moving from one model to the next.

    Instead of telling the model how to think, tell it what it needs to achieve and how the result will be evaluated. On a hard problem, give the evaluation criteria; give example solutions (examples shape internal reasoning too); raise the effort for genuinely hard work. If you want a short justification inside the answer, ask for it as part of the output format: “At the end, justify your choice in two sentences.”

    CautionA thinking summary is not a faithful record of the model’s actual computation (Level 1). An agent that thinks “I checked the tests” may not have run the tests. Tie verification not to the model’s narrative but to the result of a command the harness actually ran (Level 5).

    The end of prefill

    Prefill used to be a trick people working with Claude used a lot: you put a partial assistant message at the end of the messages array, and the model continues its answer from there. If the last message is "{", the model has to start writing JSON; if it is "Root cause:", it gets straight to the point. It was a cheap, effective technique used everywhere.

    According to Anthropic’s guide, starting with the Claude 4.6 models, prefilling the last assistant turn returns an HTTP 400 error. So if your old code uses prefill, the request is rejected outright once you switch to a new model. The guide suggests three migration paths:

    • For JSON and a fixed schema: structured outputs or a tool with a schema (strict: true). Instead of “forcing” the format with text, you guarantee it at the API level (Level 4).
    • To cut the preamble: say it explicitly in the system instruction: “Respond directly without a preamble.”
    • For a reminder in a long conversation: put the reminder inside the next user turn.

    Key takeaways

    • “Think step by step” worked because the written intermediate steps gave the model extra computation and working memory. Reasoning models now do this by themselves.
    • On current Claude models, rely on the thinking feature and the effort setting instead of manual CoT; asking for thinking with a <thinking> tag can be rejected.
    • From Claude 4.6 onwards, prefill returns 400. For JSON use structured outputs or a strict tool; for the preamble, a system instruction; for reminders, the user turn.

    A prompt is a ticket

    You have known for years what a good bug report looks like: which environment, which steps, what was expected, what happened, what the log says. A task given to an agent is exactly that kind of report. The difference: the colleague reading this report starts working without asking questions and fills in the missing information with their own guesses.

    You already know thisScrum’s “definition of done”, the “steps to reproduce” in a good bug report and the code-review question “what does this PR not change?”. A good task definition for an agent is the sum of those three. It is not a new skill; it is doing what you already do inside a team, in writing and completely.

    The parts of a coding task

    Context

    Which system, which screen or endpoint, since when, the evidence you have (log, error, measurement). Things the model cannot work out from the repo.

    Task

    An explicit verb and scope: find the root cause and fix it; report only; write a test first.

    Constraint and reason

    What must not be touched, and why. The reason lets the model recognize exceptions correctly.

    Done and verification

    Which command must pass, what is delivered at the end (root cause, changed files), and in what format.

    Stop condition

    When it should stop and ask instead of carrying on alone: a schema change, a public API, a deletion.

    Isn’t a long prompt expensive?

    The final version takes several times more tokens than the first. But that arithmetic is misleading. You saw in the first topic that by turn 40 the request is hundreds of thousands of tokens; the few hundred tokens you add to the task definition are a rounding error there. The real cost is in the extra turns a vague task causes: reading the wrong files, undoing unwanted refactors, correcting “no, that’s not what I meant” three times. Every extra turn means resending the entire history (Level 2).

    Claude Code’s best-practices page has concrete advice on this: watch the first minute, and press Esc the moment the agent goes off track; after two failed corrections, run /clear and write a better prompt. Trying to fix a polluted context is usually more expensive than starting over with a clean one (failure modes in Level 5).

    When is a short prompt enough?

    This lesson is not saying “every prompt should be a page long”. If the context is already in the context window, a short message works perfectly. In a session where you have just investigated a bug together, “now fix it and run the test” is enough, because the context, the evidence and the goal were already discussed in earlier turns. The criterion is not length but missing information: when the model reads this message, which question will it have to answer by guessing?

    Conversely, the first message of a new session, or the first message after /clear, is like the first ticket handed to a colleague who has just walked in. There, a short message means the model fills every gap with “average project” assumptions. There is one more distinction: if you rewrite the same context in every session (the build command, the test command, the decimal rule for money), that information belongs not in the task definition but in the project instruction file. The task definition should carry only what is specific to this job.

    In practiceOn a large or ambiguous job, ask the model for the diagnosis and the plan before the code: “Before making any changes, write the root cause and your plan in two paragraphs.” Catching a wrong diagnosis before any code is written is much cheaper than reverting a wrong diff. Claude Code’s plan mode is this habit built into the harness (Level 8).

    Four common mistakes

    • Dictating the solution. Say “add a null check on line X” and the model does no diagnosis; if your diagnosis is wrong, the fix is wrong too. Give the problem and the evidence; if you want the solution, have it explained first.
    • Leaving the scope open. If you don’t forbid “while I’m here” clean-ups, the agent may, with the best intentions, touch places it should not. Write down the scope and its reason.
    • Not allowing an empty result. If a review request doesn’t say “if there are no findings, say so”, the model is more inclined to produce weak findings just to find something.
    • Leaving verification to the model. “Make sure” is not verification. Give it a command to run, a test that must pass, an output to compare against.

    Key takeaways

    • A good task definition = context + explicit task + constraint with reason + done/verification + stop condition.
    • Shouting, personas and tips carry no information; removing them costs nothing.
    • A few hundred extra tokens of clarity are always cheaper than a few extra turns.
    • Stop an agent that goes off track early; after two failed corrections, a clean context and a better prompt.

    From “How do I say it?” to “What do I put in the window?”

    In a single question and answer, the wording of the prompt matters. In a forty-turn agent session, the wording is a small part of the request. The real question changes: on each turn, which tokens get put in front of the model, and which stay out?

    In September 2025 Anthropic gave this question a name: context engineering. Its definition: the natural progression of prompt engineering; strategies for curating all the tokens the model sees at inference time (system prompt, tools, MCP, external data, message history). And this curation is redone on every turn. The same article defines an agent in one plain sentence too: LLMs autonomously using tools in a loop.

    Why isn’t “more context” better?

    The window has grown: as of November 2026, all current Claude models offer a 1M-token context (Level 2). But fitting in the window does not mean the model will use all of it with equal attention. Anthropic describes context as a finite attention budget: every token eats a piece of that budget.

    On the evidence side there is Chroma’s context rot report from July 2025. Across 18 models, including Claude, GPT-4.1, Gemini 2.5 and Qwen3, it showed that even on simple tasks, performance becomes increasingly unreliable as input grows. In one of its most striking experiments (LongMemEval) the same question was asked once with a focused input of about 300 tokens containing only the relevant part, and once with the full input of about 113 thousand tokens; the focused input did better on every model. Thinking narrowed the gap but did not close it.

    The right altitude for a system prompt

    Anthropic’s context engineering article describes a “Goldilocks zone” for the system prompt between two extremes. At one end are brittle instructions written like if/else: they try to hard-code every situation and break on the first unforeseen one. At the other end are vague, high-level exhortations: they give the model no concrete signal, and the model assumes a shared context. The target is the smallest set of information that fully describes the expected behavior: the right altitude.

    Preload, or fetch when needed?

    There are two ways to introduce an agent to a repo. The first is preloading: putting everything that might be relevant into the context up front. The second is just-in-time retrieval: keeping only lightweight references (file paths, queries, URLs) in the context and fetching the data with tools when it is needed. Claude Code does the second: instead of indexing the codebase in advance, it searches on demand with tools such as grep, glob and reading the head of a file. Anthropic’s Agent SDK article also recommends starting with agentic search, and finds semantic search less accurate, harder to maintain and less transparent. In practice the best option is often a hybrid: a small map up front, details on demand.

    The toolbox for long sessions

    The other techniques of context engineering will come up one by one in later levels; let’s draw their map here:

    • Compaction. A context that is nearly full is summarized, and work continues from the summary in a new window. The Claude Code documentation states the price openly: detailed instructions from the start of the conversation can be lost. That is why lasting rules are written into CLAUDE.md (Levels 2 and 8).
    • Clearing tool results. Dropping old tool output that is no longer needed from the context; the lightest form of compaction.
    • Structured notes. Notes the agent writes outside the context (a NOTES.md, a to-do list, a progress file) and reads back later (Level 5, long tasks).
    • Subagents. Helper agents that do exploration in a clean context and return a summary of usually 1,000–2,000 tokens to the main agent (Level 8).
    • Progressive disclosure. For skills, only the name and description are loaded up front; the body when it becomes relevant, linked files only when needed.
    • Tools are context too. Every tool definition takes up space in every request. A small number of non-overlapping tools; tool search for large numbers of MCP tools (Level 4).
    In practiceThe Claude Code documentation says this about CLAUDE.md: every line takes a small share of the model’s attention on every task. Keep the file short; move long procedures (cutting a release, data-fix steps) into skills. If you find yourself emphasizing a line a little more every week, that line probably belongs in a hook (Level 6).
    You already know thisContext engineering resembles designing a cache and memory hierarchy. You cannot put everything into the L1 cache (the context); you keep hot data there and pull the rest from main memory or disk (the file system, tools) when needed. A bad layout slows down every access, like a cache full of the wrong data.

    Key takeaways

    • Context engineering is the job of choosing all the tokens to put in front of the model on each turn; the wording of the prompt is only one part of it.
    • More context is not better: performance degrades as input grows (context rot). Focused input did better on every model.
    • A system prompt should sit at the right altitude: neither a pile of if/else nor empty exhortation.
    • Instead of preloading, keep lightweight references and fetch details on demand; a hybrid is often best.
