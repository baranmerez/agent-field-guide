Everything outside the model

Remember the equation from the Getting started page: Agent = Model + Harness. From level 3 through level 5 we built the pieces of that equation one by one: we wrote the prompt, defined tools, and put the tools in a loop. In this level we step back and look at the whole picture. What surrounds that loop, why is it there, and how much of an agent’s success does it decide?

The clearest definition of the term as it is used today is Vivek Trivedy’s post at LangChain, “The Anatomy of an Agent Harness”, dated 10 March 2026. The definition is deliberately broad: the harness is every piece of code, every configuration and every bit of execution logic that is not the model itself. The line that sticks is this one: “If you’re not the model, you’re the harness.” In other words, everything that touches the agent apart from the model’s weights sits on this side.

Trivedy groups the components into five buckets:

  • System prompts. The text that tells the model who it is, what environment it runs in, and how to use its tools.
  • Tools, skills, MCP servers and their descriptions. The model’s hands reaching into the world, and the way those hands are described.
  • Bundled infrastructure. File system, sandbox, browser: the place where commands actually run.
  • Orchestration. Subagents, handoffs from one agent to another, model selection by task type.
  • Hooks and middleware. Code that steps in at specific points of the loop, such as compaction, “keep going” logic and lint checks.

The vendors speak the same language

This is not just a framework company’s marketing frame. Anthropic’s Claude Code documentation describes Claude Code with exactly this word: the layer around the model that provides the tools and manages the context, in other words an agentic harness. There is a more concrete signal too: in 2025 the Claude Code SDK was renamed the Claude Agent SDK. The reason was simple: the same harness was running agents that do not write code. File system, bash, search, permissions and context management are not “coding” features; they are the infrastructure any general-purpose agent needs.

LangChain founder Harrison Chase made the same point in his “Deep Agents” post: what makes Claude Code so capable is not only the model, but a general harness made of a planning tool, a file system, subagents and a very detailed system prompt. Put those four pieces around a different model and you also get an agent that works “deep”.

You already know thisThink of the relationship between an operating system and a program. When a program wants to write to a file, it does not do it itself; it makes a system call, the kernel checks permissions, carries out the operation and returns the result. The program does not know how the disk works; it only sees the result of the call. Here the model is the program, the tool call is the system call, and the harness is the kernel plus the runtime. Another analogy: the model is the business logic, the harness is the framework, the DI container, the middleware chain and all the infrastructure. However good the business logic is, it runs badly in a misconfigured framework.

Three things in the diagram deserve your attention. First, everything the model produces is a request: “I want to run this command”, “I want to change this file like so”. Every step that turns that request into reality, rejects it, truncates it, formats it and feeds it back belongs to the harness. Second, the things you write (your message and CLAUDE.md) reach the model not where and how you want, but where and how the harness chooses. Third, some pieces, like the compaction summary, are mixed: a model writes the text, but the harness decides when it is written, what is kept and where it goes.

What does this distinction change in practice?

  1. Debugging. When the agent does something bad, the first question should be: “Did the model make the wrong decision, or did the harness fail to give it the information, tool or feedback it needed to make the right one?” The second is surprisingly common. If it ignored an important file, look at the context; if it ran the wrong command, look at the tool description and the permissions; if it keeps repeating the same mistake, look at the feedback the environment gives it.
  2. Selection decisions. “Which model is best?” is an incomplete question. As you will see in lesson 3 of this level, the same model gives very different results in different harnesses. The right question is: “Which model and harness pair is best for my work?”
  3. Security. You cannot guarantee what the model will produce. You can, however, control exactly what the harness will execute. Because the harness is the only place where a guarantee is possible, security is built there too (level 10).
Myth“The harness is just an interface; the real work happens in the model.” The interface is the outermost and most visible layer of the harness, but not the most influential one. The Claude Code documentation says that the terminal, IDE, desktop, web and CI surfaces all run the same loop. The surface changes; the tool set, permissions, context management and hooks stay the same. Those inner layers are what shape the behavior.
CautionThe most expensive reflex is this: when the agent breaks a rule, add one more sentence to the prompt, then one more “IMPORTANT”. If the rule is the kind the harness can enforce (do not read a file, do not run a command, make the tests pass before finishing), the prompt is the wrong layer. Lesson 5 of this level is about exactly that decision.

Key takeaways

  • The harness is everything that touches the agent apart from the model’s weights: prompts, tools, infrastructure, orchestration, hooks.
  • The model only produces requests. The harness turns a request into reality, rejects it, and feeds the result back.
  • The Claude Code SDK becoming the Claude Agent SDK shows that a good coding harness is really a general-purpose agent infrastructure.
  • When an agent fails, ask first: was the decision wrong, or was the information, tool or feedback needed for the decision missing?

The nine layers of a coding harness

The while loop in level 5 was the skeleton of the harness. A real coding harness wraps that skeleton in layers, each of which closes off a specific way agents fail in the real world. We use Claude Code as the reference because its documentation describes these layers explicitly; Codex CLI and the others have their equivalents (level 7).

The list below is based on the Claude Code documentation as of November 2026. Names and details may change from release to release; the concepts last.

1. System prompt and system reminders

The instructions the harness puts at the start of every request: identity, working rules, environment information (operating system, working directory, git status). On top of that there are system reminders inserted into the conversation: the contents of CLAUDE.md, the selected output style, “this file changed after you read it” notes, the attribution lines to add to commits. The harness writes and places all of them; you control part of the content, not where it goes.

2. Tools, MCP and skills

The built-in tools cover groups such as file operations, search, command execution, web and code intelligence. Tools from the MCP servers you connect are loaded deferred by default: thanks to tool search, only the tool names and server instructions sit in the context, and the full definition arrives when it is needed (level 4). Skills work the same way: first just the name and description, the content when needed.

3. Permissions and sandbox

Which tool runs without asking, which needs approval, which never runs at all. Claude Code has several permission modes: Auto, where a classifier decides; Manual, which asks about everything; Accept edits, which accepts edits on its own; and Plan, which produces a plan without changing anything. Above these sit allow and deny rules, and at the very bottom the sandbox, which limits commands’ file system and network access at the operating system level.

4. Checkpoints and the session log

The harness snapshots the files it edits; you can rewind with Esc Esc. The whole session is stored as a JSONL file; resume and fork are built on top of it. The checkpoint is the layer that gives the agent freedom to make mistakes: you supervise something you can undo more loosely.

5. Context management

Automatic compaction as the window nears full, the breakdown you see with /context, and the cap placed on tool output. In Claude Code a tool result can be at most 25,000 tokens; anything beyond is truncated. We saw the mechanism of this layer in level 2; what matters here is that all of these are harness decisions, not model decisions.

6. Memory

CLAUDE.md (project instructions shared with the team), CLAUDE.local.md (personal, never committed to the repo) and MEMORY.md, the automatic memory file Claude maintains itself. According to the documentation, the first 200 lines or the first 25 KB of automatic memory are loaded at session start. Memory is the harness’s answer to the model’s statelessness: the model starts every session from scratch, the files do not.

7. Hooks

Points where your code runs at specific events of the loop (before a tool call, after it, at session start, when the model says “done”). Tell two kinds apart: command and http hooks are deterministic, meaning a script or an HTTP endpoint decides. In prompt and agent hooks, a model makes the decision again. That difference is decisive when you choose where to put a rule (lesson 5). The syntax is in level 8.

8. Subagents

Helper agents that run in a separate context window and return only a summary when they finish. They can start with a clean window or with a copy of the current conversation (fork). Their real value is context isolation more than parallelism: the dozens of files read during exploration never enter the main window.

9. Interfaces

Terminal, IDE extension, desktop app, web, Slack, CI. The documentation stresses that they all run the same loop. Changing the interface should not change the behavior; if it does, a different permission mode or a different settings file is usually in play.

The line between deterministic and model-decided

The onion’s “Who decides?” view shows the most important idea of this level. Some layers are deterministic: a deny rule, the sandbox, a command hook, the tool output cap. They give the same response to the same input every time; they can be tested and audited. Others ultimately come down to the model’s interpretation: CLAUDE.md, skill descriptions, prompt hooks, the classifier in Auto mode. The Claude Code documentation says so plainly: CLAUDE.md is guidance, and Claude may decide that a line does not apply in a given situation. Hooks, deny rules and managed settings, on the other hand, are enforced by the harness.

You already know thisIt is the difference between a “let’s do it this way” comment in code review and a required check in CI. The comment is guidance; a developer may ignore it for a good reason. A branch protection rule asks nobody. CLAUDE.md is like the review comment; hooks and deny rules are like branch protection.
In practiceWhen you wonder what an agent is working with, do not guess; ask the harness. In Claude Code, /context shows the context breakdown, /permissions the active rules, /hooks the registered hooks. Codex CLI has similar status commands. It is the fastest way to find where a behavior comes from.

Key takeaways

  • The nine layers of a coding harness: instructions, tools, permissions and sandbox, checkpoints, context management, memory, hooks, subagents, interfaces.
  • Each layer closes off a specific failure path. If a layer is missing, that failure will happen sooner or later.
  • Some layers are deterministic (enforced), others are model-decided (guidance). Critical rules belong on the deterministic side.

Same model, different harness, different result

The claim that “the harness matters” feels intuitively right, but how much does it matter? We have a few measurements on this. None of them is flawless, so we will read each one together with its source, its method and its weak spot.

Evidence 1: pin the model, change only the harness

LangChain pinned the model to gpt-5.2-codex in its own open-source coding agent, deepagents-cli, and changed only the prompt, the tools and the middleware. The Terminal-Bench 2.0 score went from 52.8% to 66.5%. Two changes stand out. The first is adding an explicit plan, build, verify, fix structure to the loop: the agent has to pass through a verification step before it may say it is done. The second is what the post calls the “reasoning sandwich”: high reasoning effort for the planning and verification steps, medium for the implementation steps. The result is a vendor measuring its own product, in other words vendor-reported. Still, the direction is clear: same weights, a gap of roughly 14 points.

Evidence 2: change only the edit tool

Can Bölük’s post of 12 February 2026 measures an even narrower variable: the file edit format. 16 models, 180 tasks. A “hashline” format, in which lines are tagged with short content hashes, beat apply_patch in 14 of the 16 models by roughly 15 points on average. The most extreme case is Grok Code Fast 1: from 6.7% to 68.3%. This is a single-author company blog vendor blog, single author; we have not seen an independent replication. But the mechanism is plausible and we will examine it in the next lesson: the format changes the surface on which the model can make mistakes.

Evidence 3: interface design as an academic result

The SWE-agent paper (Yang et al., NeurIPS 2024) named the interface between the agent and the computer the “ACI”. A file viewer with a 100-line window, an edit command with a linter that rejects syntactically broken edits, and short search output. GPT-4 Turbo went from 11.0% on SWE-bench Lite with a plain shell to 18.0% with this interface; with the edit action removed it dropped to 10.3%. The figures come from secondary summaries; the paper’s table is authoritative secondary source.

Why does a small change make such a big difference?

At first glance it is surprising: how can an edit format or a verification step be worth dozens of points? The answer is that agent tasks are long chains of steps. Anthropic’s “Building effective agents” post says it plainly: in agents, errors compound. Think of a simple calculation (an illustrative one, not a measurement): an agent that gets each step right with 98% probability finishes a 50-step task without a single mistake about 36% of the time (0.9850). Raise per-step success to 99% and that rate climbs to about 60%. A one-point improvement per step makes a difference of more than twenty points at the task level.

The harness acts on exactly that per-step probability. A vague error message wastes a step; a patch that does not apply wastes a turn on re-reading; the absence of a verifier lets a small mistake ride along for twenty steps. The reverse holds too: even if a good harness cannot prevent an error entirely, it catches it early and cheaply. A test turning red right away, a linter rejecting a broken edit, a hook stopping a write to the wrong file and saying why: each of these lets the next link in the chain start from solid ground. The linted edit command in SWE-agent and the verification step at LangChain are two implementations of the same idea.

That is why, when you evaluate a harness, these questions matter as much as “how smart is the model”: how many steps later does it see the error, how clearly does it see it when it does, and how many turns does the fix cost?

How should you read these numbers?

There are compilations going around that show the same model scoring very differently with different harnesses on the Terminal-Bench leaderboards. One secondary compilation from around April 2026 says that with Claude Opus 4.6 the best harness scored about 82% and Claude Code about 58%, a 24-point spread on a single model. We could not verify this; it sits in a separate tab of the diagram, with a warning. LangChain’s post also notes separately that Opus 4.6 trailed the other harnesses by a wide margin inside Claude Code.

When you read a gap like that, do not forget one important distinction: leaderboard harnesses are tuned for the benchmark. They run non-interactively, choose timeouts to fit the tasks and allow everything. Product harnesses optimize for other things: asking the user, permissions, sandbox, cost, reversibility. Claude Code trailing on a benchmark does not mean it will be worse in your repo; it may mean it spends its budget on things the benchmark does not measure. The reverse is also true: the permission model of a harness that shines on a benchmark may be unacceptable for your company.

Myth“Model X is so many points better than model Y.” Model comparisons often quietly include a harness. The reported score is the score that model got with that harness and those settings. You cannot carry the number on a model card over to your own toolchain; when you do, expect a deviation as large as the harness gap.

When debugging: model or harness?

In day-to-day work, this evidence translates into a debugging habit. When the agent does something you did not expect, instead of blaming the model right away, look in this order: what was in the context, what did the tool return, which rule was in effect, what feedback did the environment give?   • Even a tool decision that looks small, such as the edit format, can make a big difference.

Model and harness evolve together

Part of the explanation for the gaps in the previous lesson is simple: models are not trained in a vacuum. Labs train their models during the RL phase with specific tool names, specific edit formats and specific working environments. A model performs best in an environment that resembles the harness it was trained in.

In the vendors’ own words

OpenAI’s Codex prompting guide is unusually explicit about this. It “strongly” recommends using their own apply_patch implementation exactly as is, saying the model has been trained to excel at this diff format. It also states that the model was trained predominantly with a dedicated terminal tool, and trained to follow AGENTS.md instructions closely. Those three sentences are really a configuration manual for anyone putting a Codex model into their own harness.

On the Anthropic side the same idea shows up as “Anthropic-schema client tools”. The schemas of the bash, text_editor, memory, computer and browser tools are trained into the model; the documentation says Claude has been optimized on thousands of successful trajectories that use these exact tool signatures. The practical consequence: these tools get called more reliably than tools that do the same job but are defined with names and schemas you made up.

You already know thisIt is the difference between a library’s “official” client and a wrapper you wrote yourself. The official client knows every edge case the server expects; your wrapper works most of the time and quietly misbehaves in a rare case. Here the “server” is the model’s habits: speak the format it was trained on and you get fewer surprises.

Why does the diff format matter so much?

Editing a file is one of the most delicate outputs a model has to produce. The model does not rewrite the whole file; it produces a description of the change for the harness to apply. That description comes in three main forms, and each has a different weak spot:

  • Find and replace (str_replace in Claude’s text_editor tool, the Edit tool in Claude Code): the model writes the old text verbatim, the harness searches for it in the file and replaces it with the new text. The old text must occur exactly once. One whitespace difference gives a “not found” error, two matches an “ambiguous” one.
  • Contextual patch (Codex’s apply_patch): the model writes the lines to change plus the surrounding context lines in a patch format. The harness places the hunk using the context lines. Any drift in the context lines makes the patch impossible to apply.
  • Line-referenced (like hashline): when the file is read, each line is tagged with a short content hash; the model describes the edit as “this line, this hash”. It does not have to rewrite the old text. If the hash does not match (the file has changed), the harness rejects the edit.

In each format, the thing the model can get wrong is different. With find and replace it has to remember the old text letter for letter; with a patch, copy the context correctly; with line references, pick the right line. Whatever format a model was trained on, it has learned to avoid that format’s mistakes. Give it a different format and it would have to learn that format’s mistakes all over again, and it cannot, because its weights are frozen.

Fitting too closely is a risk too

LangChain’s harness anatomy post puts forward an interesting argument: products like Claude Code and Codex go through post-training with the model and the harness in the loop, and this can turn into a kind of overfitting. Change the tool logic and performance may drop; so the best harness for a task is not necessarily the one the model was trained in. This is an argument, not a result measured in that post. But the hashline result is consistent with it: some models did better in a format other than their “native” one.

Taken together, the two observations say this: the training format is a strong default, not dogma. If you are building your own harness, start with the tool names and formats the model was trained on. If you want to try a different format, do it by measuring on your own tasks (evals in level 9).

Practical consequences

  1. Changing the model means changing the harness too. When you switch models inside the same tool, part of the behavioral difference may come from the new model not being used to that tool’s formats. The reverse also holds: if you use a Codex model in a non-Codex tool that gives it some other edit format instead of apply_patch, you may not see the quality you expect.
  2. The name of the instruction file is part of the format. Codex was trained to follow AGENTS.md; Claude Code loads CLAUDE.md. If you use both tools in the same repo, keep the two files consistent or point one at the other (levels 7 and 8).
  3. Tool names are not trivial. In your own harness, choosing names close to the ones the model saw in training, rather than giving a tool an arbitrary name, can buy consistency. There are third-party experiences that support this, but we have not seen verified numbers; try it with your own eval.
  4. Retire the question “Which model is best?” Replace it with “Which model and harness pair is best, on my tasks, by my criteria?”
In practiceIf the agent keeps hitting “no match found” or “patch failed to apply”, before blaming the model’s intelligence, check these: does the file mix tabs and spaces, are line endings mixed between CRLF and LF, did a formatter change the file after the agent read it? All of these are friction at the format level, and most are solved with a harness or repo setting.

Key takeaways

  • Models are trained with specific tool names and formats: apply_patch and the terminal tool for Codex; bash, text_editor and the other trained-in schemas for Claude.
  • Each edit format has its own error surface: exact matching, copying context, or picking the right line.
  • The training format is a strong default; other formats may be better, but know that by measuring on your own tasks.

Where does a rule go?

Your team has settled on a rule: “applied files in the migrations folder are never touched.” How do you teach that to the agent? Most people’s first answer is “I’ll put it in CLAUDE.md.” Sometimes that is the right answer. Most of the time it is not. This lesson teaches you how to decide which harness layer a rule belongs in.

The basic distinction: guidance or enforcement?

The distinction you saw in the earlier lessons becomes a decision criterion here. Line up the harness layers like a ladder, from soft to hard:

  1. CLAUDE.md / AGENTS.md. Guidance that sits in the context on every request. The model reads it and usually follows it, but it may decide that a line does not apply in a given situation. Every line costs a little attention on every task.
  2. Skill. A procedure loaded on demand. The right place for long, rarely needed knowledge: only its name and description sit permanently in the context.
  3. Tool design. Bake the rule into the tool itself. A read-only database tool carries a no-writes rule better than any prompt, because the ability to write simply does not exist (level 4).
  4. Permission rule. allow, ask, deny. The harness stops a tool call based on a pattern. Simple, fast, deterministic; but patterns can be sidestepped.
  5. Hook. Your code, running on an event. PreToolUse can block a call and tell the model why; PostToolUse can run something after every edit; a Stop hook can run a check when the model says “done” and send it back to work (level 5). A command hook is deterministic.
  6. Sandbox. A file and network boundary at the operating system level. It stops even a command that sidesteps the harness’s patterns.
  7. Outside the harness: git hooks, CI. The last gate, applying to everyone, agent or human. Its feedback comes late, but nobody can skip it.

The Claude Code documentation’s advice on this fits in one sentence: if you keep adding emphasis to a CLAUDE.md line and Claude still misses it, that line belongs in a hook. The documentation adds that “adding IMPORTANT probably won’t fix it”. As you saw in level 3, with newer models capitalised, shouting instructions also cause overtriggering: the rule starts being applied in unrelated situations too.

You already know thisIt is the question of where you put a business rule in a database. An if in the application code is usually enough, but another client can bypass it. A CHECK constraint or a foreign key asks nobody. Critical integrity rules go into constraints, flexible business rules into code. Here CLAUDE.md is like the if in application code; hooks and the sandbox are like constraints.

Four questions for the decision

  1. Does it have exceptions? If the rule has legitimate exceptions and telling them apart takes judgment, write it in the soft layer (CLAUDE.md), together with the reasoning. A deterministic check cuts off the exceptions too.
  2. What does a violation cost? If a violation means irreversible damage, a security hole or data loss, the rule must be enforced: a deny rule, a hook or the sandbox. “Usually complies” is not enough.
  3. Is the rule an action or a judgment? “Run the formatter after every edit” is an action; a hook does it every time. “Keep the code readable” is a judgment; no deterministic check can decide it.
  4. How often is it needed? A short rule needed on every task goes in CLAUDE.md; a long procedure needed once a month goes in a skill.

The hard layer has a cost too

Putting every rule in the hardest layer is not the right answer either. A deterministic check does not recognize exceptions: it blocks legitimate work too. And a blocked agent does not stop; it looks for another way. If the hook in the simulation only watches the Edit and Write tools, on the next attempt the model may try to make the same change through bash with sed -i. That is not malice; the model is trying to finish the task and sees the obstacle in front of it as a technical problem. So a good block does two things: it keeps its scope wide enough to cover the real risk (with the sandbox if necessary), and its block message states the legitimate alternative explicitly. An agent that has an alternative does not look for shortcuts.

Harnesses know about this tension and build in safety valves. According to the Claude Code documentation (as of November 2026), auto mode stops deciding and falls back to asking the user after 3 consecutive or 20 total blocks; and when a Stop hook blocks 8 times in a row, the harness overrides it (level 5). The message is clear: if a hard layer says “no” forever, the agent either locks up or tries to get around it. A hard layer should be firm, but it should not drive the loop into a dead end.

As a practical rule of thumb: guidance layers (CLAUDE.md, skills) make sure the agent picks the right path; enforcing layers (permissions, hooks, sandbox) make sure the wrong path is closed. In a good setup the two work together: most of the time the agent never hits the block, because the guidance has already put it on the right path; and when it does hit it, the block tells it where to go.

CautionDeterministic layers can be breached too. Even if a deny pattern stops the Read tool, the same file can be cat-ed through bash; a command pattern can be sidestepped with a different spelling. Do not rely on a single layer for a critical rule: use a deny rule together with the sandbox, and if possible take the secret itself out of the agent’s environment. Level 10 expands on this defense-in-depth idea.
In practiceWhen you move a rule into an enforcing layer, do not delete it from CLAUDE.md; leave it as a short explanation. For example: “The migrations folder is protected by a hook; create a new migration for schema changes.” That way the model picks the right path without ever hitting the block, and you save a turn and the tokens.

Key takeaways

  • CLAUDE.md is guidance; the model may decide a line does not apply. Hooks, deny rules, managed settings and the sandbox are enforced.
  • If you keep adding emphasis, the rule is in the wrong layer: move it to a hook or a permission rule.
  • The decision questions: are there exceptions, what does a violation cost, is it an action or a judgment, how often is it needed?
  • A good block also states the reason and the right path. Use more than one layer for critical rules.

Building your own harness

One day the out-of-the-box behavior of Claude Code or Codex will not be enough: a support agent that talks to an internal system, a maintenance agent that runs overnight, a review step that runs in CI. Then you will build part of the harness yourself. This lesson shows what you must not skip when you write one from scratch.

First, don’t write it from scratch

The first piece of advice may come as a surprise: if you can, do not write the harness from scratch. The Claude Agent SDK is the programmable form of the harness that runs Claude Code; tools, permissions, hooks, context management and subagents come ready-made. The OpenAI Agents SDK also provides its own loop, handoffs and max_turns guard. Writing your own loop is an instructive exercise; but in production, rewriting every layer means rediscovering every failure path each layer closes off.

Anthropic’s Agent SDK post describes an agent’s work as a four-step loop: gather context, take action, verify the work, repeat. It lists three options for verification: rules (lint, tests), visual feedback (screenshots) and LLM-as-judge. About the last one the post is frank: it is generally not a very robust method. In other words, use a deterministic verifier wherever you can.

To take that skeleton to production you add pieces, each of which closes off a failure path. In the diagram below, switch the pieces on one by one and watch the loop grow. Common mistakes

  • No stop condition. A loop that starts with while True carries the bill into infinity too when the model gets stuck. max_turns and a token or cost budget are the first two things to add.
  • Error messages not written for the model. A tool result that just says “failed” makes the model repeat the same call. Error text that says what happened and how to fix it shortens the loop (level 4).
  • No verifier. It is done when the model says it is done. If verification is not inside the loop, “done” means “looks done” (level 5).
  • Permission checks living inside the model. The sentence “do not run dangerous commands” sits in the system prompt, but the executor has no check at all. However good the model is, that is not a security boundary.
  • Observability as an afterthought. Debugging a harness that does not record each turn’s request, response and tool results is like debugging a distributed system without logs. It is one reason Claude Code stores sessions as JSONL.
  • No context limit. Letting a tool return 200 KB of logs exhausts both quality and budget within a few turns. Truncate the output, and when you do, tell the model how to narrow it down.
You already know thisThis list looks a lot like the checklist for an API gateway that handles requests from an untrusted client to a backend service: timeouts, rate and budget limits, authorization, input validation, response size limits, an audit log. The difference is that the “client” here is your own agent. Its untrustworthiness comes not from malice but from being probabilistic.

Test the harness too

The best thing about the harness is that it is ordinary software. You cannot unit-test the model, but you can unit-test the harness. Test the permission matcher with a list of commands: is git push --force rejected, does git status pass? Run the hook scripts with fixed JSON inputs and check their exit codes. Verify that the truncation function gives the model a hint to narrow down when it truncates. Keep the JSONL logs of real sessions; when you change the harness, replay the same tool calls and see what the new rules block. Measuring the model’s behavior is a job for evals (level 9); measuring the harness’s behavior is the testing you already know.

When to build your own, when to use an off-the-shelf one?

SituationReasonable choiceWhy
Coding work on the developer’s own machineClaude Code, Codex CLIAll the layers are ready; shaped by settings files, CLAUDE.md / AGENTS.md and hooks.
A recurring agent step in CIThe ready-made CLI’s non-interactive mode, or the Agent SDKSame loop; permissions and output format are controlled from a script (level 9).
A domain agent that talks to an internal systemAgent SDK + your own tools or MCP serverThe loop and context management are ready; the value is in your tool design.
A job whose steps are known in advanceWorkflow: fixed code + a few model callsNo agent needed; cheaper and more predictable (level 5).
CautionWhen you build your own harness, security becomes your responsibility too. Tool results are untrusted input; a web page or a database row can carry text that looks to the model like an instruction. Restricting privileges, network isolation and human approval for irreversible actions are the harness’s job. Do not ship an agent that faces the outside world before reading level 10.

Key takeaways

  • If you can, do not write it from scratch: the Claude Agent SDK or the OpenAI Agents SDK gives you most of the layers ready-made.
  • Minimum production harness: stop condition, permission checks, output cap, deterministic verifier, context management, checkpoints, session log.
  • Whatever you add, there is only one line with the model in it; the rest of the harness is ordinary, testable software.
  • LLM-as-judge is the verifier of last resort; tests, lint and type checks come first.
