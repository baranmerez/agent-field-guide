A one-sentence definition, ten lines of code

The word agent has been stuck onto so many things in the last two years that its meaning has gone blurry. The definition that is useful to an engineer is short: an agent is a model that runs tools in a loop until it reaches a goal.

In September 2025 Simon Willison boiled this down to one sentence: “An LLM agent runs tools in a loop to achieve a goal.” Anthropic’s context engineering post says the same thing: an agent is an LLM autonomously using tools in a loop. Both definitions have three parts: tools (we covered them in level 4), the loop (the subject of this level) and the goal, the thing that decides when the loop ends. Take away any one of the three and you no longer have an agent: a loop without tools is just a chat talking to itself, a tool without a loop is a one-off function call, and a loop without a goal is an infinite loop that burns money.

The canonical loop

The loop in Anthropic’s tool use documentation works like this. The harness sends the messages and tool definitions to the model. As long as the response’s stop_reason field is "tool_use", the harness runs the requested tools, appends the model’s response (the assistant message) to the history, then appends a user message carrying the tool results, and calls the model again. When stop_reason has any other value, the loop exits. At the heart of every coding agent, no matter how many layers are stacked on top, this loop is beating.

messages = [user(task)]
for turn in range(MAX_TURNS):                  # hard stop condition
    resp = llm(system, tools, messages)        # PURPLE: the single probabilistic line
    messages.append(assistant(resp.content))   # the response enters the history
    if resp.stop_reason != "tool_use":         # end_turn / max_tokens / refusal
        break
    results = [run(t) for t in resp.tool_uses] # TEAL: deterministic execution
    messages.append(user([tool_result(r) for r in results]))
    if tokens(messages) > BUDGET:              # context management
        messages = compact(messages)
else:
    raise MaxTurnsExceeded()                   # limit reached, controlled failure

The intelligence is in one line

The only “smart” place in the code is the llm(...) call. The model decides what to read, which command to run and whether the work is done. Every other line is ordinary, deterministic, testable software: appending to a list, comparing a field, calling a function. This split is the most solid frame for thinking about agent systems. When something goes wrong, the first question should be: did the model make the wrong decision, or did the harness fail to give it the information, tool or feedback it needed to make the right one? The second case comes up far more often than you would think, and it is also much easier to fix, because that side is the one you write.

You already know thisThink of the reconcile loop in Kubernetes: the controller observes the current state, compares it with the desired state, takes an action and observes again. It stops when it reaches the desired state. The agent loop has the same skeleton. The difference is that “the gap between desired and current state” is computed by a model, not by a deterministic diff function. That is why neither the stop condition nor the correctness of the action is guaranteed; you have to put fuses around the loop.

stop_reason: the loop’s steering wheel

A single field decides where the loop goes. Each stop_reason value means something different to the loop, and harnesses that do not tell them apart break silently. The most common bug is treating everything other than tool_use as “work done”. A response cut off by max_tokens is not finished; it is truncated. refusal is not a finished job but a refused one, and it should be shown to the user as such. In server-side tool loops (such as web search), pause_turn means “I hit the iteration limit, resend the request to continue”; a harness that mistakes it for completion abandons the work halfway.

The same loop in the other ecosystem

The OpenAI Agents SDK loop is a slightly more abstracted version of the same idea. The SDK calls the model; if the output is “final”, meaning there is text output of the requested type and no tool call, it stops. If the output is a handoff, it passes control to another agent. If there are tool calls, it runs them, appends the results and calls again. When the max_turns limit is exceeded it raises MaxTurnsExceeded; if you defined an error handler, you can return a controlled final output instead. So both big providers guarantee the same three things: append tool results to the history, recognize the final answer, set a limit.

Where did it come from?

This loop did not appear overnight. The 2022 ReAct paper popularised the idea of having the model write “Thought / Action / Observation” lines in turn and executing the Action line by parsing it out of plain text. Back then the harness caught a line like Action: search[...] with a regular expression; if the model bent the format a little, the loop broke. Toolformer in 2023 showed that a model could learn to insert API calls into its own text. Today’s native tool calling APIs are the productised descendants of those ideas: the model no longer produces free text but a structured tool_use block that matches a schema, and it learns this specifically in post-training (levels 1 and 4).

CautionDo not write an unbounded loop. An agent built on while True, with no turn or budget limit, can repeat the same failing command until morning, and because it resends the whole history every turn, the cost grows with every turn. The limit belongs on the loop’s first line; it is not an improvement to add later.

Key takeaways

  • Agent = a model that runs tools in a loop until it reaches a goal. The harness writes the loop.
  • The loop’s steering wheel is stop_reason. Every value other than tool_use has its own meaning; do not call them all “done”.
  • The intelligence is in one line; the rest is deterministic code. When debugging, ask first: “model or harness?”
  • Give every loop a turn and budget limit from day one.

An agent fixing a red test, in the raw

What you see in the UI is a few lines of summary: “Ran 3 commands, edited 2 files, tests pass.” Behind the curtain there is a message array that grows every turn, seven model calls and, at one point, a harness that rejects the model’s “done” decision. In this lesson we lift that curtain.

Here is the scenario: example_app is an ASP.NET Core API backed by PostgreSQL. After this morning’s deploy, one of the OrderMapper tests is red: Map_NullStatus_ReturnsUnknown. When an order’s status_code comes in as NULL, the mapper throws InvalidCastException. The user types one sentence to the agent: “The OrderMapper test in example_app is red, fix it.” The harness has a Stop hook that runs the tests; the moment the agent says “done”, the harness will run the tests itself.

What did you see in the simulation?

The model did not run anything. Every model call produced either plain text or a tool_use block. It was always the harness that ran dotnet test, read the file and applied the edit. On the next step the model only saw the text the harness put back as a tool_result. That is why how clear and how short the tool output is directly determines the quality of the model’s next decision (which is exactly what good tool design in level 4 is for).

Every call re-read the whole history. On the first call the model saw roughly nine thousand tokens of system prompt and tool definitions plus a sixty-token user message. On the last call it saw all of that plus every tool result, its own earlier responses and the hook feedback. Because the API is stateless (level 2), this is unavoidable. The result: total processed input grows not linearly with the number of turns but roughly quadratically. The “total processed input” counter at the bottom right of the simulation shows this. Prompt caching cuts the price of that load considerably, but it does not reduce the space it takes in the context window.

Tool results filled most of the context. What the model wrote itself is a few hundred tokens; the test output and file contents are thousands. In real sessions the ratio is even more extreme: a single log dump or a whole large file can take tens of thousands of tokens. That is why Claude Code capping a single tool output at 25,000 tokens is a harness decision.

The critical moment: where the model says “done”

On the fourth model call the model said “Fixed it” and stopped with end_turn. But the fix was incomplete: it assigned "UNKNOWN" in the NULL case, yet a normalization a few lines below lowercased that value. Because the model finished without rerunning the test, it never saw this. This is the most common failure mode of agents: premature completion. From the inside, the model has no signal that could show it the difference between “I made a sensible fix” and “the fix works”; only a verifier can produce that signal.

This is where the harness stepped in. The configured Stop hook ran the tests when the model wanted to stop; because the test was red, it exited with code 2. In Claude Code that means the hook’s error output is passed back to the model and the loop continues. The model saw “1 test failed: expected UNKNOWN, got unknown” as a new message and solved the problem in two turns. The user probably did not even notice this extra round.

You already know thisA Stop hook works like a CI gate placed inside the loop. When a developer says “merge it” and the pipeline is red, nothing gets merged; when the agent says “done” and the test is red, the turn does not end. The difference is that CI reports to a human, while the hook reports straight to the model. That makes the hook output a prompt too: a short, actionable message that says which test broke and why gets a fix far faster than a long stack dump.

What you do not see in the UI

Had you watched this session in a terminal, you would most likely have seen a few tool lines, a “Fixed it” message, a short hook notice and the final summary. The real message array lives in the harness’s session log. Claude Code writes sessions to JSONL files, and resuming or forking a session works from that log; we will open it up in levels 6 and 8. When you are trying to understand an agent’s behavior, looking at this raw log is always more instructive than looking at the summary in the UI. The model decided based on what it saw; you cannot judge its decision without knowing what that was.

In practiceWhen an agent makes a strange decision, first ask “what was in the context at that moment?” In Claude Code, /context shows what the context is filled with. If you are writing your own harness, logging the full request body of every model call is half of debugging.

Key takeaways

  • A session is a single messages array that grows every turn; every model call re-reads all of it.
  • Tool results fill most of the context. Short, clear tool output is both cheaper and leads to better decisions.
  • When the model says “done”, the work may not be done. A harness that puts a verifier at the loop’s exit catches this.

Not every LLM application needs to be an agent

Once you learn the loop, you want to build a loop for everything. Yet for many jobs the best solution is a flow where your code decides the steps and the model is only called at specific points.

Anthropic made this distinction explicit in “Building effective agents”, published in December 2024. It calls both “agentic systems” but splits them in two. In workflows, LLMs and tools are orchestrated through predefined code paths: the order, the branching and the stop condition are written in your code. In agents, the model directs its own process and tool use: the model decides how many steps to take, which tool to call and when to stop. The first is a pipeline; the second is an employee with a goal.

Both share the same building block: the augmented LLM, a single model call enhanced with retrieval, tools and memory. Workflows wire these blocks together with code; an agent puts the block in a loop.

Five workflow patterns

The post lists five patterns that show up often in production. Knowing all of them pays off, because being able to look at a problem and say “this is a routing problem” saves you from building an agent you did not need.

  1. Prompt chaining. The work is split into sequential steps; each step’s output is the next one’s input. You can put programmatic gates between steps: if the output is not in the expected format, the chain stops. Example: extract the changes from commit messages, categorize them, write the release notes.
  2. Routing. A classifier recognizes the input and sends it to a specialized handler. Each branch runs with its own prompt, and if needed with a cheaper or a stronger model. Example: sorting incoming support tickets into billing, technical bug and feature request.
  3. Parallelization. It comes in two forms. Sectioning: the work is split into independent pieces that run in parallel, and the results are merged. Voting: the same task is run several times and the decision is made by a vote or a threshold. Example: reviewing a PR separately for security, performance and readability; or checking a security suspicion with three independent runs.
  4. Orchestrator-workers. An orchestrator model dynamically breaks the work into subtasks, hands them to workers and merges the results. The difference from parallelization is that the subtasks are not known in advance. Example: a change where you cannot tell up front how many files it will touch.
  5. Evaluator-optimizer. One model generates, another call evaluates against criteria and gives feedback, and the generator tries again. It works for tasks with clear evaluation criteria where iteration genuinely improves the result. Example: a translation that must follow a terminology glossary.

When is it an agent?

Anthropic’s advice is surprisingly conservative: start with the simplest solution and add complexity only when you see a measurable benefit. Most of the time the simplest solution is a single model call enriched with retrieval and a few examples. Workflows give predictability and consistency for well-defined tasks. Agents are for open-ended problems where the number of steps cannot be known in advance and the path cannot be hard-coded. “Find and fix this bug” is exactly that kind of job: nobody can know how many files will be read or how many times the tests will run.

The price of an agent is just as clear: you trade flexibility for higher cost and latency, and errors compound. Even if each step has a 95 percent chance of being right, the chance that 20 independent steps all go right is 0.9520 ≈ 36 percent. This simple calculation treats the steps as independent, and in reality the picture is not that grim because agents can see and correct their mistakes; but it explains well why a long agent chain without a verifier is fragile. If you are going to use agents, the post itself recommends testing in a sandbox and setting up guardrails from the start.

Multi-agent systems cost even more. In Anthropic’s research system (June 2025), single-agent runs used about 4 times the tokens of a chat, and multi-agent runs about 15 times. The same post notes that most coding tasks, which need shared context, are not a great fit for multi-agent parallelism. That is why subagents in Claude Code are used mostly for “explore in a clean window and bring back a summary”; more on that in level 8.

You already know thisA workflow is like a CI pipeline or a DAG: the steps are written in YAML, each step’s input and output are known, and when a step breaks you know where it broke. An agent is like an engineer you hand a job to and tell “let me know when it’s done”. You use both, but not for the same job. Nobody hands the release pipeline to an intern with “you decide how to do it each time”.
Myth“Agents are here, workflows are obsolete.” Even Anthropic’s current prompting guide says the opposite: although the model handles multi-step reasoning well on its own, explicit prompt chaining is still useful when you need to inspect intermediate outputs or enforce a specific pipeline structure. For work that needs an audit trail, compliance and reproducibility, a workflow is often the right answer.

How does the loop break, and what holds it together?

Agent failures are not random; they fall into a few familiar patterns. Once you recognize the pattern, the cure is largely known too, and most cures live in the harness, not in the prompt.

1. Premature completion

The model says “done” before the work is done. As you saw in the previous lesson, from the inside the model has no signal that shows the difference between “I made a sensible change” and “the change works”. Long tasks have another variant: a freshly started session looks around, sees that a lot of code has been written and decides the project is finished. The cures are layered. In the prompt, give a verifiable definition of “done” (level 3). For long jobs, keep a structured feature list where every item starts with "passes": false; let the agent change only that field, and state explicitly that deleting or editing tests is unacceptable. On the harness side, put a verifier at the loop’s exit: in Claude Code, if a Stop hook returns exit code 2, Claude is sent back to work. This is not infinite either: if the hook blocks 8 times in a row, Claude Code disregards the hook and ends the turn. As an alternative, the /goal command has a separate model check every turn whether the condition has been met.

2. Doing everything at once

An agent that tries to finish a big task in one go leaves three half-built features and a broken build in the middle of its context. The cure from Anthropic’s long-running agent experiments is simple: work on one feature per session and end the session in a clean, committable state. We will see this in detail in the next lesson.

3. Looping and thrashing

The model retries the same failing command over and over with small variations. Every attempt adds another error output to the context, and as the context grows the model loses focus even further. There is a harness version of this too: thrashing. If a large tool output refills the context right after compaction, the harness keeps trying to compress; Claude Code gives up on automatic compaction after a few attempts. The cure is always a hard limit: maximum turns, maximum tokens or maximum time. Claude Code’s auto mode has something similar: if the classifier blocks 3 actions in a row (or 20 in total), Claude Code drops out of auto mode and goes back to asking you.

4. Drift

Drift is the agent slowly wandering away from the task: while fixing a null bug it thinks “while I’m here” and starts fixing naming in six files. The resulting diff is harder to review and carries unwanted changes. Claude Code’s advice is practical: watch the first minute and press Esc as soon as you see it veer; if two correction attempts fail, clear with /clear and write a better prompt. Trying to repair a polluted context is usually more expensive than starting over with a clean one.

5. Overeager or too timid

Some models and prompts push the agent to call a tool for every little thing; others make it stop at the first ambiguity and ask the user a question. OpenAI’s GPT-5 guide shows both directions are tunable: to curb eagerness, a tool call budget and an escape hatch along the lines of “proceed even if you are not sure”; to increase persistence, an instruction telling it not to hand back on uncertainty. Anthropic also provides two opposing example blocks: one says to take action by default, the other says not to act until instructed. Which one you choose depends on the risk of the work.

6. Destructive shortcuts

An agent locked onto its goal may pick the shortest way to remove an obstacle: skipping the pre-commit hook with --no-verify, force pushing, deleting the red test, dropping and recreating a table. Anthropic suggests an example prompt block that says to ask for confirmation before hard-to-reverse actions and not to use destructive actions as shortcuts. But a prompt is a request, not a guarantee. Real protection lives in permission rules, hooks and the sandbox (levels 6, 8 and 10).

7. Stopping early near the context limit

Models that can track their remaining token budget may start wrapping up in a hurry when they notice the window is about to fill. If the harness is going to compact, you need to say so in the prompt; otherwise the model finishes early when it could actually have kept going.

Loop simulator with failure injection

Key takeaways

  • Seven familiar patterns: premature completion, everything at once, looping/thrashing, drift, too much or too little eagerness, destructive shortcuts, stopping early near the limit.
  • Most cures live in the harness: turn limits, a Stop hook or /goal, permission rules, starting over with a clean context.
  • Intervene early when you see drift; after two failed corrections, /clear.
  • If the verifier is unreliable, the agent will find a way around it. Protect the verifier too.

Work that does not fit in one context window

As of November 2026, all current Claude models have a 1M-token context window. That is a lot of room, but it is not unlimited; and as you saw in level 2, the model’s recall quality drops as the window fills. That is why work that takes hours is spread across several sessions, that is, several clean windows.

The problem is that every new session starts with no memory. It does not know what the previous session did, what it left half-finished or which approach did not work. There are two ways out. The first is compaction: summarize the conversation that is about to overflow and continue from the summary. The second is restarting from the file system: keep the state on disk rather than in the model’s memory, and open every session from scratch by reading those files. Anthropic’s current guidance recommends the second wherever possible.

Anthropic’s recipe for long-running agents

In November 2025 Anthropic described the harness it used to have an agent build an application across many sessions. The recipe rests on two kinds of session.

  1. Initializer session. Sets up the project: an init.sh that brings up the development environment, a JSON feature list that lists every feature to build and marks all of them as failing, a progress file (claude-progress.txt) where progress is recorded, and the first git commit.
  2. Coding sessions. Each one opens the same way: read the progress file and the recent git log, bring up the environment with init.sh, check that the basic functionality still works, pick one failing feature from the list, implement and test it, set its passes field to true only if the test passed, commit, and update the progress file.

You already know thisThe context is RAM, the file system is disk. When a database crashes, it does not try to rescue the state in RAM; it reads the WAL and the last checkpoint on disk and rebuilds. Here the git log plays the WAL, the progress file plays the checkpoint, and init.sh is the recovery procedure. Or think of an on-call handover: without a good handover note, the night shift has to rediscover everything from scratch.

When compaction, when a clean start?

Compaction is not bad; it is practical for work on a single problem that needs a short break. But a summary is lossy. The Claude Code documentation says so plainly: automatic compaction preserves requests and key code, but detailed instructions from early in the conversation may be lost. That is why persistent rules go into CLAUDE.md, because that file is reloaded on every request (covered in level 9 together with the context budget). Restarting from the file system, on the other hand, is lossless, because you decide what is kept: the progress note, the feature list, the commit history.

One more detail: some models track their remaining token budget. If the harness is going to compact, or the work is going to span several windows, you need to say so in the prompt. Otherwise the model may notice the window filling up and try to close the work in a hurry. In Claude Code you can also use /goal for a long objective: a separate model checks every turn whether the condition has been met.

Tasks are getting longer

This recipe matters more and more. According to METR’s measurement, the length of tasks (measured in human time) that models can complete with 50 percent success doubled roughly every 7 months between 2019 and 2025. More recent estimates suggest that period is getting shorter; however, we could not verify those figures against a primary source, so we do not give them here. The trend is clear enough: as the work handed to agents gets longer, designing the handover between sessions becomes a harness responsibility.

In practiceWhen you start a job that will take several sessions, dedicate the first session to setup only: create a script with the run and test commands, a JSON to-do list and a short progress file, and commit. Make the first message of every later session the same: “read the progress file and the last 10 commits, pick one failing item from the list.”

Key takeaways

  • On long jobs, keep the state on disk, not in the context: a progress file, a JSON feature list, git history, a setup script.
  • One feature per session; every session ends in a clean, committable state.
  • Compaction is lossy; where possible, prefer a clean start from the file system.
  • If the harness will compact, tell the model; otherwise it may wrap up early as it nears the limit.

What closes the loop: the verifier

The answer to why the agent loop works so well is one word: feedback. Writing correct code in one shot is hard, for humans too. But writing it, running it, seeing the error and fixing it is much easier. The loop gives the model that opportunity; the verifier determines the quality of that opportunity.

In its post introducing the Claude Agent SDK, Anthropic describes an agent’s working rhythm with four verbs: gather context, take action, verify the work, repeat. The Claude Code documentation puts the same idea more sharply: give the model something that reports pass or fail, and it can close the loop itself. This may be the most practical sentence in the whole course. An agent’s quality is bounded by how verifiable the environment it works in is.

Kinds of verifier

Rules

Compiler, type checker, linter, unit and integration tests. Deterministic, fast, cheap. The agent’s best friend. The Agent SDK post puts this first.

Visual feedback

Take a screenshot and have the model look at it. In UI work it catches the alignment and overflow bugs that tests miss; but the interpretation is still up to the model.

LLM-as-judge

Another model call evaluates the output against criteria. For work that cannot be reduced to rules it may be the only option; Anthropic describes it as “generally not very robust”.

Human

Business rules, product decisions, architectural fit. The most expensive and slowest verifier; so everything a machine can catch should be caught before it gets there.

These kinds form a ladder: the further down you go, the wider the range of bugs that can be caught, but speed, cheapness and reliability drop. A good setup puts the cheap, deterministic ones inside the loop and the expensive ones at the loop’s exit. The compiler and focused unit tests can run after every edit; the full test suite when the agent says “done”; human review when the PR is opened.

Why are models so good in the loop?

In level 1 you saw reinforcement learning with verifiable rewards (RLVR): the model writes code, the tests run, and passing solutions are rewarded. Today’s coding models were trained heavily in exactly these environments, that is, on reading a test output and deciding the next move. When you give it a test command, you put it back in the environment it was trained in. When you do not, the model flies blind and when it says “done” nobody knows whether it really is.

Three places to put the verifier in the loop

  1. In the prompt. Tie the definition of “done” to a command: “first write a failing test that reproduces the bug, then fix it; finish when dotnet test passes.” Claude Code’s own example is the same: instead of “login is broken, fix it”, a task that includes the symptom, the relevant folder and the instruction “write a failing test first” (level 3).
  2. In the harness. Stop hook, /goal, automatic format and lint after edits. These do not depend on the model remembering; they run every time. Detailed setup in level 8.
  3. In the environment. Fast, focused test commands and readable error messages. A test suite that takes twenty minutes means only a handful of iterations per session. Being able to run a single class with a filter improves the agent’s speed and accuracy together.

The verifier’s output is a prompt too

A verifier does not just say pass or fail; what it says when it fails determines the model’s next move. Between an output that says “1 test failed” and one that says “Map_NullStatus_ReturnsUnknown: expected UNKNOWN, got unknown (OrderMapperTests.cs:42)” there is a difference of one or two turns for the agent. The reverse holds too: a stack dump hundreds of lines long fills the context and buries the line that matters. When you write your own Stop hook or test script, remember that the model will read the output: which test, which expectation, which file and line. A short, actionable, reproducible error message is the verifier-side counterpart of good tool design (level 4).

Then there is speed. The agent waits on every verification round, and every wait is real time. Instead of running the whole suite after every edit, running the relevant class with a filter inside the loop and saving the full suite for the “done” point makes room for far more iterations in the same session.

You already know thisThis is TDD’s red-green cycle. The difference: humans practise TDD through discipline, while for an agent you can make it mandatory. The “show me the red test first” step is also a diagnostic check: if the test really reproduces the bug you saw, you can be sure the fix fixes the right thing.
CautionGoodhart’s law applies to agents too: when a measure becomes a target, it stops being a good measure. An agent fixated on passing the tests may loosen an assertion, skip the test or set the expected value to the actual output. Read the diff of the test files separately; if possible, block edits to the test folder with a hook or require approval for them.

Key takeaways

  • An agent’s quality is bounded by the verifiability of its environment. Fast, deterministic verifiers are the best investment.
  • Cheap verifiers inside the loop, expensive ones at the exit: the compiler on every edit, the test suite at “done”, a human at the PR.
  • LLM-as-judge is for work that cannot be reduced to rules; on its own it is not a reliable gate.
  • Protect the verifier too: read the test diff, lock the test folder.
