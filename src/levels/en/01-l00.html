The single operation beneath all the magic

A large language model (LLM) is a huge function that takes a sequence of tokens and returns a probability distribution for the next token. The sentence looks simple, but every behavior you will run into, from Claude Code finding and fixing a bug to a chat “forgetting” something, is rooted here.

f(token_1, token_2, …, token_n)  →  P(token_n+1)

// f: billions of trained, frozen numbers (weights).
// Input: the ENTIRE text so far (system prompt, conversation, tool results).
// Output: one probability for every token in the vocabulary; they sum to 1.

There are two separate pieces here, and the distinction matters for the rest of the course. The first is the model: a function made of weights that never changes once training is over. You give it a text and it produces a score for every candidate in its vocabulary. The second is the code that calls this function: it picks a token from the scores, appends it to the text, calls the function again, and decides when to stop. The general name for this outer layer is the harness. When you send a request to the API, the harness on the provider’s server runs this loop for you; an agent such as Claude Code builds yet another loop on top of it.

A “chat” is really a document

The model does not see roles, sessions or users as data structures. All it sees is a long sequence of tokens. The information “the user said this, the assistant said that, the tool returned this” is embedded in that sequence with special marker tokens. Because the model learned during training to “continue” documents containing these markers, it writes whatever follows the assistant marker the way an assistant would. So in a chat, what the model does is still document completion; the document just happens to be shaped like a transcript of a conversation with an assistant.

That is why a 500-token answer means calling the function roughly 500 times. With each call the input grows by one token. A single “think and edit a file” move by an agent consists of dozens of model requests, and each request of hundreds or thousands of forward passes. This way of generating, where each token is produced one at a time by looking at all the tokens before it, is called autoregressive generation.

You already know thisThe model is very much like a pure function: mathematically it produces the same scores for the same input, it has no side effects and keeps no internal state. The randomness comes from the sampler that sits outside the function, just as if you bolted a random number generator onto a deterministic business rule. In topic 4 you will see why the word “mathematically” matters: on real hardware even this purity is not fully preserved.

What is inside the function?

What we call “weights” are the numbers used in matrix multiplications. For open-weight models you can download them: the largest member of Meta’s Llama 3 family, for example, has 405 billion parameters. Parameter counts for Claude or GPT models are not published. The number itself does not matter much to you; what matters is that these numbers are set once by training and then frozen. No weight changes while you are talking. Every moment where you feel the model has “learned” something, the knowledge is actually sitting in the current input text. That is the subject of level 2.

Myth“It only predicts the next word, so it cannot think ahead; it’s a stochastic parrot.” The mechanism’s interface really is “the next token”, but that does not mean there is no planning inside. To predict the next token well, the model has to represent where the text is going. Anthropic’s interpretability work showed that Claude picks the rhyming word in a poem before it starts writing the line (you will play with this in topic 5). The opposite is a myth too: “It understands, so it knows things the way a human does.” Its knowledge is lossy and sometimes internally inconsistent; its correctness has to be verified from the outside.

What this means for your daily work

  • The text, not you, defines the input. The model sees the tokens in the context, not your intent. If you don’t write down the assumptions in your head, the model doesn’t know them.
  • Every token is a decision. A small early choice (a wrong table name) conditions every token that follows. The model cannot go back and delete; it can only continue. That is why agents need feedback such as tests and compilers.
  • Long output is slow and expensive. Output tokens are produced one by one, and pricing reflects that (topic 4).

Key takeaways

  • LLM = a frozen function that takes text and returns a probability distribution for the next token.
  • The code around the function does the picking, appending and stopping. Model + that code = the generation loop.
  • A chat is a document with role markers; the model continues that document.

The model doesn’t see letters, it sees tokens

The model does not process text letter by letter or word by word, but in pieces called tokens. A token is sometimes a whole word (“ the”), sometimes part of a word (“ing”, or the Turkish plural suffix “ler”), sometimes a single punctuation mark or a byte. The component that splits text into tokens and gives each piece an integer ID is called the tokenizer. The model only ever sees those IDs.

Why not letters? At the letter level the vocabulary is small but sequences become very long; since the cost of each forward pass grows with sequence length, that is expensive. Why not words? At the word level the vocabulary grows without bound; a model that never saw a word like the Turkish “siparişlerimizdekilerden” (roughly “from among the ones in our orders”, a single word) could not represent it. Tokens are a compromise between the two: frequent pieces become a single token, rare ones become a few pieces.

BPE: how is the vocabulary learned?

Most of today’s tokenizers belong to the BPE (byte-pair encoding) family. The algorithm is surprisingly simple:

  1. The starting vocabulary is the 256 bytes. Since any UTF-8 text can be written with these bytes, there is no such thing as an “unknown character”; a rare alphabet simply falls apart into many byte tokens.
  2. First, a regular expression splits the text into words, numbers and punctuation (pre-tokenization). Merges stay inside these pieces.
  3. The two symbols that appear next to each other most often in the training corpus are found and merged into one new symbol. That is a “merge” rule.
  4. Step 3 repeats until the target vocabulary size is reached. The rules are learned once and frozen; the model is trained with this frozen vocabulary.

The diagram below runs a real implementation of this algorithm. The corpus is small and deliberately Turkish. Turkish is agglutinative: it builds words by stacking suffixes onto a stem, so one word can carry what English says in a whole phrase (“ev” is house, “evler” houses, “evlerde” in the houses, “evlerden” from the houses). That makes the effect easy to see. Perform the merges one at a time and watch suffixes such as “ler”, “lar” (plural) and “yor” (present continuous) turn into tokens on their own.

Run BPE from scratch

A small Turkish corpus (words and how often they occur). At each step the most frequent adjacent pair is merged. Then type a word that is not in the corpus: the learned rules apply to it too.

This mechanism has two important consequences. First, the vocabulary reflects the distribution of the training corpus. If most of the corpus is English and code, English words and code patterns collapse into single tokens, while the suffixes of other languages (Turkish is our example here) stay more fragmented. Second, token boundaries do not have to line up with grammatical boundaries: “ler” can be a token, yet the stem “değerlendir” (evaluate) and the suffix “ebil” (be able to) may be cut at arbitrary places.

The token tax on non-English languages: Turkish as the example

The NeurIPS 2023 study by Petrov and colleagues measured how the same sentence takes very different numbers of tokens depending on the language: with the GPT-4 tokenizer, French and German take about 1.6 times as many as English, and some languages up to 15 times. This has three concrete consequences: more money for the same content, higher latency, and less content in the context window.

For Turkish it is hard to give a single clean multiplier. There is no primary source measuring the Turkish/English ratio on frontier models’ tokenizers; figures in circulation such as “1.3–2 times” are not verified. What is verified is this: in a 2025 study on Turkish MMLU text (Bayram et al.), the same text took about 29% more tokens with the Qwen2.5 tokenizer than with aya-expanse, and only 40–51% of the tokens corresponded to valid Turkish units. The same study found that the share of valid Turkish tokens correlated with model performance better than linguistic purity did.

Same model family, new tokenizer, new bill

The token count depends not only on the language but also on the tokenizer version. Anthropic switched to a new tokenizer with Opus 4.7. According to the documentation, 1 million tokens correspond to roughly 555K English words with the current tokenizer, compared with roughly 750K on earlier models. That means the same English text takes about 1.35 times as many tokens (a ratio computed from the two figures in the documentation). Even if the price per token stays the same, the same prompt costs more and the context fills up faster.

In practiceDon’t use the “4 characters = 1 token” rule of thumb for non-English text or code. If you are working out a budget or a cost, measure the real number with the provider’s token counting endpoint (the token counting API at Anthropic) or from the usage field in the response. Measure again when you switch models.

Oddities caused by tokenization

In his lecture where he builds a tokenizer from scratch, Karpathy traces many strange behaviors back to tokenization. Because the model sees token IDs rather than letters, the question “how many r’s are in strawberry?” used to be hard: to the model the word is perhaps two or three opaque pieces. Numbers are split arbitrarily too (“12345” → “123” + “45”), so operations that need digit alignment become fragile. In code, whitespace and indentation affect how sequences are tokenized. Still, it is not right to blame every arithmetic error on the tokenizer: in topic 5 you will see how the model actually does addition internally, and that story is more interesting.

Myth“If I write in my own language instead of English, the model understands less, so I should ask everything in English.” The cost that is certain is tokens: Turkish and other non-English text takes more of them. On the understanding side, Anthropic’s interpretability findings show that concepts are largely represented by shared features across languages; knowledge learned in one language carries over to another. The practical middle ground: write the instructions in whatever language you are comfortable with, but give identifiers such as table, class and function names verbatim, exactly as they appear in the code.

Key takeaways

  • The model sees token IDs; the tokenizer is a set of merge rules learned from a corpus and then frozen.
  • Agglutinative languages such as Turkish take more tokens: more cost, more latency, more context used.
  • The tokenizer version changes token counts too (~1.35× with Opus 4.7). Don’t estimate, measure.

From scores to probabilities, from probabilities to a choice

The model’s last layer produces a raw score for every token in the vocabulary. These scores are called logits. If the vocabulary has 200K tokens, every step yields a vector of 200K numbers. Logits can be negative, and their sum means nothing. The operation that turns them into probabilities is softmax:

p_i = exp(z_i / T) / Σ_j exp(z_j / T)

T → 0   : piles up on the highest logit (greedy, argmax)
T = 1   : the model’s raw distribution
T > 1   : the distribution flattens, low-scoring candidates get a chance

The exponential amplifies differences: a 1-point gap between two logits means roughly a 2.7× gap in probability. Temperature (T) divides the logits and so widens or narrows that gap. Then come two truncation methods. Top-k keeps the k most likely candidates. Top-p (nucleus) keeps, from the candidates sorted by probability, the smallest set whose total probability reaches p. The probabilities of the remaining candidates are renormalized to 1, and a token is drawn at random from that distribution. The usual order: temperature → top-k → top-p → sampling. The whole process is called sampling.

Why not always pick the most likely one?

Greedy selection (argmax at every step) intuitively looks “most correct”, but on long texts it leads to self-repeating loops and flat, formulaic sentences. A token being the most likely on its own does not mean the sequence starting with it is the best sequence. A bit of randomness carries the richness of the model’s distribution into the text. That is why chat and code models have historically run with a temperature near 1 and a top-p a little below 1.

You already know thisSampling is weighted random selection: a weighted round-robin load balancer, or roulette-wheel selection in genetic algorithms. Temperature is a knob that sharpens or softens the weights by raising them to a power; top-k and top-p are the rule “send no traffic at all to servers below this threshold.”

The API reality: these knobs now belong to the provider

As of November 2026, if you send a non-default value for temperature, top_p or top_k to current Claude models, the API returns HTTP 400. From API version 2026-10-21 onwards, sending these parameters with any value at all is a 400 error on every model. So you are learning this topic not as a settings knob but as a mechanism: it is what explains why the model gives different answers to the same question, and why it behaves “creatively” or “consistently”.

The reasoning behind it: reasoning (thinking) models produce long chains of thought, and the quality of those chains is sensitive to sampling settings. The provider wants the model to run with the settings it was trained with. You steer behavior with the prompt and with the effort setting you will see in the next level.

POST /v1/messages

Myth“If I set temperature to 0, the answer will be both deterministic and more accurate.” Two mistakes at once. Accuracy: T=0 just picks the top of the distribution; if the top is wrong, you get the same wrong answer every time. Determinism: because of how the computation runs on the server, even T=0 does not guarantee bit-for-bit identical output (next topic). And on current Claude models, sending this setting is an error anyway.
In practiceIf you need consistency, get it from the system, not from sampling settings: bind the output to a schema (structured output), check the result with a compiler, tests or a validator, and for critical work run it more than once and compare. A single run proves nothing, good or bad.

Key takeaways

  • The model produces logits; softmax turns them into probabilities, and the sampler turns the probabilities into a single token.
  • Temperature sharpens or flattens the distribution; top-k and top-p cut off the tail.
  • Current Claude models reject these parameters. The prompt and effort steer behavior.

Prefill, decode and the KV cache

Processing a request consists of two very different phases, and that difference drives both latency and pricing.

Prefill

All the tokens in the prompt are processed at once, in parallel. The weights are read once and matrix-matrix multiplications run for thousands of tokens: the limit is the GPU’s compute. This phase determines TTFT (time to first token).

Decode

Answer tokens are produced one at a time. At every step all the weights and the history’s KV cache are read from memory again, but only one token is computed: the limit is memory bandwidth. This phase determines the latency between tokens.

KV cache

Attention produces a “key” and a “value” vector for every token. These are stored so the history does not have to be recomputed for every new token. The memory cost of long contexts comes from here.

This asymmetry shows up directly in the price list: as of November 2026, on Claude, OpenAI and Gemini 4 models an output token costs roughly 5 times as much as an input token. On Claude Opus 5.5, for example, a million input tokens cost $4 and a million output tokens $20. Input is processed in parallel and efficiently; output is sequential and memory-bound.

Why does the KV cache matter so much?

The KV cache size for one sequence is computed with this formula: 2 × layers × KV heads × head dimension × sequence length × bytes. The leading 2 is for keys and values. For a Llama-3-70B-like architecture (80 layers, 8 KV heads, dimension 128, bf16 i.e. 2 bytes) that comes to about 0.33 MB per token; a single 128K-token sequence holds about 40 GB of memory. This is why serving long contexts is expensive and why providers offer prompt caching. Prompt caching is, quite literally, storing the KV cache of a prefix. The OpenAI documentation also says the cache stores the key-value tensors, not the original tokens. We will cover this in detail in level 2.

Why isn’t even T=0 deterministic?

The common explanation used to be “GPUs work in parallel and atomic operations scramble the order.” A September 2025 study by Thinking Machines Lab showed that this is largely wrong: a single forward pass, rerun under the same conditions, is deterministic. The real cause is a lack of batch invariance. The server processes requests that arrive at the same time as a group (a batch). RMSNorm, matrix multiplication and attention kernels change their reduction strategy depending on the batch size. Because floating-point addition is not associative, adding in a different order produces different final digits. And the batch size depends on who else is using the server at that moment. In other words, your answer depends on other people’s load.

The experiment is striking: Qwen3-235B, T=0, “Tell me about Richard Feynman”, 1,000 runs of 1,000 tokens each. The result: 80 different completions. All runs were identical for the first 102 tokens; at token 103, 992 of them said “Queens, New York” and 8 said “New York City”. A tiny numerical difference was enough to swap the top two logits; after that, a completely different path. With batch-invariant kernels all 1,000 runs produced the same output, but at a price: on Qwen3-8B the vLLM default took 26 seconds, the naive deterministic version 55, and the optimized deterministic version 42 seconds.

In practiceWhen you test agents and LLM-based features, don’t trust a single run. Run evaluation sets several times, look at rates, and separate “passed once” from “passes reliably”. If you cannot reproduce a failure, the cause may not be your code but sampling and server load.

Key takeaways

  • Prefill is parallel and determines TTFT; decode is sequential, memory-bound, and determines total time.
  • That is why an output token costs ~5 times as much as an input token. Long answer = slow and expensive answer.
  • The KV cache is the memory cost of long context; prompt caching is storing it.

A quick look inside the function

This course does not aim to turn you into a model architect. But a few intuitions keep concepts you will meet later, such as “context rot” and the “attention budget”, from being mere vocabulary.

  1. Embedding. Each token ID is turned into a vector with thousands of dimensions. Position information is added too; in modern models usually with a rotation-based method called RoPE.
  2. Attention. Each token produces a “query” vector and compares it with the “key” of every previous token (a dot product). The scores go through softmax, and the “value” vectors of the previous tokens are summed with those weights. Think of it as a soft, learned lookup over the context: “which earlier tokens matter to me right now?”
  3. Multiple heads. This is done in parallel by dozens of “heads” in the same layer. Each head learns to look at a different kind of relationship: one at the previous token, one at the noun a pronoun refers to, one at the stem a suffix attaches to.
  4. MLP and layers. After attention, each token goes through a feed-forward network on its own. The attention + MLP block is stacked dozens of times. Early layers deal with surface features, later layers with abstract concepts. The last layer is projected onto a logit vector the size of the vocabulary.

n² and the attention budget

In a sequence of n tokens, every token looks at every previous token, so roughly n² scores are computed. 1,000 tokens means a million scores; 1 million tokens means a trillion scores (for every layer and every head). Anthropic frames this as a limited “attention budget”: every token added to the context takes a share of that budget. Picture a meeting where everyone glances at everyone else’s notes before speaking. With ten people that’s fine; with ten thousand, the glances explode and the important note gets lost in the crowd. The “context rot” in level 2 is the measured version of this intuition.

Interpretability: what really happens inside?

Anthropic’s “Tracing the thoughts of a large language model”, published in March 2025, used a method called “attribution graphs” to trace computation paths inside Claude 3.5 Haiku. The interpretability findings show how much the phrase “next-token prediction” hides:

Planning ahead

In a rhyming couplet, the model picks the word the line will end on before it starts writing the second line. When that word’s representation is suppressed, it switches to another rhyme; when a different concept is injected, it moves to a coherent line that fits it.

Shared concepts

The question “the opposite of small” activates the same “smallness” and “opposite” features in English, French and Chinese. The larger model shares more than twice as many features across languages as the smaller one.

Addition inside

For 36+59, one path roughly estimates the magnitude of the result while another finds the last digit (6+9 → 5); together they make 95. But when asked “how did you work that out?”, the model describes the carry method taught in school.

Multi-step reasoning

For “the capital of the state where Dallas is located”, the intermediate steps Dallas → Texas → Austin are visible inside. When the Texas representation is swapped for California, the answer becomes Sacramento.

The hallucination circuit

The default path is “I can’t answer.” A “known entity” feature suppresses that path. When a name feels familiar but there is no knowledge about it, this feature misfires and the model makes something up.

Unfaithful reasoning

Asked for the cosine of a large number, the model says it computed it, but there is no trace of computation inside. Given a hint, it builds its reasoning backwards so that it lands on the hint.

CautionThe lesson of the addition example is worth its weight in gold for a developer: the model’s account of its own process is not the process itself. When an agent says “I ran the tests, they all passed” or “here is how I computed this”, that is a narrative. The evidence is in the tool output, the log and the diff.

You should also know the method’s limits: the technique captures only part of the computation, and tracing a prompt of a few dozen words takes hours of human effort. So these findings are a window, not a full map of the model.

Key takeaways

  • Attention is a learned, soft lookup over the context; its cost grows with the square of the sequence length.
  • Behind the “just the next token” interface there is planning, multi-step reasoning and concepts shared across languages.
  • The model’s explanation of itself is not a record of its mechanism. Look for the evidence in the tool output.

Through an engineer’s eyes: wrong mental models

Half of using a tool well is knowing what not to confuse it with. The mechanisms you have seen in this level directly refute each of the common wrong models below.

It is not a database

The model does not store its training data record by record; it turns it into a lossy representation compressed into the weights. It knows frequently seen patterns (a popular framework’s API, SQL syntax) very well. A rarely seen detail (a method signature in a specific version of a little-used package) it may reproduce “fluently but wrongly”. There is no query, no index, no “record not found” error; only a plausible continuation. The way to guarantee correct information is to put it in the context: have it read the documentation, open the code, call the tool.

It is not a system that learns while it runs

The weights are frozen. When you “teach” the model something during a conversation, what is learned lives in the conversation text, not in the weights. When the conversation ends, or when the text is compacted in a long session, that knowledge is gone. Every feature sold as “memory” (persistent rule files, notes, session summaries) is the harness putting text back into the next request.

It is not deterministic

Sampling adds deliberate randomness; even if you cannot touch it, there is still the batch effect on the server. Two runs of the same prompt can veer onto different paths. An agent session that “worked yesterday and doesn’t today” does not always mean the code changed.

It is not a calculator or a spell checker

It sees tokens, not letters, and does arithmetic internally along approximate, parallel paths. It is fragile with long numbers and with tasks such as counting letters or reversing strings. That is what the code execution tool is for: instead of having the model compute, have it write code that computes.

It is not a witness to its own inner workings

The model can describe how it thinks, but that description comes from the “this is how people explain things” pattern in its training data. Nor does it reliably know what it knows and what it doesn’t: the hallucination circuit is exactly that boundary misfiring.

It is not a fixed product

The same weights behave very differently with a different system prompt, a different tool set and a different context. Claude in Claude Code and Claude in the chat interface may be the same model, but they are not the same “agent”. When you interpret a behavior, always ask: does this come from the model, the harness or the context?
