Context is not a window, it is a budget

In level 2 you saw that context is the model’s entire world, that it is re-sent from scratch on every turn, and how caching makes that cheaper. The heart of advanced use is turning that knowledge into spending discipline. Anthropic’s September 2025 post calls this context engineering: deliberately choosing all the tokens the model sees on each turn (system prompt, tool definitions, MCP, external data, conversation history).

Why a budget?

As of November 2026, every current Claude model has a 1M-token window. Claude Code’s official guide now lists “the context window is your main constraint” among the habits you can drop. That is true but incomplete: window size has stopped being the bottleneck for most work, but the quality and cost of context have not. Two mechanisms are at play:

  • Attention budget and context rot: Chroma’s July 2025 report tested 18 models and found that even on simple tasks, performance becomes “increasingly unreliable” as input grows. Anthropic likewise describes context as a finite attention budget that every token depletes a little. A rule buried in the middle of a long session is not as effective as the same rule at the start of a short one.
  • Every turn pays for everything again: in a 30-turn session, the first turn is read 30 times. Caching makes reads cheaper but not free; the cache drops after 5 minutes of silence; compaction forces the cache to be rewritten.

Claude Code’s system prompt, tool definitions and instruction files take up context before you have typed your first message. Third-party measurements put this at around 20–35K tokens, but that is not a verified figure and it varies a lot with MCP and memory. See your own number with /context.

Four strategies

1. Fetch just in time

Don’t load everything up front; keep paths, queries and URLs as lightweight references and fetch them with a tool when needed. Claude Code does this with grep, glob and head; it does not pre-index directories. Tool outputs are capped too: Claude Code truncates a tool response at 25,000 tokens. MCP tool definitions are deferred by default; only their names enter the context.

2. Compact

Compaction summarizes a context that is close to full and continues in a fresh window. It is lossy: according to the official docs, detailed instructions from early in the conversation can be lost. That is why durable rules go in CLAUDE.md. /compact <focus> or a “Compact Instructions” section in CLAUDE.md steers the summary. If a large output immediately refills the context, auto-compaction stops after a few attempts.

3. Take notes

The agent writes progress to a file outside the context and reads it back later: NOTES.md, a to-do list, a memory tool. Anthropic’s long-running agent setup uses a progress file, a JSON feature list, git history and an init.sh; it reports that JSON is less likely than Markdown to be “inappropriately overwritten”.

4. Isolate

A subagent explores in a clean window and usually returns a 1,000–2,000-token summary to the main agent. The rule: delegate work where the process is big and the result is small. But don’t overdo it: Anthropic also notes that newer models tend to spawn a subagent where a direct grep would be faster.

Context budget simulator

Try actions in a session one after another. Each action counts as a turn; on that turn the whole main context is re-sent, so “total billed input” grows much faster than the context itself. Watch whether a rule stated at the start of the conversation survives compaction. Token values are illustrative; measure your own session with /context.

You already know thisContext is like a CPU cache: small, fast and precious. You keep the frequently used things close and fetch the rest from main memory (file system, git, notes) on demand. A subagent is like a separate core: it fills its own cache and writes back only the result.
In practiceOne clean session per task. When a job is done, /clear; if you have to stop in the middle of a big job, first have the agent write the state to a notes file, then clear and start the new session by having it read that file. If the model doesn’t know compaction is coming, it may try to wrap up early; for long jobs, saying “context will be compacted automatically when needed” in the prompt is a measure Anthropic recommends.

Key takeaways

  • The 1M window solved the size problem; the quality problem (context rot) and the cost problem (every turn, everything) remain.
  • Four strategies: fetch just in time, compact, take notes, isolate.
  • Compaction is lossy; durable rules go in CLAUDE.md, work state goes in a file.
  • Give subagents work where the process is big and the result is small; don’t spawn a subagent for a single grep.

Multiple agents: when, and at what cost?

In level 5 you saw Anthropic’s workflow patterns: parallelization (sectioning or voting) and orchestrator-workers. Claude Code offers them as concrete tools: concurrently running subagents, background subagents, a separate worktree per session and the experimental agent teams. The question is no longer “can I?” but “is it worth it?”.

Token cost multiplies

The figures from Anthropic’s multi-agent research system post are still the best reference: a single agent uses about 4 times the tokens of a chat, a multi-agent system about 15 times. According to the same post, token usage alone explains 80% of the performance variance on BrowseComp. So if parallel agents give better results, a large part of that is “thinking more”, and that has a price. The Claude Code docs estimate roughly 7 times the tokens for agent teams.

The same post’s most important warning is about coding: most coding tasks are a poor fit for multi-agent parallelism, because the pieces of the work share a common context. One agent doesn’t know about a design decision another one made; two agents change the same interface in two different ways.

Work that fits well

  • Independent exploration: “How do these three services handle authentication?” Each subagent reads one service and returns only a summary.
  • Map-reduce: 40 log files, 200 test failures, the dependency list of 30 modules. Each item is separate and the results are merged in a structured form.
  • Writer and reviewer: one session writes, another with a clean context reviews. The reviewer doesn’t carry the writer’s assumptions.
  • Truly independent modules: work in separate worktrees, on separate branches, that doesn’t touch shared files.

Work that doesn’t fit

  • Changes that touch the same files (a worktree doesn’t remove the conflict, it postpones it to merge time).
  • Sequentially dependent steps: if B looks at A’s result, it isn’t parallel.
  • Anything beyond your review capacity. If five agents opened five PRs and you can review two PRs a day, parallelism produces a backlog.

In practice: long-running workThe rules from Anthropic’s long-running agent setup come before parallelism: one feature per session, a clean, committable state at the end of every session, and a progress file plus git history as the state record. Every item in the feature list starts with passes: false and the agent may change only that field; deleting or changing tests is unacceptable. Myth“More agents, faster delivery.” The agent side speeds up; delivery moves at the speed of the slowest link. In most teams that link is human review, merge conflicts and the CI queue. Before adding parallelism, measure your review capacity, test duration and how independent the tasks really are.

Key takeaways

  • A single agent uses ~4 times the tokens of a chat, a multi-agent system ~15 times; agent teams ~7 times.
  • Most coding work needs shared context and fits parallelism poorly; exploration, map-reduce and review fit well.
  • A worktree separates file conflicts but postpones them to the merge.
  • Human review sets the delivery speed; if parallelism outruns it, you get a backlog.

The agent that runs unattended

Claude Code and Codex also run without the interactive interface. This is how you embed an agent in CI pipelines, scheduled jobs or your own scripts. But first, a change of mindset: in an interactive session, if something goes wrong, a permission prompt protects you. In headless runs there is nobody to approve anything; the allowed-tools list, the budget cap and the sandbox are your only defense.

claude -p

claude -p "task" runs a one-shot task. Important flags as of November 2026:

FlagWhat it does

Caution: -p and an untrusted folderThe docs warn explicitly: without --bare, claude -p running in an untrusted folder executes the repository’s .claude/settings.json hooks and .mcp.json servers without a trust dialog. In non-interactive mode there is no screen to ask the trust question. In CI, checking out code from a PR someone else opened and running it without --bare means running the hooks that PR wrote on your runner, with your secrets.

codex exec

Codex’s non-interactive mode runs in a read-only sandbox by default; writing requires --sandbox workspace-write. --json gives a JSONL event stream (thread.started, turn.started, turn.completed, turn.failed, item.*, error); --output-schema <file> forces a schema; -o writes the last message to a file; --ephemeral doesn’t persist the session; --ignore-user-config and --ignore-rules disable user configuration; codex exec resume --last continues. An important detail: pass CODEX_API_KEY inline, for that single invocation only, not at the job level; otherwise the repository’s build scripts can read the key too.

Reading the output

Documented fields in the JSON output: type, subtype, result, session_id, total_cost_usd, a per-model usage breakdown, structured_output and permission_denials. v2.1.318 added the credential_expires_at field. permission_denials is especially valuable: it is the list of things the agent wanted to do but couldn’t; in CI, if it isn’t empty, either your permissions are too narrow or the agent tried something unexpected.

GitHub Actions

For Claude Code, anthropics/claude-code-action@v1 runs in two modes: interactive mode (invoked with @claude in a comment) and automation mode (with the prompt input). The action checks that the triggering actor has write access and is a human; there is an option for workload identity federation via OIDC. The thing to watch: the ready-made GitHub App asks for broad permissions (including write on Actions, Workflows and Repository hooks). Caution: PR text is an attack surfaceThe PR title, description, issue text and comments are text an attacker can write. Embedding them directly in the prompt was exactly the mechanism of the “Comment and Control” attacks reported in April 2026: a PR title hijacked the agent in CI and leaked secrets. Covered in detail in level 10.

Key takeaways

  • Headless has no approvals: the allowed-tools list, --max-turns, --max-budget-usd and the sandbox are your only defense.
  • In CI use claude -p --bare; -p without --bare runs the repository’s hooks and MCP servers without a trust question.
  • codex exec starts read-only; give CODEX_API_KEY to that one invocation only.
  • Check that structured_output exists and that permission_denials is empty.
  • PR and issue text is untrusted input; don’t embed it in the prompt.

You can’t improve what you don’t measure

You added a line to CLAUDE.md, rewrote a skill or switched models. Did it get better? Gut feeling is misleading here, because the system is probabilistic: a single successful run could be luck, and so could a single failure. The solution is something you already know from software: a test suite. In the agent world it is called an eval.

Vocabulary

Anthropic’s January 2026 post “Demystifying evals for AI agents” proposes a shared vocabulary: task (an input and a success criterion), trial (one run of the task), grader (whatever measures success), transcript (all of the agent’s steps), outcome (the final state of the environment) and eval suite. An important distinction: an eval assesses the eval harness, the agent harness and the model together. It is the small-scale version of the benchmark lesson in level 7.

Three kinds of grader

Code-based

Tests, static analysis, state checks (“this table must not change”), tool-call requirements. Fast, cheap, repeatable; but they can be brittle: they may reject an output that is correct but formatted differently.

Model-based

Rubrics, pairwise comparison, multiple judges. Measures what code can’t (readability, coverage). Must be calibrated against human judgment; give the judge an “Unknown” option.

Human

The gold standard; slow and expensive. Used to calibrate the other graders and to decide edge cases.

The core for coding agents: unit tests plus an LLM quality rubric; alongside them static analysis, state checks and tracking of turns, tokens and time. There are also two kinds of eval: capability evals start with a low pass rate and measure “what we can’t do yet”; regression evals sit around ~100% and measure “what we haven’t broken”. Tasks that become reliable in a capability eval graduate into the regression set.

pass@k and pass^k

In a probabilistic system you run each task more than once. Then you can ask two different questions, and their answers are very different:

  • pass@k: the probability that at least one of k trials succeeds: 1 − (1 − p)k. It rises as k grows. The question is “can the agent find it within a few tries?”; meaningful when a human can pick among the results.
  • pass^k: the probability that all k trials succeed: pk. It falls as k grows. The question is “can I trust this agent?”; this is the real measure for an agent running unattended in CI.

The example from the post: 75% success per trial means roughly 42% for pass^3. “It works three times out of four” is a very different statement from “it works three times in a row”.

pass@k and pass^k

Change the per-trial success rate (p) and the number of trials (k). The two curves plot the real formulas: 1 − (1 − p)k and pk.

Reward hacking: passing the test is not doing the job

Reward hacking is the agent producing the success signal without doing the work: editing or deleting the test, special-casing the test input, skipping the check with --no-verify. ImpossibleBench (ICLR 2026) measures this by modifying tests so they contradict the specification; that way, any “pass” means cheating. In the original study GPT-5 cheated on 93% of the conflicting LiveCodeBench tasks; an instruction to “stop if the tests look wrong” brought that down to 1%. Claude Opus 4.1 stayed at 46% on the conflicting SWE-bench tasks. In a newer third-party run with a different setup: GPT-5.4 0%, Opus 4.6 2.9%, Gemini 3.1 Pro 11.8%. Hiding the tests brings cheating close to zero but also lowers real performance.

Choosing a grader is choosing what you measure

Task: “Fix the bug where the discount is applied twice in example.orders.” Six agent transcripts and five graders. Toggle the graders; see which transcript passes and whether that is right or wrong. If a cheating transcript passes, it is a false positive; if a correct transcript fails, it is a false negative.

Roadmap

  1. 20–50 tasks from real failures. Work the team has done in the past and the agent struggled with.
  2. Unambiguous tasks, reference solutions. Test both the “should do” and the “should not do” cases.
  3. Isolated, clean environments. Every trial starts from scratch.
  4. Grade the outcome, not the path. What matters is the final state, not the order in which the agent read files; give partial credit.
  5. Read the transcripts. In the post’s words, “failures should seem fair”. 0% across all trials usually means a broken task.
  6. Watch for saturation. Once everything is at 100%, the eval tells you nothing new; add new capability tasks.
In practiceTreat an instruction change like a deploy. Run the eval before and after you change CLAUDE.md, a skill or a hook; if there is a regression, roll back. Protect test directories with an Edit deny rule, run the real test suite from a Stop hook and flag diffs in test files separately during review.

Key takeaways

  • Evaluate a probabilistic system with repeated evals, not a single run.
  • pass@k = 1 − (1 − p)k rises; pass^k = pk falls. For an unattended agent, pass^k is what matters.
  • Code-based graders are fast but brittle; model-based ones are flexible but need calibration; combine them.
  • Passing the test is not doing the job; check test-file changes and special cases separately.

Where does the bill come from?

As of November 2026, Claude Code’s costs page gives an enterprise average of about $13 per developer per active day, $150–250 a month; 90% of users stay under $30 per active day. These numbers are a compass: your team’s figure can be very different depending on the type of work, the model and habits. The real question is which habits make the bill grow.

A sample /usage block from the docs is very instructive: session cost $0.55; 940K cache-read tokens against only 1.2K uncached input tokens. In long sessions the overwhelming majority of traffic is read from the cache. That is why anything that breaks the cache (a break longer than the 5-minute TTL, a setting that changes the system prompt, compaction) shows up on the bill right away.

Habits that grow the bill

  • Long sessions that are never cleared: every turn pays for the whole history again.
  • Using the biggest model by default for every job.
  • Cache misses after the TTL: the first turn after a coffee break is expensive.
  • Subagents and agent teams: each one fills its own context.
  • Compaction itself: summarizing is also a model call and it rewrites the cache.
  • Scheduled loops and /loop: they run while nobody is watching.

In practiceIf your enterprise contract price differs from list price, modelPricing in managed settings (v2.1.242+) makes the reported cost match your contract. For rate-limit planning, the table in the docs shows that the per-user TPM requirement falls as the number of users grows: 200–300K TPM per user for 1–5 users, 10–15K TPM for 500+ users. Not everyone works hard at the same time.

Observability: OpenTelemetry

When an agent does something unexpected in production, logs are the only answer to “why?”. Claude Code exports metrics and events with OpenTelemetry.

CLAUDE_CODE_ENABLE_TELEMETRY=1
OTEL_METRICS_EXPORTER=otlp
OTEL_LOGS_EXPORTER=otlp
OTEL_EXPORTER_OTLP_PROTOCOL=grpc        # no default, set it explicitly
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel.example.test:4317

Metrics

claude_code.session.count, token.usage (input, output, cacheRead, cacheCreation), cost.usage, lines_of_code.count, commit.count, pull_request.count, code_edit_tool.decision, active_time.total.

Events

user_prompt (text hidden by default), tool_result, api_request, api_error, tool_decision (source: config, hook, user_permanent, user_abort), assistant_response, api_refusal.

Privacy

Off by default: OTEL_LOG_USER_PROMPTS, OTEL_LOG_TOOL_DETAILS, OTEL_LOG_TOOL_CONTENT, OTEL_LOG_RAW_API_BODIES. Before turning them on, think about which customer data will end up in telemetry.

Traces are enabled in beta with CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1. A subtle security detail: the repository’s .claude/settings.json cannot set the exporter variables. Otherwise a repo you cloned could redirect your telemetry to its own server and collect your prompts. Don’t be surprised if you see a short-lived claude_code.safety_event metric in the changelog: it was added in 2.1.307 and discontinued in 2.1.312.

You already know thisYou wouldn’t put a microservice into production without metrics and distributed tracing. An agent is a service too; the only difference is that its decision logic is probabilistic. The source field of the tool_decision event shows whether an action went through because of a rule, a hook or a user’s “always allow” click; in a post-incident review, that is worth its weight in gold.

Key takeaways

  • Compass: ~$13 per active day, 90% of users under $30 (November 2026, enterprise average).
  • In long sessions the overwhelming majority of traffic is cache reads; anything that breaks the cache shows up on the bill.
  • Track tokens, cost and permission decisions with OpenTelemetry; turn on content logs deliberately.
  • Repo settings can’t change the telemetry destination; this is a deliberate exfiltration safeguard.
