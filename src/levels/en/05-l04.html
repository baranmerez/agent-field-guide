The model runs nothing

You watch a coding agent read files, run tests, query a database. But the model does none of that. The model only produces tokens; some of those tokens form a machine-parseable piece of JSON that says “I want to run this tool with these arguments.” What actually runs it is your code, or the harness you use.

Anthropic’s documentation says it plainly: the model executes nothing on its own; it produces a structured request, your code performs the operation, and the result flows back. Take that sentence seriously and the whole architecture of tool use falls into place: permissions, security, error handling, logging, all of it lives on your side. On the model’s side there is only one decision: on this turn, do I write text or do I ask for a tool?

How does the model know how to make that decision? During post-training (we saw it in level 1) it was trained to read tool definitions and emit well-formed call blocks. So tool use is as much a learned behavior of the model as it is an API feature. The API then draws a strict contract around that behavior.

The four moves of the loop

  1. Request. Your code sends the API the system prompt, the tools array (name, description, input_schema for each tool) and the messages array. The API is stateless: the whole history goes out again on every request (level 2).
  2. Decision. If the model needs a tool, instead of plain text it emits one or more tool_use blocks: id, name, input. The response ends with stop_reason: "tool_use". That means “I’ve stopped, your turn.”
  3. Execution. Your code reads the block, validates the input, checks permissions and runs the tool. Whether it reads a file, runs SQL or makes an HTTP request, from here on it is ordinary software.
  4. Result. Your code appends the model’s response to the history as an assistant message, then appends a user message whose content starts with tool_result blocks, and calls the model again. Each tool_result says which call it answers through its tool_use_id field.

Here is what it looks like raw. The model’s response:

{
  "role": "assistant",
  "stop_reason": "tool_use",
  "content": [
    { "type": "text", "text": "Let me look up the order record." },
    { "type": "tool_use", "id": "toolu_01",
      "name": "example_orders_get", "input": { "order_id": 1042 } }
  ]
}

The two messages you append to the messages array of your next request:

{ "role": "assistant", "content": [ ...the content above, verbatim... ] },
{ "role": "user", "content": [
    { "type": "tool_result", "tool_use_id": "toolu_01",
      "content": "{\"order_id\":1042,\"status_code\":\"DELIVERED\"}" }
] }

Note: you put the model’s response back into the history exactly as it was. The model does not “remember” its previous turn; you show it again. That is also why tool_use_id exists: if the model asked for three tools in the same turn, this id is the only way it can match each result to its request.

You already know thisThe request-reply pattern in message queues: the client sends a message with a correlation id, and the reply comes back with the same id. Here the client is the model, the worker listening on the queue is your code, and the correlation id is tool_use.id ↔ tool_result.tool_use_id. Or the planner-executor split: the model writes a plan, the executor carries it out and reports back. The planner cannot know whether the executor really ran anything; it sees whatever gets reported to it.

Three buckets of tools

In Anthropic’s API, tools fall into three groups depending on who defines them and who runs them. The split matters because it tells you where the responsibility lies.

Your tools

You write the name, the description, the schema; you also run them. Business tools like example_orders_get and your own MCP servers live here. The loop turns in your code.

Anthropic-schema client tools

bash, text_editor, memory, computer, browser. Anthropic defines the schema; running them is still your job. Because the model was trained on thousands of successful trajectories with exactly these signatures, it calls them more reliably. We come back to them in level 6 as “tools baked into training.”

Server tools

web_search, web_fetch, code_execution, tool_search. They run on Anthropic’s infrastructure; the result arrives inside the response. If the server-side loop hits an iteration limit, the response comes back with pause_turn, and you resend the request to let it continue.

The strict rules of the contract

The API checks the shape of the message history tightly. The rules are not arbitrary; they preserve the order the model saw during training. Break them and the model never runs at all; the request comes back with HTTP 400:

  • Results come immediately. The user message carrying the results must come right after the assistant message that contains tool_use. You cannot slip another message in between.
  • Results first. In that user message’s content array, the tool_result blocks sit at the very start. Put a text block in front of them and you get a 400; if you need to add a note from the user, add it after the results.
  • Parallel results in one message. If the model asked for two tools in the same turn, both tool_results go in the same user message (topic 4).
  • Every request expects an answer. For every tool_use block you return a tool_result with the right tool_use_id. Even if the tool blew up: in that case is_error: true and an explanatory message.

The last rule is the one most often skipped in practice. When an exception happens inside a tool, handing the error back to the model with is_error: true instead of crashing the loop gives the model a chance to correct itself. According to Anthropic’s documentation, after an invalid call the model usually retries two or three times with corrections, and then apologizes and gives up. Whether those retries work depends on the quality of the error message. In the simulation below, see for yourself the difference between “failed” and an actionable error message.

OpenAI’s Responses API builds the same loop; the names differ, and so does one important detail.

That arguments is a string is a small but sneaky difference: your code has to open it with JSON.parse, and that step can blow up. When it does, don’t bring the loop down; return a function_call_output that explains the parse error and let the model fix it. CautionThe model sees only what you show it as a result, and it reads it. A web page, an email, an issue comment or a notes field in the example.customers table can contain text that looks like instructions. That is why Anthropic recommends putting untrusted content inside a tool_result rather than in the system prompt. But that alone is not protection; the real defense is the permission boundaries in the harness. Level 10: prompt injection.

Common mistakes

  • Sending only the results without appending the model’s response to the history. The API rejects a tool_result that has nothing to answer.
  • Not catching the tool’s exception and letting the loop crash. The agent dies on an error it could have fixed itself.
  • Returning "failed" or an 80-line traceback as the error message. The first carries no information; the second floods the context (topic 3).
  • Believing the model “ran” the tool and leaving logging to the model. Only your code knows what actually ran; the audit trail belongs there.

Key takeaways

  • The model does not call the tool; it writes a request to call it. Your code runs it, validates it and returns the result.
  • The key to the loop is stop_reason: "tool_use"; the key to the matching is tool_use.id ↔ tool_use_id.
  • The contract is strict: results come immediately, sit at the start of the content, and parallel results share one message. Otherwise, 400.
  • A tool error is not the end of the loop; it is an is_error: true result. The quality of the error message decides whether the model recovers.

A tool definition is a prompt

The model decides when and how to use a tool by looking only at the three fields you wrote: name, description and input schema. It has no access to your source code, your tests or your wiki page. Those three fields are the only user manual the tool offers the model.

An example from the research, a tool that searches shipment events:

{
  "name": "example_shipments_search",
  "description": "Search shipment events for one order in example.shipments.
    Use when the user asks where an order is or why it was late.
    Returns events oldest-first. Use response_format=summary unless
    the user needs every scan.",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": { "type": "integer", "description": "example.orders.order_id" },
      "response_format": { "type": "string", "enum": ["summary", "full"] }
    },
    "required": ["order_id"],
    "additionalProperties": false
  },
  "strict": true
}

Field by field

name is the tool’s identity in the model’s mind, and it sits in the same list as every other tool. A name like search loses its meaning when three different MCP servers bring the same name. A namespace by service and resource (example_shipments_search) both makes selection easier and prevents collisions. In the next topic we look at its measured effect.

description is where the real work happens. A good description answers four questions: what the tool does, when it should be used (and when not), what it returns, and what its limits and traps are. Anthropic recommends writing tool descriptions “as if you were explaining them to a new hire.” In their own SWE-bench Verified work they report that improving the tool descriptions alone took Claude Sonnet 3.5 to the best result of its time.

input_schema is a standard JSON Schema object: type, properties, required, enum, a per-field description. The schema does two jobs: it tells the model what it has to send, and it gives you a contract for validating the incoming input. Two near-identical field names (user and user_id), a format field left as free text, an id with an ambiguous type: these are places where the model has to guess, and every guess is a chance of error.

Myth“The schema is enough; the description is decoration, keep it short to save tokens.” The schema says what is valid; the description says what is right. When the model picks between two valid tools, it looks at the description, not the schema. Anthropic’s SWE-bench result came precisely from improving descriptions. You save tokens not by trimming descriptions but by removing unnecessary tools or loading definitions lazily (topic 5).

strict: true and the guaranteed schema

By default the model “reads” the schema but is not bound by it; sometimes it skips a required field, writes a value outside the enum, puts a string where an integer belongs. You validate the input, return an error, the model fixes it; that costs a turn and a few thousand tokens. In strict mode the API guarantees that the generated input will conform to the schema. Anthropic describes it plainly as something that “eliminates invalid calls.” The price is a few restrictions on the schema.

On the OpenAI side the restrictions are spelled out: strict mode requires additionalProperties: false, and every field in properties must be in the required list. You express an optional field not as “may be absent” but as “may be null”:

"response_format": { "type": ["string", "null"], "enum": ["summary", "full", null] }
"required": ["order_id", "response_format"]

It feels odd at first, but it makes sense: the schema behaves like a grammar; instead of the ambiguity of “this field is either there or not,” saying “this field is always there, its value may be null” makes generation deterministic.

input_examples: what the schema can’t say

JSON Schema can say “a date is a string,” but it can’t say “in this API dates look like 2026-10-01, the time zone is UTC, and in nested filters the customer comes before the status.” Anthropic’s input_examples field lets you add a few sample inputs to the tool definition. By Anthropic’s own measurement (November 2025, vendor data) accuracy on complex parameters rose from 72% to 90%. Examples are tokens too; add them not to every tool, only to the ones whose input is genuinely complex.

The token cost of definitions

Tool definitions don’t travel through some magic side channel; they are part of the prompt and are resent on every request. As of November 2026, according to Anthropic’s documentation, when tool use is enabled the API adds a tool-use system prompt of roughly 286 tokens before your definitions (Opus, Sonnet and Haiku 5.5). When you force a tool (tool_choice: any or tool, topic 4) that number grows; the example given for Opus 5 is 406 versus 286. Each definition’s own tokens come on top.

There is a second, less well-known consequence: prompt caching (level 2). At Anthropic the cache prefix is built in the order tools → system → messages, and changing the tool definitions invalidates the entire cache. Adding a tool mid-session, “touching up” a description or shuffling the order of the list means the whole prefix gets written from scratch on the next request. Keep the tool list fixed for the whole session. That is also why the current MCP version recommends that the tools/list response be deterministic (topic 6).

You already know thisLike writing an OpenAPI document, except the reader can’t ask questions, rereads the document from the top on every request and pays by the word. OpenAI’s guide calls this the “intern test”: with the information you gave the model, could an intern use this function correctly? If not, the model can’t either.

    Pitfalls

    • Overlapping tools. If search_orders and find_orders sit in the same list, the model picks between them at random. If a human can’t say for sure which one to use, neither can the model.
    • A description that lies. A tool that says “fast” but takes 40 seconds leads the model to call it again and again inside the loop. The description must describe the real behavior.
    • Shouting in capitals. Phrases like “CRITICAL: You MUST use this tool when…” were written for older models to fix under-calling; on newer models they cause over-calling. Anthropic recommends toning it down: “Use this tool when…”. Details in level 3.

    Key takeaways

    • Name, description and schema are everything the model knows about a tool. Put as much effort into the description as into the code.
    • Vague name, vague parameter, free-text format field: each one is a place where the model guesses.
    • strict: true closes off the class of invalid calls; on OpenAI every field is required and optionality is expressed with null.
    • Definitions are tokens on every request and the start of the cache prefix. Keep the list fixed within a session.

    Designing an interface for an agent

    You know user interface design: the same function is easy with a good screen and impossible with a bad one. The same holds for agents. The SWE-agent paper calls this the agent-computer interface (ACI) and shows that the same model does markedly better when only the interface changes.

    In the SWE-agent work (Yang et al., NeurIPS 2024), GPT-4 Turbo solved about 11% of SWE-bench Lite with a raw shell alone; with a windowed file viewer showing 100 lines, an edit command with a linter that rejects syntactically broken edits, and a search with short output, it rose to about 18%; with the edit command removed it fell to around 10%. These figures come from secondary summaries; check them against the table in the paper before quoting them. But the direction is beyond dispute: same model, different interface, different result. In level 6 we extend this idea to the whole harness.

    Anthropic’s seven principles

    In September 2025 Anthropic compiled its own experience of writing tools. Below I walk through each principle using Example Co’s order system.

    1. Don’t wrap endpoints; consolidate around the workflow. Giving the agent three tools because your REST API exposes list_users, list_events, create_event means also loading the orchestration onto it: three turns, three results in context, three chances for an error in between. Anthropic’s example merges them into a single schedule_event tool, and offers search_logs instead of read_logs. On the order side: instead of “fetch the order, then fetch the shipments, then decode the status code,” one tool that returns the information needed to answer the delay question in one go.
    2. Namespace. example_orders_search, example_shipments_search. When several MCP servers pour tools into the same list, the namespace rescues both selection and readability. Anthropic reports that even the choice of prefix versus suffix has a measurable effect.
    3. Return meaningful context. Human-readable names instead of UUIDs: not customer_id: "9f3c…" but customer: "Example Co". Let the model choose the level of detail it needs with a response_format enum (concise / detailed). In Anthropic’s Slack example the concise format took about a third of the tokens of the detailed one.
    4. Respect tokens. Pagination, filters, truncation with sensible defaults. Claude Code cuts tool responses off at 25,000 tokens. When you truncate, tell the model so and show it how to narrow the next request: “Showing the first 200 records; use a narrower date range or a status_code filter.”
    5. Actionable errors. Not a traceback but what is wrong and what is right: the valid values and an example of correct input.
    6. Write descriptions as if for a new hire. Spell out implicit knowledge (internal terms, abbreviations, relationships between resources). Don’t leave parameter names ambiguous: not user but user_id.
    7. Measure with realistic tasks. Not single-call toy tests but real tasks that chain several tools. Have the model analyze the transcripts and rewrite the tools. In Anthropic’s multi-agent research system, a tool-testing agent rewrote tool descriptions and cut task time for subsequent agents by 40% (vendor data).

    Poka-yoke: make the mistake impossible

    Poka-yoke, from Japanese manufacturing engineering, means a design that makes misuse physically impossible: like a USB plug that can’t go in upside down. In December 2024, while working on its SWE-bench agent, Anthropic saw the model make mistakes with relative file paths after it had moved out of the root directory. The fix was not to tell the model “be careful” but to make the tool require an absolute path; that eliminated a whole class of errors.

    Poka-yoke opportunities in your own tools: require ids as integers, constrain formats with enums, add a confirmation field for dangerous operations, accept a single date format and write it in the description. Writing a rule into the prompt is a request; writing it into the schema is a guarantee. We will see the general form of this idea in level 6 under “the right place for a rule.”

    You already know thisThe difference between git status and git status --porcelain. The first is designed for humans, the second for machines; same information, different consumer. The response_format enum is the agent version of the same idea. And an actionable tool error is to the model what a good CLI error message (“unknown option --forse; did you mean --force?”) is to you.

    An error message is an instruction

    When a tool returns an error, that message is the only information the model has. Say “failed” and the model, with no idea what happened, repeats the same call or tries a random variation. Return a traceback and it will most likely find the fix, but it dumps internal file paths and stack frames into the context; a long stack takes thousands of tokens. An actionable message gives the model enough information to fix things on the next turn, and no more than it needs. MCP’s 2025-11-25 version also requires input validation errors to be returned not as protocol errors but as tool execution errors; the goal is exactly that the model can see the error and correct itself.

    Three error messages, three different next turns

    The model sent the date to the example_orders_search tool in the wrong format. The tool can return the error in three different ways. For each one, see what the model does next (simulated) and what it costs.

    Pitfalls

    • One tool that does everything. Taking “consolidate around the workflow” too far and writing an example_do_anything with 30 parameters just moves the selection problem from the tool list to the parameter list. The yardstick: a tool should map to a question the user might ask or a job they might want done.
    • Returning everything “just in case.” The model does not ignore the extra fields; it reads them, reasons about them and sometimes uses the wrong one. Make the default response short and the detail optional.
    • Silent truncation. Cutting the result at 200 lines without saying so leads the model to draw a confident conclusion from incomplete data. If you truncated, write the count and how to get the rest.
    • Secrets in the error message. An exception text containing a connection string, an internal server name or a token goes straight into the context, from there into the logs, and maybe on to another tool. An error message is text written for the model; don’t put anything there you wouldn’t show a user.

    Key takeaways

    • Tools are the agent’s interface; the same model works markedly better with a good interface.
    • Don’t wrap endpoints; consolidate the workflow into one tool. Namespace, return meaningful names, let the model choose the level of detail.
    • When truncating, say how to narrow; when returning an error, give an example of the correct input.
    • Bake the rule into the schema where possible (poka-yoke): a guarantee, not a request.

    Several calls in one turn

    The model can emit more than one tool_use block in the same response. These are called parallel tool calls, and at Anthropic they are on by default. This small feature radically changes both the duration and the cost of an agent session.

    Why? Because every model turn costs two things. The first is time: the model takes time to process its input and to produce its output token by token; the tool itself is often faster than that. The second is tokens: because the API is stateless, the whole history is resent on every turn. If the model reads three files one by one, that is four turns, with a growing history in all four. If it asks for all three in the same turn, two turns. The gap widens as the number of independent reads grows.

    Nothing new on the mechanism side: the model writes several blocks, each with its own id. Your code can run them concurrently if it wants, and sends all the results back in a single user message, each with its own tool_use_id. You saw this in the simulation in topic 1: toolu_01 and toolu_02 went out in the same turn, and their results came back in the same message.

    When is parallel safe?

    On the model’s side, parallelism is a suggestion; your executor decides what actually runs concurrently. Independent reads (two files, three queries) run in parallel without trouble. Two calls that write to the same resource (two edits on the same file, two requests updating the same order), however, must be serialized; just because the model wrote two blocks in the same turn doesn’t mean you have to run them at the same time. It is the same engineering decision as running independent SELECTs in parallel in a database while queueing the UPDATEs.

    If you want to turn parallelism off, use disable_parallel_tool_use: true inside tool_choice at Anthropic, or parallel_tool_calls: false at OpenAI; OpenAI says that in that case a turn will contain zero or one call. In the other direction, you can also increase parallel calling: the <use_parallel_tool_calls> block in Anthropic’s prompting guide is said to raise doing independent operations in the same turn to “nearly 100%”. For Fable 5.1, repeating that instruction on every turn is recommended (as of November 2026).

    tool_choice: who picks the tool?

    By default the model decides on its own whether to use a tool. tool_choice lets you narrow that decision.

    When does forcing make sense? The most common use is structured data extraction: you define a “record” tool, force it with tool, and the input the model produces is exactly the JSON you wanted. This approach has gained importance: since the Claude 4.6 models, prefilling the last assistant turn returns a 400 error; the recommended ways to get JSON are structured outputs or tools (level 3). Inside a conversation, though, forcing is usually a bad idea: with any on, the model has to call a tool even if the user just says “thanks.”

    OpenAI’s allowed_tools option reflects a subtle engineering decision: changing the tool list breaks the prompt cache (topic 2), but passing the allowed subset in a separate field doesn’t. So you can say “only read tools in this step” and keep the cache. A warning applies at Anthropic too: changing tool_choice invalidates the messages part of the cache. Don’t change it on every turn.

    Tuning triggering through the prompt

    tool_choice is a blunt switch; fine-tuning happens in the prompt. Anthropic’s documentation gives two extreme examples: “Use the tools to investigate before responding.” increases tool calling; a phrase in the style of “Use your judgment…” makes the model more conservative. Because newer models are far more sensitive to the system prompt, aggressive phrasing written to fix under-triggering in older models now causes over-triggering. OpenAI says the same thing: a team working with GPT-5 describes how the instruction “Be THOROUGH when gathering information” caused unnecessary searches even on small tasks, and softening the wording fixed it.

    Common mistakes

    • Splitting results across messages. Sending the results of two parallel calls in two separate user messages breaks the contract: the first message is missing the answer to toolu_02. Collect all the results and send them in one message.
    • Getting stuck on the slowest tool. In a parallel turn the model waits until all results arrive. If one hangs, the turn hangs. Put a timeout on every tool; when it expires, return is_error: true for that call with a result like “No response within 30 s, retry with a narrower filter,” and don’t hold up the others.
    • Running parallel side effects blindly. The model may ask for “edit the file” and “run the tests” in the same turn. Run them at the same time and the tests run against the old file. Execute calls with side effects sequentially, in the order the model wrote them.
    • Leaving tool_choice pinned. If you forget to switch a setting you moved to tool for an extraction step back to auto on the next conversation turn, the model answers every message by calling that same tool.

    Key takeaways

    • Parallel calls reduce the number of model turns and the history that gets resent. Independent reads in parallel, writes to the same resource in sequence.
    • All parallel results go in one user message, each with its own tool_use_id.
    • tool_choice: auto for conversation, tool for structured extraction. any and tool enlarge the system prompt.
    • Don’t change the tool list or tool_choice on every turn; the cache breaks. If you need a subset, use allowed_tools on OpenAI.

    Tool definitions are context too

    For an agent working with five tools, the cost of the definitions is negligible. But connect three or four MCP servers and the picture changes: in Anthropic’s own example, 58 MCP tools take about 55,000 tokens before the conversation has even started.

    That creates two separate problems. The first is cost and latency: those 55 thousand tokens go out again on every request. Cache reads make it cheaper but not free; at November 2026 prices, normal input on Opus 5.5 is $4 per million tokens and a cache read is $0.20. The second, sneakier one is attention: the size of the context window (1M today) tells you its capacity, not its quality. As the window fills, recall weakens (context rot, level 2), and picking the right tool among dozens of similar ones gets harder. OpenAI’s function calling guide even gives a rough limit for this: aim for fewer than 20 functions.

    Tool search: load definitions on demand

    Anthropic’s answer is the Tool Search Tool, announced in November 2025. When you mark a tool with defer_loading: true, its definition does not enter the context up front. The model sees a small tool for searching tools; when it needs a capability it searches for it, and only the definitions of matching tools are loaded. Think of it as an application loading modules with dynamic import when needed instead of loading all of them at startup.

    Results reported by Anthropic (vendor data, 24 November 2025): in the 58-tool example the definition load fell from about 55K to about 8.7K tokens (roughly an 85% reduction). On the MCP evaluation, accuracy rose from 49% to 74% on Opus 4 and from 79.5% to 88.1% on Opus 4.5. So it is not just savings; a model that sees fewer but more relevant tools chooses better.

    Claude Code makes this the default: MCP tool definitions are deferred via tool search, and only tool names and server instructions stay in context. You can see this breakdown in your own session with /context (levels 8 and 9). OpenAI also supports tool search and namespaces; as of November 2026 it requires gpt-5.4 or later models.

    Programmatic tool calling: keep intermediate results out of the context

    Tool search solves the load of the definitions; the load of the results is a separate problem. Suppose you want to find which of Example Co’s 120 orders delayed in October passed through the TST-2 hub. In the classic flow the model first fetches the orders, then calls the shipment tool for each one; all 120 results enter the context, and the model filters them “in its head.” It is both expensive and error-prone: for an LLM, missing one row in a long list is much easier than writing an if inside a loop.

    With programmatic tool calling, you say allowed_callers: ["code_execution_20250825"] when you define the tool. The model calls these tools not directly but from inside a program it writes in the code execution environment. The loop, the filtering and the joining happen in code; only what the program prints comes back into the context. In Anthropic’s measurement (vendor data) the average tokens per task fell from 43,588 to 27,297 (about 37%).

    Exposing MCP as a code API

    On 4 November 2025 Anthropic published a post that takes the same idea one step further: expose MCP servers not as a tool list but as code modules sitting in a file system (like ./servers/google-drive/getDocument.ts). The agent reads the file it needs, writes the code and filters the data inside the sandbox. In the post’s example of moving data from Google Drive to a CRM, token usage dropped from about 150K to about 2K (98.7%). Side benefits: personal data can be masked in the sandbox before it reaches anywhere the model will see it; a piece of code that works can be saved as a skill and reused. Cloudflare calls the same idea “Code Mode.”

    You already know this“Take the computation to the data, don’t bring the data to the computation.” Instead of pulling 120 thousand rows into the application and filtering them in C#, you run the WHERE in the database. Programmatic tool calling is the LLM version of the same decision: do the filtering in code, not in the context.

    Which one when?

    These three techniques solve different bottlenecks; don’t substitute one for another. If the problem is “a tenth of the context is full of tool definitions before the conversation starts,” use tool search. If the problem is “tool results are large and the model reads them only to filter them,” use programmatic tool calling. If the problem is “exposing dozens of services one by one as tools has become unmanageable,” expose MCP as a code API. An agent with five tools and small results needs none of them; an extra layer is extra error surface.

    They have their costs too. With tool search the model has to find the tool: a tool with a bad name and description is no longer merely misused, it is never found at all. That is why the design principles of topics 2 and 3 become even more important as scale grows. There is also no point deferring the few core tools used on every turn; they are needed on every request anyway. With programmatic calling, intermediate results can drop out of your sight just as they drop out of the model’s: if one of the 120 calls inside the code fails silently, the model only sees it if the program prints it. Log the calls inside the sandbox too, and ask the program to report errors explicitly.

    CautionAll of these approaches mean that code written by the model runs somewhere. Anthropic’s post states clearly that this requires a secure sandbox: resource limits, network isolation, observability. Anthropic’s server-side code execution tool provides that environment; if you are building it into your own harness, the responsibility is yours. Level 10.

    Key takeaways

    • Tool definitions are context sent with every request. 58 tools ≈ 55K tokens; selection quality also drops as the number of tools grows.
    • defer_loading + tool search: load definitions when needed. In Anthropic’s example, about 85% fewer tokens and higher accuracy.
    • Programmatic tool calling and exposing MCP as a code API: intermediate results stay in the sandbox, only a summary returns to the context.
    • Every solution that runs code needs a sandbox.

    Why a protocol?

    If every AI application writes its own integration with every service, you need N applications × M services worth of integrations. Model Context Protocol (MCP) exists to bring that down to N + M: a service writes an MCP server once, and every MCP-capable application can use it.

    You already know thisLanguage Server Protocol. Editors used to need a separate plugin for every language; with LSP a language writes a server once, and both VS Code and Vim speak to it. MCP makes the same move for tools and data sources; underneath, like LSP, it uses JSON-RPC 2.0.

    Three roles: host, client, server

    The host is the AI application the user works in: Claude Code, an IDE, a desktop app. It is the one that talks to the LLM API, manages user approval and makes the security decisions. The host creates a separate client for each server it connects to; each client holds a one-to-one connection with a single server. The specification’s deliberate design decision: servers must not be able to read the whole conversation, and must not see into one another. Only the host combines the context.

    This also means MCP does not talk to the model directly. The model still writes a tool_use block as in topic 1; the host knows it belongs to an MCP tool, sends a tools/call to the server through the corresponding client, and hands the answer back to the model as a tool_result. MCP is the cable between the harness and the outside world; the contract between the model and the harness stays the same.

    This “who controls it” column is the least-read yet most important part of MCP. The model can call a tool on its own; that is why, when operations with side effects are exposed as tools, the approval layer must live in the host. A resource, on the other hand, enters the context only when the application or the user selects it.

    Transport: stdio and Streamable HTTP

    With stdio, the host starts the server as a child process and sends JSON-RPC messages line by line over standard input/output. Simple and fast for local tools; credentials come from environment variables and the process runs with your user permissions. With Streamable HTTP, every message is POSTed to a single endpoint; the response comes back as plain JSON or as a request-specific SSE stream. In the current version requests carry the MCP-Protocol-Version, Mcp-Method and Mcp-Name headers, so a gateway can see which tool is being called without opening the body.

    2026-07-28: the protocol goes stateless

    As of November 2026 the current specification version is 2026-07-28. Compared with the previous version (2025-11-25) it brings a major architectural change; if you learned MCP from an older guide, most of what follows will be new to you.

    Topic2025-11-252026-07-28
    Connection setupinitialize handshake, sessionNo handshake. Every request carries the protocol version and client capabilities in _meta; new and mandatory server/discover
    SessionMcp-Session-Id headerRemoved. A server that needs state issues an explicit handle and passes it around as a tool argument
    Server asking the clientThe server sends its own request (elicitation/create, sampling/createMessage, roots/list)MRTR: the server returns resultType: "input_required", the client resends the request with inputResponses
    DeprecatedRoots, Sampling, Logging (use a tool parameter, call the LLM API directly, log to stderr/OTel), the old HTTP+SSE transport, Dynamic Client Registration
    Long-running workExperimental tasksMoved to the io.modelcontextprotocol/tasks extension

    Why statelessness? In a session-based protocol, requests from the same client have to go to the same server instance; scaling horizontally behind a load balancer gets hard. In the stateless model each request carries its own context, and any instance can answer. MRTR follows from the same logic: the server can no longer ask the client a question over an open channel; it returns a result saying “to do this I need the following information,” and the client adds the answer and repeats the request. It resembles getting a 401 over HTTP and retrying with a token.

    Authorization

    stdio servers take their credentials from the environment. For servers running over HTTP the specification defines OAuth 2.1, and it is quite strict:

    • The MCP server is a resource server and MUST publish Protected Resource Metadata (RFC 9728); that is where the client learns which authorization server to go to.
    • When requesting a token the client MUST send the resource indicator (RFC 8707); the server MUST verify that the token was issued for it (audience).
    • Token passthrough is forbidden: the server may not accept any other token, and may not forward a token it received to an API behind it. Otherwise the authority you grant one server leaks into everything it talks to.
    • PKCE and iss validation (RFC 9207) are mandatory. With insufficient scope the server returns 403 and a step-up scope flow begins.
    • Dynamic Client Registration is deprecated; Client ID Metadata Documents replace it.
    CautionAdding an MCP server is adding a dependency, and one that can write text straight into your context. Tool descriptions and tool results are text the model reads; a malicious or compromised server can plant instructions there. A stdio server runs with your user permissions; a remote server sees every piece of data you send in tool arguments. Who wrote it, which tools it exposes, which permissions it runs with: review these the way you would review a NuGet or npm package. Details in level 10.
    In practiceAfter connecting a new MCP server, check how much room it takes in Claude Code with /context; gate tools with side effects behind approval using permission rules (level 8). If you are writing your own server, the tool design principles of this level apply unchanged: namespacing, a concise response format, actionable errors, a deterministic tools/list.

    Key takeaways

    • MCP is LSP for tools and data sources: the host opens a separate client for each server, and only the host combines the context.
    • Tools are under the model’s control, resources under the application’s, prompts under the user’s. Approval for tools with side effects lives in the host.
    • With 2026-07-28 the protocol is stateless: no handshake and no session, but there is server/discover; to ask a question the server returns input_required.
    • HTTP servers are protected with OAuth 2.1; token passthrough is forbidden. Every MCP server is a dependency and an attack surface.
