Instructions hidden in data

In level 5 we said that tool results are untrusted input. Now let’s see why. For the model there is no hard boundary between instructions and data: both are part of the same token sequence. If a web page, an issue comment, a README or a database row says “ignore previous instructions and do this”, the model will sometimes treat it as an instruction. That is not a software bug; it is a natural consequence of the architecture.

You already know thisRemember SQL injection. The fix was not to “read user input carefully”; it was to separate data from commands structurally: parameterized queries. LLMs do not have such a clean separation yet. The system prompt, the user message and the tool result are marked with different roles, but in the end they all become a single stream of text that the model reads. That is why defense relies on restricting what the model can attempt to do.

Direct and indirect

Direct

The attacker is the user: they try to push the model outside its rules with the text they type into the chat (a jailbreak). In a coding agent this matters less: the user is already you, and you can do whatever you like on your own machine anyway.

Indirect

The instruction is hidden in content the agent reads: issues, PR titles, web pages, READMEs, dependency docs, MCP tool descriptions, rules files. The user is innocent, the agent is innocent; the attacker has left a note on the agent’s path. For coding agents, this is the real threat.

Prompt injection is number one on OWASP’s 2025 Top 10 for LLM applications (LLM01). The first item of the agentic applications list published in December 2025 comes from the same root: agent goal hijack (ASI01).

Why model-side defense is not enough

As you saw in level 7, both labs train their models with an instruction hierarchy: tool output is data, not instructions. Modern models are increasingly resistant to these attacks. But that resistance is probabilistic. In Simon Willison’s words, a 95% detection rate in security is “very much a failing grade”: the attacker can try a hundred times and only needs one to land. You would never accept a web product that says “we stop 95% of SQL injections”.

Invisible instructions

The sneakiest form of indirect injection is text a human cannot see but the model reads. HTML comments, white-on-white text and image alt text are well-known routes. Less known are invisible Unicode characters:

  • Zero-width characters: U+200B, U+200C, U+200D, U+2060, U+FEFF. They take up no space on screen; they can split words to slip past filters, or carry information.
  • Direction control (bidi) characters: U+202A–U+202E and U+2066–U+2069. They change the displayed order of text, so what a human sees differs from what the machine reads.
  • Tag characters: the U+E0000–U+E007F range. Every ASCII character has an invisible “twin”, so an entire sentence can be embedded invisibly, and some models can read it.

The “Rules File Backdoor” attack reported in early 2025 used exactly this: invisible characters embedded in Cursor and GitHub Copilot rules files steered code generation in the direction the attacker wanted, and kept living when the repository was forked. In code review the file looked innocent.

Invisible text detector

The AGENTS.md in the box looks innocent. The detector marks every invisible character, decodes text embedded in tag characters and gives you the cleaned version. You can paste your own file too; nothing leaves your browser.

In practiceReview rules files (AGENTS.md, CLAUDE.md, .claude/rules, .cursor/rules) like code and check for invisible characters in CI: an instruction file containing anything from the ranges above should block the merge. Put prompts and skills you copy from elsewhere through the same filter.

Key takeaways

  • The model cannot reliably separate instructions from data; a tool result is always untrusted input.
  • For coding agents the real threat is indirect injection: issues, PRs, the web, READMEs, tool descriptions, rules files.
  • Model-side resistance is probabilistic; 95% is not a passing grade in security.
  • Invisible Unicode (zero-width, bidi, tag) hides instructions from human eyes; scan rules files in CI.

When the risk becomes truly dangerous

The framework Simon Willison named on 16 June 2025 shows clearly when prompt injection risk turns into a data leak. If an agent has all three of the following at once, the lethal trifecta is complete:

  1. Access to private data: source code, secrets, customer records, private repositories, email.
  2. Exposure to untrusted content: the web, issues, PRs, email, dependencies, tool descriptions.
  3. The ability to communicate externally: an HTTP request, a PR or issue comment, git push, email, even an image URL or a DNS lookup.

The attacker’s recipe is simple: put an instruction in untrusted content, let the agent read it, have it pick up private data and send it out over an external channel. Willison’s remedy is just as simple: remove one of the three legs. Instead of trying to detect the attack, build a setup where it cannot do damage even if it succeeds.

In coding agents, all three are the default

The uncomfortable truth: a local coding agent has all three legs out of the box. It reads your repository and your home directory (private data); it reads web pages, dependency docs and issues (untrusted content); it has network access and can git push (external communication). Even a single MCP server can carry all three: in the GitHub MCP incident of May 2025, the same token could read a public issue, see private repositories and open a PR on a public repository.

The variety of exfiltration channels matters too. Shutting off network egress is the first thing most people think of; but if the agent writes a Markdown image pointing to the attacker’s server into a PR comment, what fetches that image is not your sandbox but the platform rendering the comment. The data leaves in the image URL’s query parameter.

Break the attack chain

Scenario: an agent triaging issues in Example Co’s public example/widgets repository. Its token can also see the private example/billing-internal repository. Someone has left a hidden instruction in an issue. Pick the exfiltration channel and the defenses, then run the attack. Probabilistic layers roll the dice on every run; the “Run 1000 times” button computes the expected leak rate.

Lessons from the lab. Narrowing the token’s scope to a single repository removes the private-data leg for certain. A read-only token closes the PR and comment channel but leaves the network channel open; a sandbox network allowlist closes the curl channel but cannot close the PR channel, because GitHub is allowed. The deny rule Bash(curl *) only stops curl when it is written out literally. The auto mode classifier and human approval are probabilistic: one misses 5.7% of synthetic exfiltration attempts, the other gets 93% of prompts approved. Plan-then-execute and dual LLM break the chain architecturally. Those are exactly the subject of the coming lessons.

CautionThe “Always Allow” button is not a convenience; it is a configuration decision that leaves one leg permanently open. In the GitHub MCP incident, users had pressed that button. A simple policy such as access to only one repository per session would have made that attack impossible.

Key takeaways

  • Private data + untrusted content + external communication = exfiltration risk. Remove one.
  • Coding agents have all three legs by default; even a single MCP server can carry all three.
  • Exfiltration channels are not just the network: PR comments, image URLs, git push, DNS.
  • Deterministic controls (token scope, network allowlist, write permission) cut legs; probabilistic controls lower the rate.

Patterns

The agent becomes the attacker’s tool

In the Nx “s1ngularity” attack, malicious npm releases invoked the agent CLIs installed on the machine with flags such as --dangerously-skip-permissions and --trust-all-tools and sent them hunting for secrets: 2,349 credentials from 1,079 systems. The attacker did not write their own code; they used your agent.

Configuration is code

Check Point’s February 2026 report showed two CVEs: a repository’s .claude/settings.json hooks and MCP definitions could run before the trust dialog (CVE-2025-59536, CVSS 8.7), and a repository could leak the API key by changing ANTHROPIC_BASE_URL (CVE-2026-21852). Both have been patched (1.0.111+ and 2.0.65+).

CI input becomes a prompt

In the “Comment and Control” attacks reported in April 2026, a PR title or issue text hijacked Claude Code Security Review (CVSS 9.4), the Gemini CLI Action and the Copilot agent in GitHub Actions and leaked secrets. The mechanism: untrusted text was embedded directly in the prompt. The source is a vendor blog; read the details with that in mind.
Myth“These attacks are lab demos; they don’t happen in the real world.” The list above has real victims: a deletion prompt merged into an IDE extension with hundreds of thousands of installs, an MCP server downloaded more than 1,600 times that sent a blind copy of every email to the attacker, credentials harvested from more than a thousand machines.

Key takeaways

  • Most incidents are either the lethal trifecta or the agent’s supply chain; often both.
  • Your installed agent CLI and your YOLO flags can become someone else’s attack tool.
  • A repository’s configuration files run code; every repo you clone is input an attacker can write.
  • Embedding untrusted text in a prompt in CI is an open invitation to remote command execution.

Defending with architecture

The paper “Design Patterns for Securing LLM Agents against Prompt Injections”, published by Beurer-Kellner and colleagues in June 2025, sets out the most useful principle in the field: once an agent has read an untrusted input, it must be impossible for that input to trigger a consequential action. Not “hard”: “impossible”. The paper proposes six patterns that achieve this principle. Their shared price is flexibility: the more you constrain an agent, the less general-purpose it becomes.

How far does the poisoned input get?

Pick a pattern and press “Trace the poisoned input”. Red marks the nodes untrusted content reaches; the line is the boundary where the flow stops. See what each pattern protects, what it costs and what it looks like in a coding agent.

CaMeL: provable security and its price

The CaMeL work by Debenedetti and colleagues from Google DeepMind and ETH Zurich, dated March 2025, takes the “write code, then run it” idea to its extreme. Control and data flow are derived only from the trusted user query; untrusted data can “never” change the program’s flow. Capabilities are attached to every value, and unauthorized flows are stopped at the moment of the tool call. On the AgentDojo benchmark the result is instructive: 77% of tasks are completed with provable security, against 84% for the undefended system. So the price of provable security is roughly 7 points of capability. That is a good measure of how security is always a design trade-off.

Harness controls: layers from the inside out

  1. Least privilege: every credential the agent holds has the narrowest permission the task requires. A read-only database role, a token scoped to a single repository, and never keys that bypass everything, like service_role. This is the cheapest and strongest control.
  2. A sandbox with two walls: Anthropic’s sandboxing post is explicit: without network isolation a compromised agent can exfiltrate data; without filesystem isolation it can escape. Both together.
  3. Credentials outside the sandbox: the web version of Claude Code keeps git credentials outside the sandbox, behind a narrowly scoped git proxy. The agent never sees the key.
  4. Deterministic controls: deny rules, PreToolUse hooks, managed settings. They work independently of the model’s decisions.
  5. Human approval only for the irreversible: a system that asks for approval on everything trains people to say “yes” blindly; 93% of prompts are approved anyway. Save approval for the moments that really matter.
  6. Probabilistic layers on the outside: the auto mode classifier, warnings in the prompt. Useful, but they do not cut a leg.
Go deeper: what does the auto mode classifier see?According to Anthropic’s March 2026 post, the classifier sees only the user messages and the tool calls; the assistant’s prose and the tool results are stripped out. This is deliberate context minimization: injected text cannot “argue” with the classifier, because the classifier never reads it. On top of that there is a separate server-side injection probe. The reported figures: a 0.4% false positive rate over 10k real actions; a 17% miss rate on 52 real overeager actions, and 5.7% on synthetic exfiltration. A good layer; not the only layer.

Key takeaways

  • The principle: once untrusted input has been read, it must be impossible for it to trigger a consequential action.
  • Six patterns: action-selector, plan-then-execute, map-reduce, dual LLM, code-then-execute, context minimization.
  • CaMeL: 77% of tasks provably secure, 84% undefended. Security is a trade-off.
  • Layers from the inside out: least privilege, a two-walled sandbox, credentials outside, deterministic controls, selective human approval, probabilistic layers.

The agent’s own dependencies

Everything you extend an agent with, that is MCP servers, skills, plugins and hooks, runs with your permissions. You should look at an MCP server with the same suspicion you give an npm package’s postinstall script. The difference: these components do not just run code, they also supply the text the model reads.

  • Tool poisoning: in April 2025 Invariant Labs showed that instructions embedded in MCP tool descriptions could steer the model. The user does not see the description; the model does.
  • Malicious server: the first malicious MCP server, found in September 2025 (postmark-mcp 1.0.16), forwarded a blind copy of every email sent to the attacker; it had been downloaded 1,643 times. Pinning versions and reviewing the diff of every update is how you catch a package that turns bad later.
  • The agent itself: in July 2025 a prompt containing deletion instructions got into version 1.84.0 of the Amazon Q VS Code extension through a merged PR; the extension had roughly 964k installs.

The repo you clone is input

The most practical lesson of this topic: a repository’s .claude/, .codex/, .mcp.json, AGENTS.md and CLAUDE.md files are input an attacker can write. After the CVEs Check Point found, Claude Code’s current behavior is built on that idea: the project’s hooks and MCP servers do not run until workspace trust is granted; allow rules in the project wait for trust, while deny and ask apply immediately; defaultMode: auto or bypassPermissions in the project file is ignored; imports from outside the project require approval; repository settings cannot change the telemetry destination. Codex runs hooks with hash-based trust. But the exception you saw in level 9 still stands: claude -p without --bare, in an untrusted folder, runs hooks and MCP servers with no trust dialog.

Slopsquatting: packages that do not exist

Models sometimes confidently suggest a package name that does not exist. A study published at USENIX Security 2025 collected 576k samples from 16 models: 19.7% of the suggested packages did not exist. The rate is ~5.2% for commercial models and ~21.7% for open models. The truly dangerous finding: 43% of the hallucinated names reappeared in all 10 repetitions. In other words, these names are predictable; an attacker can register them and fill them with malicious code. This is called slopsquatting.

Failing without an attacker

Beyond security, there are places where agents fail in predictable ways. These come not from malice but from the model’s inclination to “be helpful” and from missing context. OWASP’s agentic list names several of them: tool misuse (ASI02), unexpected code execution (ASI05), cascading failures (ASI08). Anthropic’s auto mode post also says the main threat is not an outside attack but overeager scope: work the user did not ask for, which the agent does “to be helpful”.

Five failures, five harness answers

Pick a failure mode. A realistic transcript opens, along with the mechanism and the concrete setting that answers it in the harness.

Why does it happen?

The same two mechanisms sit underneath all of them. First, the model focuses on the success signal: if the signal is “did the tests pass”, changing the test is one way to get there; if the signal is “is the error gone”, silencing the error message is another. This is the reward hacking from level 9. Second, the model guesses to fill gaps in its context: if it does not know a database’s name, it picks one with a similar name; if authentication failed, it looks for another key. Both are “clever” behaviors; what makes them dangerous is when they combine with an irreversible action.

Claude Code handles some dangerous actions at the harness level: rm and rmdir on critical paths are never auto-approved; auto mode blocks force pushes over other people’s work, production deploys and the curl | bash pattern. Anthropic also publishes a sample system prompt block that asks for confirmation before hard-to-reverse actions (force push, dropping tables) and tells the model not to use destructive shortcuts (such as --no-verify). The prompt helps; but the principle from level 8 applies here too: rules without exceptions belong in the harness.

Key takeaways

  • The main threat is often not an attacker but overeager scope; auto mode misses 17% of it.
  • Reward hacking and guessing a target are “clever” behaviors; the danger is in combining them with an irreversible action.
  • Don’t give the agent a production identity; if you can’t avoid it, put every path to production through a deterministic control.

A checklist for your own harness

Throughout this course you have met the parts of a harness one by one. If you are building your own agent (a CI reviewer, an internal support agent, or your team’s Claude Code setup), start with these questions. Each answer is a line of configuration.

  1. Identity: Which credentials does the agent run with, and are they broader than the task requires?
  2. Trifecta: Which of private data, untrusted content and external communication are really needed? Have you shut off the ones that aren’t?
  3. Irreversibles: Where are the irreversible actions, and do they go through a deterministic control?
  4. Verification: Is there a fast check the agent can use to verify its own work?
  5. Context: What lives in a persistent file, and what in a temporary session? Are the persistent rules in a file that gets loaded?
  6. Budget: Is there a ceiling on turns and spend?
  7. Measurement: Do you have a repeatable eval set that measures instruction changes?
  8. Trace: When something goes wrong, can you trace back what happened from the logs?

Closing: back to the equation

Agent=Model+Harness

In level zero we started with a frozen function: take text, return the probability of the next token. Then we talked about how that function is trained, what it sees, how to talk to it and how to put it in a loop. In level 6 we named the right-hand side of the equation; in level 7 we compared two ecosystems across those two layers; in 8 and 9 we shaped the harness for our own team and measured it. In this final level we talked about weaving permissions, sandboxes, hooks, evals and logs around that probabilistic function so it can be connected to real systems safely.

What to expect from the model

Capability, judgment and an instruction hierarchy. Probabilistic: right most of the time, sometimes confidently wrong. A better model means fewer mistakes, not zero mistakes.

What to expect from the harness

Deterministic boundaries: what it can see, what it can touch, when it stops, who approves, what gets logged. Rules that hold no matter what the model thinks.

What to expect from context

Everything the model knows at that moment. The right information at the right time, with the unnecessary kept out. The place where the two layers meet.

Perhaps the most important thing to take away as a team is this: the new part of this field is the presence of a probabilistic component. The rest, that is least privilege, defense in depth, testability, observability and code review, is engineering you have known for years. The teams that use agents well turn out to be not the ones who write the best prompt, but the ones who build the sturdiest deterministic frame around that probabilistic component. The next time an agent does something unexpected, let your first question be: is this the model, the harness, or the context?

Key takeaways

  • Security lives in the infrastructure, not in the prompt: least privilege, a two-walled sandbox, deterministic controls, selective human approval.
  • Break one leg of the lethal trifecta; don’t try to detect, try to make the damage impossible.
  • The agent’s configuration, its plugins and every text it reads are attack surface.
  • Measure: without evals, cost tracking and telemetry you cannot run an agent safely.
  • Agent = Model + Harness. For every behavior, first ask which layer it came from.
